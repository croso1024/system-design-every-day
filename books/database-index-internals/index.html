資料庫索引原理 (B+Tree / Composite / Covering Index)

「這條查詢為什麼沒走索引？」是後端面試最常見的追問之一。答案幾乎都落在三個問題上：索引能不能讓查詢定位到起點、定位之後要掃多少條目、掃到的條目夠不夠回答查詢，還是得回表。本篇從 B+Tree 的頁結構與樹高估算講起，對照 InnoDB 的聚簇索引與 PostgreSQL 的 Heap + TID，再走過複合索引的最左前綴、Covering Index、選擇性，以及函式包欄位、隱式轉型、前置萬用字元這些讓索引「建了卻用不上」的情境。

01

總覽：一條查詢走不走得到索引

索引是一份依 key 排好序、可以跳著找的副本；用不用得上它，取決於查詢的形狀。

沒有索引時，資料庫只能把整張表的每一頁讀一遍，也就是全表掃描。索引是另一棵依某些欄位排好序的樹，讓查詢直接跳到起點，只讀需要的那一段。代價是它佔空間，而且每一次寫入都要同步維護。

「這條為什麼沒走索引」幾乎都能拆成三個依序發生的問題。本篇的章節就照這三問展開：

WHERE 條件
比較的是哪些欄位、什麼形狀
▸
① 定位得到起點嗎
最左前綴、欄位有沒有被函式或轉型包住
▸
② 要掃多少
範圍有多寬、選擇性高不高
▸
③ 要不要回表
索引條目夠不夠回答查詢

三個問題有先後：① 不成立，② 就變成「整棵掃」；① ② 都便宜，③ 仍可能因為回表次數太多而讓優化器放棄索引。

讀者設定是日常寫 SQL、看過 EXPLAIN、知道「建索引會變快」，但還說不清楚「為什麼這條不會變快」的後端工程師。範例以 PostgreSQL 與 MySQL（InnoDB）為主，兩者在第 5 節會分開談，因為它們對「索引指向哪裡」的答案不同，很多面試追問就出在這裡。

範圍本篇只談索引的結構，以及查詢怎麼使用它

B-Tree 與 LSM-Tree 的寫入路徑對照在嵌入式資料庫篇。優化器如何估成本、EXPLAIN 怎麼讀、Join 演算法怎麼選，會在談查詢計畫的主題處理。InnoDB 的 Row Lock、Gap Lock 為什麼鎖在索引記錄上，則由談資料庫鎖與死鎖的主題負責。本篇在需要的地方點到為止。

一句話答法索引是依欄位排好序的 B+Tree；查詢要用上它，得先能從最左欄位定位到起點，掃描範圍要夠窄，最好還不用回表。三者任一不成立，優化器就可能選全表掃描。
02

為什麼是 B+Tree：頁、fanout 與葉節點鏈

記憶體與磁碟之間搬的是頁，不是列；B+Tree 讓每一頁塞滿分隔鍵，樹因此又矮又寬。

資料庫以頁（page）為單位讀寫。InnoDB 預設 16 KiB，PostgreSQL 8 KiB。就算只要一列，也得把整頁讀進 InnoDB 的 buffer pool 或 PostgreSQL 的 shared buffers。所以索引結構要壓低的不是比較次數，而是從根走到目標要讀幾頁。

B+Tree 的設計全部圍繞這件事：

  • 內部頁只放「分隔鍵 + 子頁指標」，不放整列資料。一頁能放幾百個子頁指標，這個數字叫 fanout。fanout 越大，樹越矮。
  • 所有 key 都在葉頁，而且所有葉頁在同一深度。任何查詢走的頁數都一樣，延遲可以預期。
  • 同一層的葉頁串成雙向鏈。範圍查詢只要定位起點一次，之後沿葉鏈往右讀，不必回到上層。

二元樹的 27 層來自 log₂(10⁸) ≈ 26.6。B+Tree 的 log 底數是幾百，同樣 1 億筆只要 3 到 4 層，第 3 節會把這個數字算出來。

命名上要注意：PostgreSQL 的文件與 InnoDB 的原始碼都把它們的索引叫 B-tree，但實作上都是 B+Tree 的變體。PostgreSQL 用的是 Lehman–Yao 版本，每頁多帶一個 high key（這頁的上界）與右鄰頁指標，讓並行的頁分裂不必鎖住整條下探路徑。

一頁裡面長什麼樣

以 InnoDB 的索引頁為例。聚簇索引與二級索引用的是同一種頁格式，差別只在記錄裡放什麼。

頁內找 key 一樣是二分搜尋，只是對象是 Page Directory 的 slot；跨頁靠的是 File Header 裡的上一頁／下一頁指標。

PostgreSQL 的 B-tree 頁格式不同，道理相同：頁頭之後是一排行指標（line pointer），索引條目從頁尾往前長，頁尾的 special space 放左右鄰頁指標與層級；不是最右邊的頁，第一筆條目是 high key。

陷阱「B+Tree 查詢是 O(log N)」答得太快

二元樹也是 O(log N)。面試官想聽的是底數：fanout 讓 1 億筆只有 3 到 4 層，而上面幾層小到幾乎一定在記憶體裡，所以一次等值查詢的實體 I/O 往往只剩葉頁那一次。B+Tree 贏在每次 I/O 能篩掉的範圍，不在 big-O。

一句話答法磁碟以頁為單位讀寫，B+Tree 讓內部頁只放分隔鍵、把 fanout 拉到幾百，1 億筆只要 3 到 4 層；資料全在同深度的葉頁，葉頁串成鏈，範圍查詢定位一次就能循序讀。
03

樹高估算：三四層撐起上億列

把頁大小、key 大小、列寬代進去，就能心算一棵樹有幾層。面試時寫出假設，比背出某個數字重要。

容量(h) = fanouth−1 × 每葉筆數

fanout 是一個內部頁能放幾組「分隔鍵 + 子頁指標」，每葉筆數是一個葉頁能放幾筆記錄，h 是樹的層數（含根與葉）。以下假設刻意取整，方便驗算：

  • InnoDB 頁 16 KiB = 16,384 B。扣掉頁頭、頁尾、Page Directory 與保留空間，假設可用約 15,000 B。
  • 主鍵 BIGINT（8 B）。內部頁每筆 = 8 B 主鍵 + 4 B 子頁號 + 約 5 B 記錄標頭 ≈ 17 B，fanout ≈ 15,000 ÷ 17 ≈ 880。
  • 聚簇索引的葉頁存整列。假設列寬 200 B（含記錄標頭，以及 InnoDB 每列隱藏的 6 B 交易 ID 與 7 B 回滾指標），每葉 75 列。
  • 二級索引 (user_id BIGINT)：葉頁每筆 = 8 B user_id + 8 B 主鍵 + 5 B 標頭 ≈ 21 B，每葉約 714 筆。非唯一的二級索引，內部頁也要帶主鍵才能唯一定位，每筆 ≈ 8 + 8 + 4 + 5 = 25 B，fanout 600。
  • PostgreSQL 頁 8 KiB。bigint 的 B-tree 條目 = 8 B 條目標頭（內含 6 B 的 TID）+ 8 B key + 4 B 行指標 ≈ 20 B，每頁約 400 筆，內部頁也取 400。

驗算：880² × 75 = 774,400 × 75 = 58,080,000。列寬減半，3 層就從 5,808 萬撐到 1.16 億。「欄位能小就小」在索引層的意義，是樹可能少一層。

所以 1 億列、列寬 200 B 的 InnoDB 表落在 4 層；把列寬壓到 100 B，3 層就夠。實際數字會因變長欄位、頁的填充率與碎片而上下浮動，但量級不會錯，而且最多差一層。

更值得算的是哪幾層會在記憶體裡。以 5,808 萬列、3 層的聚簇索引為例：葉頁有 58,080,000 ÷ 75 = 774,400 頁，約 11.8 GiB；中間層只有 880 頁，約 13.75 MiB；根 1 頁。上兩層小到一定常駐 buffer pool，所以一次主鍵等值查詢最多一次實體 I/O，而且只發生在葉頁沒被快取的時候。

關鍵回表的成本要乘上命中筆數

走二級索引再回表，每一筆命中都要從聚簇索引的根再下探一次。命中 1 筆時是 3 + 3 頁的邏輯讀，沒什麼感覺；命中 5,000 筆、而且散在 5,000 個不同的葉頁時，就是 5,000 次可能的隨機 I/O。這正是第 7 節「選擇性」要處理的問題。

一句話答法樹高 ≈ log 以 fanout 為底；16 KiB 頁、8 B 主鍵的 fanout 約 880，列寬 200 B 時每葉 75 列，3 層約 5,800 萬、4 層數百億。上層常駐記憶體，所以一次查詢大約只有葉頁那一次 I/O。
04

互動：在 B+Tree 上增刪 key，看頁分裂與範圍掃描

頁分裂、樹高與葉鏈要自己插幾個 key 才有手感。這棵樹的每個數字都由你的操作算出來。

這棵樹把頁容量刻意調得很小（每頁 3、4 或 6 個 key），讓幾十個 key 就長到 3 到 4 層。畫面與下方所有數字，都由 computeBTree() 把你的操作紀錄從空樹重播一遍算出來；切換頁容量或分裂點，就是用同一串操作重建一棵新樹。

  • 插入／刪除：輸入 1–99 的 key。葉頁超過容量就分裂，新右頁的第一個 key 當分隔鍵往父頁推；父頁也滿就繼續往上，推到根就長出新根，樹高 +1。
  • 遞增 vs 亂序：「遞增 1–30」模擬 AUTO_INCREMENT 主鍵，「亂序 30 筆」模擬隨機 UUID。比較兩者的填充率與葉鏈不連號次數。
  • 葉頁分裂點：「中點對半」是教科書做法；「遞增最佳化」模擬 InnoDB 偵測到循序插入時改在插入點分裂，舊頁留滿、新頁只放新 key。示範把它簡化成：新 key 落在最右葉頁的尾端時才套用，而且只套在葉頁。
  • 範圍掃描：改 BETWEEN 的上下界，看下探經過哪幾頁、葉鏈走過哪幾頁、一共讀幾頁。

藍框是範圍掃描的下探路徑與走過的葉頁，綠格是命中的 key，橘色虛線框是最後一次操作動到的頁。葉頁編號 L# 依配置順序遞增，葉鏈上的不連號，代表邏輯相鄰的兩頁在配置上並不相鄰。

可以照這三組實驗操作，數字都是按下按鈕後算出來的：

  1. 遞增插入與分裂點。按「遞增 1–30」（每頁 4 個 key、中點對半）：3 層、10 個葉頁、平均填充 75%、葉鏈不連號 0 處。切到「遞增最佳化」：還是 3 層，但葉頁減為 8 個、填充 94%。再把頁容量改成 3：中點對半長到 4 層、15 個葉頁、填充 67%；遞增最佳化只要 3 層、10 個葉頁、填充 100%。
  2. 亂序插入。按「亂序 30 筆」（每頁 4 個、中點對半）：3 層、9 個葉頁、填充 83%，但葉鏈不連號 8 處（L1 → L8 → L4 → L9 → L3 → …）。範圍 20–45 依序讀 L4、L9、L3：邏輯上相鄰，配置上散在各處。
  3. 多讀一頁才知道結束。回到「遞增 1–30」、每頁 4 個、中點對半，範圍 8–15 會讀 L3 → L4 → L5 → L6，共 6 頁（含下探的 2 個內部頁）。L6 [16 17 18] 一個都沒命中：它被讀進來，只是為了確認範圍已經結束。

實驗 2 的填充率反而比實驗 1 的「遞增 + 中點對半」高，這不是巧合。遞增插入時，每次中點分裂留下的左半頁再也不會有新 key 進來，所以永遠半滿；這就是 InnoDB 要偵測循序插入、改在插入點分裂的原因（PostgreSQL 在分裂最右葉頁時，也會依 fillfactor 讓左頁保持接近滿，B-tree 的預設 fillfactor 是 90）。隨機插入的頁長期平均大約七成滿，理論值是 ln 2 ≈ 69%。隨機主鍵真正的代價不在填充率，在後面兩件事：葉鏈在磁碟上不連續，範圍掃描變成跳著讀；插入位置散在整棵樹，每一頁都可能是熱點，快取命中率跟著下降。

刪除為什麼不會讓樹變小

示範用的是最保守的刪除策略：頁要整個刪空才歸還，不做合併或借位。PostgreSQL 的 B-tree 就是這樣：半空的頁不合併，只有完全空掉的頁，才會在 VACUUM 時被回收。InnoDB 比較積極，頁的使用率低於 MERGE_THRESHOLD（預設 50%）時會嘗試與相鄰頁合併。兩者的共同結論是：大量刪除之後，索引不會自動縮小，樹高也很少下降，要靠 PostgreSQL 的 REINDEX 或 InnoDB 的 OPTIMIZE TABLE（重建整張表）才會重新變得緊實。

你可以在「遞增 1–30」之後刪掉 8、10、12、14：葉頁還是 10 個，範圍 8–15 一樣讀 6 頁，命中卻從 8 個掉到 4 個，平均填充降到 65%。另一個值得觀察的細節是：內部頁上的分隔鍵在刪除後可能已經「過期」，它指的那個 key 早就不在了。這是合法的，分隔鍵只負責分流，不代表資料存在。

陷阱InnoDB 用隨機 UUID 當主鍵

InnoDB 的表本身就是主鍵 B+Tree。主鍵用隨機的 UUIDv4 時，每次插入都落在樹中的隨機位置：寫入熱點分散到整棵樹、buffer pool 命中率下降、頁頻繁從中間分裂，而且 16 B 的主鍵會被複製進每一個二級索引。改用遞增整數，或 UUIDv7 這類時間有序的 ID，插入就集中在最右葉頁。PostgreSQL 的 Heap 不依主鍵排序，表本身不受影響，但主鍵那棵 B-tree 一樣要承受隨機插入的分裂與膨脹。

一句話答法葉頁滿了就分裂、分隔鍵往上推，推到根才會長高，所以樹高隨資料量對數成長；遞增插入集中在最右頁，搭配插入點分裂能讓頁幾乎填滿，隨機插入則讓頁散開、葉鏈不連續。刪除通常不會讓樹變矮，要重建索引才會緊實。
05

Clustered 與 Secondary Index：InnoDB 回表 vs PostgreSQL Heap + TID

兩個引擎的索引都叫 B-tree，但 InnoDB 的葉頁直接放整列，PostgreSQL 的葉頁只放「去 Heap 的哪一格拿」。

InnoDB：表就是聚簇索引（Clustered Index）。主鍵 B+Tree 的葉頁直接存整列，所以表的實體順序就是主鍵順序。表沒有宣告主鍵時，InnoDB 拿第一個所有欄位都是 NOT NULL 的 UNIQUE 索引當聚簇鍵；再沒有，就自己產生一個 6 B 的隱藏 row ID。其他索引都是二級索引（Secondary Index），葉頁存「索引欄位 + 主鍵值」。用二級索引找到主鍵之後，再拿主鍵去聚簇索引下探一次取整列，這一步就是回表。

PostgreSQL：表是 Heap。新列寫在哪一頁有空間就放哪裡，不依任何 key 排序。所有索引，包括主鍵，都是 Heap 之外的獨立結構，條目存「索引欄位 + TID」。TID（系統欄位 ctid）是「頁號 + 頁內行指標序號」組成的 6 B 實體位址，拿到它就能直接讀那一頁的那一格，不必再走另一棵樹。

InnoDB 的二級索引記的是「邏輯位址」（主鍵），回表要再走一棵樹；PostgreSQL 記的是「實體位址」（TID），回表只讀一頁，但這個位址會隨每次 UPDATE 換掉。

InnoDB 回表的時序長這樣。重點在「每一筆」：

sequenceDiagram

    participant S as 二級索引
    participant C as 聚簇索引

    C-->>Q: 整列

二級索引那一側是循序讀，聚簇索引那一側是每筆一次的獨立下探；命中的主鍵越分散，回表越接近隨機 I/O。

關鍵為什麼 InnoDB 不讓二級索引存實體位址

聚簇索引的列會因為頁分裂而搬到別頁。如果二級索引存的是實體位址，每次分裂都要回頭改所有二級索引裡指向被搬走的那幾列的條目。存主鍵值就不怕搬家，代價是每次回表都多走一棵樹。PostgreSQL 反過來：Heap 裡的 tuple 不會因為別人插入而搬家，所以敢存 TID；代價是 UPDATE 寫出的新版本換了位址，索引得跟著補條目。第 10 節的 HOT 更新，就是為了減少這件事。

一句話答法InnoDB 的表就是主鍵 B+Tree，二級索引存主鍵，回表等於再查一次聚簇索引；PostgreSQL 的表是無序的 Heap，所有索引都存 TID，回表只讀一頁，但 UPDATE 換了 TID 就可能要更新所有索引。
06

複合索引：最左前綴與欄位順序

(a, b) 索引就是一份「先依 a 排，a 相同再依 b 排」的清單。最左前綴不是規則，是這個排序的直接推論。

複合索引 (user_id, created_at) 的葉頁條目，等於把資料先依 user_id 排序、user_id 相同時再依 created_at 排序；InnoDB 最後還會以主鍵收尾。下面這張排序表就是所有規則的來源：

條件 A 命中第 4–6 列，是連續的一段：定位一次、往後讀到不符合為止。條件 B 命中第 5 列與第 8 列，中間夾著不相干的條目；沒有 user_id 當前綴，created_at 在整份清單裡是亂的，只能整份掃過。

把這個觀察推廣到 (a, b, c)：

WHERE 的形狀，索引 (a, b, c)能用來定位的欄位原因
a = ?a最左前綴
a = ? AND b = ?a, b連續的等值前綴
a = ? AND b = ? AND c > ?a, b, c等值都在前，最後一欄可以是範圍
a = ? AND c = ?a跳過 b，c 只能在索引條目上逐筆過濾
a > ? AND b = ?aa 一旦是範圍，b 在這段範圍裡不再有序
b = ? AND c = ?無缺最左欄，定位不到起點（Skip Scan 例外，見下方）
b = ? AND a = ?a, bWHERE 的書寫順序無關，優化器會自己對應到索引欄位
a = ? ORDER BY ba 定位，b 免排序同一個 a 底下 b 已經有序，可以直接依索引順序輸出

能用來定位的，是從最左欄開始連續的等值欄，再加最多一個範圍欄。其餘條件仍可以在索引條目上過濾，但已經無法縮小要掃的範圍。

關鍵「不能定位」不等於「完全沒用」

MySQL 5.6 起的 Index Condition Pushdown（EXPLAIN 顯示 Using index condition）會在回表之前，先用索引條目上其他欄位的條件過濾。PostgreSQL 的 B-tree 掃描也會把非前綴欄位的條件放在索引內檢查。兩者省下的是回表次數，不是掃描的條目數；第 8 節的 demo 會把這兩個數字分開算。

欄位順序怎麼排
  1. 等值條件的欄位放前面，範圍或排序欄位放後面。(user_id, created_at) 同時服務「某人最近 30 天的訂單」與「某人的訂單依時間排序」兩種查詢。
  2. 一個索引盡量服務多條查詢。有了 (a, b)，單獨的 (a) 就是冗餘的，因為 (a, b) 的最左前綴已經涵蓋它。
  3. 「選擇性高的欄位放前面」只是次要準則。決定順序的是查詢形狀。如果每條查詢都帶 status = ?、只對 created_at 做範圍，(status, created_at) 就比 (created_at, status) 好，即使 status 只有四種值。
陷阱Skip Scan 不是可以忽略欄位順序的理由

MySQL 8.0.13 起有 Skip Scan：最左欄的相異值很少時，優化器可以把 b = ? 拆成「對 a 的每一個值各定位一次」。PostgreSQL 18 的 B-tree 也加入了類似的能力。它能在特定情況下救回缺最左欄的查詢，但成本隨最左欄的相異值數量線性增加。拿它當「欄位順序不重要」的理由，是在賭優化器。

一句話答法(a, b) 是先依 a 再依 b 的排序，所以只有從 a 開始、連續的等值欄加最後一個範圍欄能定位；欄位順序依查詢形狀決定，等值在前、範圍與排序在後，選擇性只是次要考量。
07

Covering Index 與選擇性

不回表的查詢最快；回表多到一定程度，優化器寧可全表掃描。

Covering Index（覆蓋索引）：查詢用到的每一個欄位，包括 SELECT、WHERE、ORDER BY 裡的，都能從索引條目拿到，就不必回表。

  • InnoDB：二級索引條目自帶主鍵，所以 (user_id, created_at) 已經覆蓋 SELECT id, user_id, created_at，EXPLAIN 的 Extra 會出現 Using index。MySQL 沒有 INCLUDE 語法，要覆蓋其他欄位只能把它們加進索引的 key。
  • PostgreSQL：索引條目只有 key 與 TID，id 不會自動在裡面。PostgreSQL 11 起可以寫 CREATE INDEX ... ON orders (user_id, created_at) INCLUDE (id, amount)，把不參與排序、只用來回答查詢的欄位放進葉頁條目。執行計畫會顯示 Index Only Scan。
陷阱覆蓋了，也可能還是要回表

PostgreSQL 的索引沒有可見性資訊。Index Only Scan 對每一筆條目先查 Visibility Map：對應的 Heap 頁被標成 all-visible，才能直接信任索引裡的值，否則照樣去 Heap 確認（EXPLAIN ANALYZE 的 Heap Fetches 就是這個次數）。剛大量寫入、VACUUM 還沒跑過的表，Index Only Scan 可能退化得跟一般 Index Scan 差不多。InnoDB 也有對應的邊界：二級索引條目不帶交易資訊，若條目被標記刪除，或該頁最近被比你的讀取視圖更新的交易改過，就得回聚簇索引確認正確版本，這時覆蓋索引的優勢就用不上。

選擇性：為什麼優化器有時寧可全表掃描

選擇性（selectivity）是條件命中的列數佔全表的比例，常用欄位的相異值數量（cardinality）來近似。它決定的是第三個問題的成本：命中越多列，回表次數越多。

回表是隨機讀；全表掃描是循序讀，一次讀一整頁，每頁裡的每一列都用得上。所以存在一個交叉點：命中比例超過某個值之後，「走索引加大量回表」反而比「直接掃全表」慢，優化器就會放棄索引。這個交叉點沒有固定百分比，取決於列寬、命中的列是否集中在少數頁、快取命中率，以及統計資訊準不準。常聽到的「超過 20% 就不走索引」只是經驗值。

典型例子是 gender、status、is_deleted 這類低基數欄位的單欄索引：WHERE status = 'paid' 若命中六成的列，索引幾乎不會被選。這類欄位不是沒用，而是適合放進複合索引當等值前綴；在 PostgreSQL 還可以改成部分索引（Partial Index），例如只索引 WHERE status = 'pending' 的那一小撮。MySQL 沒有部分索引。

邊界成本怎麼估，會在談查詢計畫的主題處理

優化器怎麼估命中列數（統計資訊、直方圖），PostgreSQL 的 Bitmap Heap Scan 怎麼把散落的 TID 先依頁號排序再讀，都屬於執行計畫的範圍。這裡只建立「選擇性 × 回表成本」的直覺。

一句話答法Covering Index 讓查詢只讀索引不回表：InnoDB 的二級索引天生帶主鍵，PostgreSQL 要靠 INCLUDE，而且還要 Visibility Map 配合。選擇性低時回表次數爆量，全表循序掃描反而便宜，所以優化器會放棄索引。

索引失效的常見情境

  

  
索引存在不代表用得上：只要查詢比較的不是欄位的原始值，索引的排序就幫不上忙。


  
所有「失效」情境有同一個原理：B+Tree 的排序建立在欄位的原始值上。條件一旦比較的是欄位經過運算之後的結果，那個結果在索引裡沒有順序，就無法定位起點。


  

    

      
        
情境範例為什麼用不上修法

      
      
        

          函式或運算包住欄位
          WHERE DATE(created_at) = '2026-11-10'
WHERE amount * 1.05 > 100		
          索引依 created_at 排序，不依 DATE(created_at) 排序
          改寫成欄位上的範圍：created_at >= '2026-11-10' AND created_at < '2026-11-11'；或建表達式索引（PostgreSQL 的 expression index、MySQL 8.0.13 起的 functional key part）
        

        

          隱式轉型（MySQL）
          phone 是 VARCHAR：WHERE phone = 13800000000
          字串欄位與數字比較時，MySQL 把兩邊都轉成數值再比，等於對每一列的欄位套函式
          常數加引號、型別一致。反方向（INT 欄位比字串常數）轉的是常數，索引仍可用
        

        

          隱式轉型（PostgreSQL）
          bigint 欄位與 numeric 參數比較
          PostgreSQL 型別較嚴，字串欄位直接比整數會報錯而不是偷偷轉；但 bigint 與 numeric 比較時，欄位會被提升成 numeric，bigint 上的索引用不到
          讓參數型別與欄位一致，特別注意 ORM 與 driver 綁定的型別
        

        

          字元集或定序不一致
          JOIN 的兩個欄位一個 utf8mb3、一個 utf8mb4
          比較前得轉換其中一邊；被轉的若是有索引的那一邊，就用不上
          統一字元集與定序
        

        

          前置萬用字元
          WHERE name LIKE '%son'
          字串索引依前綴排序，'%son' 沒有固定前綴
          'abc%' 可以走範圍；「包含」搜尋改用全文索引或 PostgreSQL 的 pg_trgm GIN 索引；「結尾」搜尋可以多存一個反轉字串欄位再建索引
        

        

          缺最左欄
          索引 (user_id, created_at)，WHERE created_at > ?
          見第 6 節的排序表
          依查詢形狀調整欄位順序，或另建索引
        

        

          選擇性太低
          WHERE status = 'paid'（命中六成）
          不是用不上，是優化器判斷全表掃描比較便宜
          改用複合索引或部分索引，或接受全表掃描
        

      
    

  

  
前五列是「結構上用不上」：查詢比較的值在索引裡沒有順序。最後一列是「優化器選擇不用」：索引可以用，只是不划算。


  

    
陷阱PostgreSQL 的 LIKE 'abc%' 也不一定走索引

    
資料庫的定序（collation）不是 C 時，一般的 B-tree 索引不能拿來做 LIKE 前綴比對，因為語系定序的排序規則不等於逐位元組比較。要建索引時指定 text_pattern_ops（或 varchar_pattern_ops），或讓欄位使用 C 定序。全文與模糊搜尋的完整做法，見搜尋與分析引擎篇的倒排索引。

  


  

    
關鍵這些常被誤列為「索引失效」

    
!=、NOT IN、IS NULL、OR。它們不是結構上用不到索引：MySQL 可以把 IS NULL 當等值查詢，跨欄位的 OR 可以用 index merge 合併；PostgreSQL 用 BitmapOr；!= 也能拆成兩段範圍。它們常常不走索引，是因為命中太多列，或計畫成本不划算，而不是排序被破壞。面試時把「結構上用不上」和「優化器選擇不用」分開講，是加分的地方。

  


  

    一句話答法索引依欄位原始值排序，所以函式包欄位、隱式轉型、前置萬用字元與缺最左欄都會讓查詢定位不到起點；選擇性低則是另一回事，索引可用，只是優化器判斷全表掃描更便宜。
  






  

    10
    
索引的寫入成本

  

  
每多一個索引，就多一棵每次寫入都要維護的樹。


  
讀取變快的代價在寫入端。兩個引擎在不同操作上的成本分布如下：

  

    

      
        
操作InnoDBPostgreSQL

      
      
        
INSERT聚簇索引插一列，每個二級索引各插一筆條目Heap 插一個 tuple，每個索引各插一筆條目

        
UPDATE 非索引欄位改聚簇索引裡的那一列（舊版本進 undo log），二級索引不動寫一個新版本 tuple。若沒改到任何索引欄位、而且同一頁放得下，走 HOT（Heap-Only Tuple），索引不動；否則每個索引都要插新條目

        
UPDATE 索引欄位該二級索引：舊條目標記刪除、插入新條目新 tuple，而且所有索引都插新條目（HOT 不適用）

        
UPDATE 主鍵等於刪除再插入整列，所有二級索引都要更新與更新其他索引欄位相同

        
DELETE標記刪除，背景 purge 再清掉聚簇與二級索引的條目標記 tuple 失效，VACUUM 再清掉 Heap 與各索引的條目

      
    

  

  
InnoDB 把成本押在「二級索引存主鍵」：列搬家不必改索引。PostgreSQL 押在「Heap 不搬家」：但每個新版本都可能讓所有索引各多一筆，HOT 是它的減壓閥。


  
除了每次寫入要多改幾棵樹，還有幾項容易被忽略的成本：

  
    
    
  • 頁分裂與空間：插入位置隨機時頁頻繁分裂、填充率下降，索引總大小超過資料本身並不少見。
    • 
    
  • 記憶體：每個索引都要搶 buffer pool 或 shared buffers；熱索引放不進記憶體時，寫入就變成隨機 I/O。
    • 
    
  • 唯一性檢查：UNIQUE 索引在插入前必須讀到對應的葉頁，確認沒有重複，這一步無法延後。
    • 
    
  • 日誌量：每個索引頁的修改都要寫 redo log 或 WAL，複製到備援節點的量也跟著放大。
    • 
    
  • 建索引本身：大表加索引要用 PostgreSQL 的 CREATE INDEX CONCURRENTLY，或 MySQL 的 Online DDL，避免長時間擋住寫入。
    • 
  


  

    
實務找出沒在用、或重複的索引

    
PostgreSQL 看 pg_stat_user_indexes 裡 idx_scan 長期為 0 的索引。MySQL 可以查 sys.schema_unused_indexes 與 sys.schema_redundant_indexes（例如已經有 (a, b)，又另外建了 (a)）。MySQL 8.0 還能先把索引設成 INVISIBLE，觀察一段時間再刪。注意這些統計是從上次重置或重啟後才開始累計；只看主庫，也會漏掉只在副本上跑的查詢。

  


  

    
邊界索引與鎖、索引與 LSM

    
InnoDB 的 Row Lock 實際上加在索引記錄上，沒有走到合適索引的 UPDATE，鎖住的範圍可能遠超過預期；這件事在談資料庫鎖與死鎖的主題處理。LSM-Tree 怎麼用寫入放大換取寫入吞吐，見嵌入式資料庫篇。

  


  

    一句話答法每個索引都是一棵寫入時要同步維護的樹，會帶來額外的頁分裂、redo/WAL、記憶體佔用與唯一性檢查；InnoDB 更新非索引欄位不碰二級索引，PostgreSQL 靠 HOT 避免改索引。沒在用的索引要定期清掉。

面試答題框架

  

  
先用三個問題定位，再談兩種引擎的差異與取捨。


  

    

      
        
常見問題答題骨架

      
      
        
為什麼用 B+Tree，不用 Hash 或二元樹磁碟以頁為單位；B+Tree 內部頁只放分隔鍵，fanout 幾百、樹只有 3 到 4 層；葉頁串成鏈，支援範圍與排序。Hash 不保序，二元樹太高。

        
這條 SQL 為什麼沒走索引依序檢查：定位得到嗎（最左前綴、函式、轉型、前置萬用字元）→ 命中多少（選擇性）→ 要不要回表（覆蓋）。最後才懷疑統計資訊過期。

        
1 億筆的表，樹有幾層先寫假設：16 KiB 頁、8 B 主鍵、fanout 約 880、列寬 200 B 時每葉 75 列，3 層約 5,800 萬，所以是 4 層。上層常駐記憶體，一次查詢大約一次實體 I/O。

        
InnoDB 為什麼建議遞增主鍵表就是主鍵 B+Tree。遞增讓插入集中在最右葉頁、頁能填滿；隨機讓分裂分散、葉鏈不連續、快取命中下降。主鍵還會被複製進每個二級索引，越窄越好。

        
什麼是回表，怎麼避免二級索引只有索引欄位加主鍵（InnoDB）或 TID（PostgreSQL），要其他欄位就得回表。用覆蓋索引避免：InnoDB 把欄位加進索引，PostgreSQL 用 INCLUDE，並留意 Visibility Map。

        
(a, b) 還是 (b, a)看查詢形狀：等值欄在前，範圍與排序欄在後；一個索引盡量服務多條查詢。選擇性只是次要考量。

        
索引是不是越多越好每個索引都是寫入時要維護的樹：多一份頁分裂、redo/WAL、記憶體與唯一性檢查。依查詢建索引，定期清掉沒在用與冗餘的。

        
Index Only Scan 為什麼還有 Heap FetchesPostgreSQL 的索引沒有可見性資訊，Heap 頁沒被標成 all-visible 時，仍要讀 Heap 確認。VACUUM 之後會改善。

      
    

  

  
每一題都可以回到同一個起點：索引是一份排序過的副本，查詢能不能利用它的排序、要讀多少頁、讀到的夠不夠用。


  

    
失分點三種常見的扣分答法

    
只背「最左前綴」口訣，卻說不出它來自排序；把所有「沒走索引」都叫「索引失效」，分不出結構問題與成本問題；估樹高不給頁大小、key 大小與列寬的假設，只丟一個「三層」。

  


  

    一句話答法索引是依欄位排序的 B+Tree，3 到 4 層撐起上億列；查詢要用上它，得能從最左欄定位、掃描範圍夠窄，最好再加上覆蓋避免回表。InnoDB 回表走主鍵，PostgreSQL 回表走 TID，而每個索引都會讓寫入變重。
