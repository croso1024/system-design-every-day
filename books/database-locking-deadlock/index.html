資料庫鎖與死鎖 (Row Lock / Gap Lock / Deadlock)

當多筆交易同時修改同一批資料，MVCC 的歷史快照已不足以保護寫入正確性——此時誰能前進、誰必須排隊、誰又會因為互相等待而被資料庫強制回滾，全看鎖管理器在索引與區間上掛了什麼鎖。

01

並發寫入時，資料庫到底鎖住了什麼？

從快照讀與當前讀的分界出發，看懂 S／X 鎖與階層式 Intention Lock 如何分工。

在現代關聯式資料庫（如 PostgreSQL 與 MySQL InnoDB）中，單純的 SELECT 預設走 MVCC 歷史版本鏈的快照讀（Snapshot Read），讀寫互不阻塞（版本鏈與 Read View 機制詳見「交易隔離級別與 MVCC」篇）。然而一旦進入寫入與當前讀（Current Read）——包括 INSERT、UPDATE、DELETE，以及顯式加鎖的 SELECT ... FOR SHARE 與 SELECT ... FOR UPDATE——資料庫就必須讀取最新已提交的版本並掛上鎖（Lock），否則兩筆交易同時基於同一個舊值改寫，就會直接覆蓋彼此的成果。

邊界單機資料庫鎖 vs 分散式鎖

本篇聚焦於單一資料庫執行個體內部由鎖管理器（Lock Manager）維護的並行控制；B+Tree 頁結構與叢集索引原理見「資料庫索引原理」篇，而跨微服務、跨儲存系統的租約與 Fencing Token 則由「協調服務」篇探討。

基本讀寫模式：Shared Lock (S) 與 Exclusive Lock (X)

鎖管理器在列級（Row-level）最核心的兩種基礎模式，決定了並發交易能否同時接觸同一份目標資料：

  • Shared Lock（S 鎖，共享鎖／讀鎖）：允許持有者讀取最新紀錄。多筆交易可同時持有同一筆紀錄的 S 鎖，但只要有任何一筆交易握著 S 鎖，其他請求 X 鎖的交易就必須排隊等待。典型觸發語法為 SELECT ... FOR SHARE，或外鍵約束檢查父表紀錄是否存在時自動加上的隱式共享鎖。
  • Exclusive Lock（X 鎖，排他鎖／寫鎖）：允許持有者修改或刪除紀錄。與任何其他的 S 鎖或 X 鎖皆互斥——同一時刻最多只有一筆交易能握住該紀錄的 X 鎖。所有 UPDATE、DELETE 與 SELECT ... FOR UPDATE 都會請求 X 鎖。

為什麼還需要 Intention Lock（意向鎖 IS / IX）？

假設一張訂單表有五千萬列，交易 T1 鎖住了其中第 38291 列的 X 鎖。此時運維執行需要全表鎖的操作（例如某些表級維護指令或顯式 LOCK TABLES ... WRITE），資料庫要怎麼知道「這張表裡有沒有任何一列正被別人鎖著」？如果逐列掃描五千萬筆紀錄去檢查列鎖，表鎖判定的複雜度會退化成 O(N)。

意向鎖（Intention Lock）正是為了把這個檢查降為 O(1) 而設計的表級旗標（Table-level Lock）。協定規定：任何交易在對底下某一列申請 S 鎖之前，必須先在資料表層掛上 Intention Shared（IS）；申請某列的 X 鎖之前，必須先在表層掛上 Intention Exclusive（IX）：

Layer 1 · Table Level 表級鎖與意向鎖（S / X / IS / IX）

交易碰觸任何索引列之前，先在表物件插旗「我正準備鎖底下的某些列」。需要全表鎖的操作只需檢查這一層即可 O(1) 判定衝突。

Layer 2 · Index Record & Gap Level 列級與區間鎖（Record S/X · Gap · Next-Key · Insert Intention）

真正決定並發寫入吞吐的戰場：兩筆交易都在表層掛了 IX（彼此相容），接著各自下探到索引樹鎖定目標紀錄或縫隙；只要鎖的不是同一筆索引項或衝突區間，就能完全平行寫入。

階層加鎖結構：表級意向鎖只是「樓層入口登記」，並不會阻擋其他交易進入同一張表鎖不同列。

面試最容易答錯的細節是：IX 與 IX 之間是完全相容的！意向鎖只跟「全表級的 S / X 鎖」互斥，絕不會阻擋另一筆也要改其他列的交易：

請求鎖 ＼ 已持有鎖 IS（意向共享） IX（意向排他） S（表級共享） X（表級排他）
IS（準備讀某列） 相容（通過） 相容（通過） 相容（全表唯讀可共存） 衝突（阻塞等待）

表級鎖相容性矩陣：注意左上角 2×2 全為相容——IS 與 IX 彼此從不互擋，真正的列衝突留到索引層才判定。

一句話答法快照讀靠 MVCC 免鎖讀取，寫入與當前讀靠 S／X 鎖序列化衝突；表級 Intention Lock（IS／IX）則是讓全表鎖能在 O(1) 時間內察覺底下列鎖存在的階層預告機制，IX 與 IX 彼此相容。
02

為什麼說「鎖是掛在索引上，而不是資料列上」？

拆解主鍵、二級索引回表與無索引全表掃描三條加鎖路徑，看清「行鎖變表鎖」的根因。

許多工程師第一次遇到「明明 WHERE 只命中 1 列，為什麼另外 10 萬列的 UPDATE 全部卡死」時，才驚覺一個核心事實：在 InnoDB 裡，Row Lock 並不是鎖在抽象的「邏輯資料列」上，而是掛在執行計畫實際走過的「索引紀錄（Index Record）」上。

在底層實作中，InnoDB 的記憶體鎖表以 (space_id, page_no) 為雜湊鍵，為該資料頁維護一張位元圖（Bitmap），每個位元對應頁內一筆索引紀錄的序號 heap_no。這意味著查詢最佳化器（Query Planner）選了哪一條索引、掃過多少筆索引項，就決定了鎖管理器在哪些 heap_no 上打勾：

  • 路徑一：命中主鍵（Clustered Index）——例如 UPDATE users SET balance = 50 WHERE id = 42，直接定位主鍵樹上的 id = 42 紀錄並掛上一把 X 鎖，鎖定範圍最精準。
  • 路徑二：命中二級索引（Secondary Index）——例如 UPDATE orders SET state = 'PAID' WHERE order_no = 'ORD-9'。InnoDB 會先在二級索引 idx_order_no 的紀錄掛上 X 鎖，取出主鍵值後，再回到主鍵樹（Clustered Index）對該筆主鍵紀錄也掛上 X 鎖。如果只鎖二級索引而不鎖主鍵，另一條直接 WHERE id = 108 走主鍵的 UPDATE 就會繞過鎖保護直接改壞同一列！
  • 路徑三：無索引或索引失效（退化為 Clustered Index 全掃描）——當條件欄位沒建索引、發生隱式型別轉換，或統計資訊判定全表掃描更快時，儲存引擎不知道哪一頁才有符合條件的資料，只能從主鍵樹第一筆一路掃到最後一筆。掃描過程中每一筆被檢查過的索引紀錄與縫隙都會被上鎖，表面寫的是單列 UPDATE，實際效果卻等同鎖死整張表。

二級索引寫入的兩段式加鎖：先鎖二級索引再回表鎖主鍵；若另一筆交易從主鍵改同列並連帶更新該二級索引，加鎖方向相反便可能形成死鎖。

陷阱最隱蔽的「行鎖變表鎖」：隱式型別轉換與函式包欄位

若 phone 欄位型別是 VARCHAR(20) 且建有唯一索引，但程式寫成 UPDATE accounts SET vip = 1 WHERE phone = 0912345678（傳入整數而非字串），MySQL 會將整張表的字串轉成數字比對，導致索引無法做區間定位而觸發全表掃描——瞬間把整張 accounts 表的既有列與縫隙全部鎖死。所有帶鎖的 UPDATE／DELETE／FOR UPDATE 上線前，務必確認執行計畫真的走了預期索引。

延伸對照：InnoDB 記憶體鎖位元圖 vs PostgreSQL Tuple Header 標記

面試常追問：「如果一筆交易一次 UPDATE 一百萬列，鎖表會不會把記憶體撐爆？」兩大主流引擎給出了截然不同的架構折衷：

  • InnoDB 在記憶體鎖雜湊表為每個被鎖頁面配置鎖結構（同一頁內共用一張 Bitmap，每頁約數百 bytes），雖然比每列獨立配置物件省得多，但超大量鎖仍會消耗 Buffer Pool／Lock System 記憶體並提高鎖表檢索成本。
  • PostgreSQL 則把列級排他鎖直接記在資料頁 Heap Tuple Header 的 xmax 與 t_infomask 旗標位元裡（共享列鎖多交易共存時升級為 MultiXactId），不在共享記憶體為每一列建立鎖物件。代價是檢查鎖狀態可能觸發頁面讀取與髒頁寫回，且 PostgreSQL 不實作 InnoDB 式的索引 Gap Lock（其 SERIALIZABLE 改採無阻塞的 SSI 謂詞鎖偵測，詳見「交易隔離級別與 MVCC」篇）。
一句話答法InnoDB 的列鎖本質是掛在索引紀錄上：走主鍵鎖 1 處、走二級索引會先鎖二級索引再回表鎖主鍵，而一旦沒走上索引退化成全表掃描，就會沿路鎖住主鍵樹上所有掃過的紀錄與區間。
03

Record、Gap 與 Next-Key Lock：封住幻讀的區間幾何

鎖定既有紀錄只是基本功；鎖住兩個索引值之間的「縫隙」，才能阻止幻影列插進來。

如果鎖管理器只能鎖住「已經存在的紀錄（Record Lock）」，那麼當交易 T1 執行 SELECT * FROM bookings WHERE slot_id BETWEEN 10 AND 30 FOR UPDATE 時，它只能鎖住目前落在 10 到 30 之間的既有列；另一筆交易 T2 隨即執行 INSERT INTO bookings (slot_id) VALUES (25) 仍會暢行無阻——T1 再讀一次就會多出一筆「幻影列（Phantom Row）」，預約名額檢查當場破功。

為了在 REPEATABLE READ 隔離級別下徹底擋住當前讀的幻讀，InnoDB 把索引軸切分成「點（既有索引項）」與「開區間（相鄰索引項之間的縫隙）」，組合出四種精密的鎖原語：

  • Record Lock（紀錄鎖）：單純鎖定某一筆既有索引項本身（例如 slot_id = 20），阻止其他交易修改或刪除該筆紀錄，但不阻擋往它左右兩側插入新值。
  • Gap Lock（間隙鎖）：只鎖定兩筆索引紀錄之間的開區間縫隙（例如 (10, 20)，或是最大紀錄之後直到虛擬上界 +supremum 的 (40, +∞)）。Gap Lock 的唯一職責是禁止其他交易往這段縫隙插入新紀錄；因此Gap S 與 Gap X 彼此完全相容——兩筆交易可以同時握住同一個 (10, 20) 的 Gap Lock 而不互擋！
  • Next-Key Lock（臨鍵鎖）：Gap Lock + Record Lock 合體而成的左開右閉區間 (prev_key, key]（例如 (10, 20]）。這是 InnoDB 在 REPEATABLE READ 下掃描索引時的預設基本單位。
  • Insert Intention Lock（插入意向鎖）：INSERT 寫入新列前，會先檢查目標落點所在的縫隙是否已被別人掛上 Gap Lock；若有則阻塞等待並掛上 Insert Intention Lock。多筆交易同時往同一個未被鎖住的縫隙插入不同鍵值時，Insert Intention Lock 之間互不相撞。

04

SELECT FOR UPDATE、NOWAIT 與 SKIP LOCKED 實戰

顯式當前讀如何消滅遺失更新，以及如何用 SKIP LOCKED 把資料表變成高吞吐工作佇列。

在預設的快照讀下，如果應用程式寫出「先 SELECT balance 讀進記憶體計算、再 UPDATE accounts SET balance = :new_val 寫回」的讀改寫（Read-Modify-Write）邏輯，兩筆並發交易會同時讀到舊餘額 100、各自扣 30 後寫回 70——其中一筆扣款無聲無息蒸發，形成典型的 Lost Update（遺失更新）。

當業務規則複雜到無法塞進單條原子 UPDATE 時，就必須在讀取當下直接把快照讀升級為顯式加鎖的當前讀：

  • SELECT ... FOR SHARE：讀取最新已提交版本並掛上 S 鎖。適合「交易期間這筆父設定（例如匯率檔、商戶啟用狀態）不准被別人改掉或刪掉，但允許其他讀取者一起參考」的情境。
  • SELECT ... FOR UPDATE：讀取最新已提交版本並直接掛上 X 鎖，把後續要修改的資料列先行獨佔，直到本筆交易 COMMIT 或 ROLLBACK 才釋放。

搶不到鎖時的三種尾綴策略：預設等待、NOWAIT、SKIP LOCKED

自 MySQL 8.0 與 PostgreSQL 9.5 起，標準 SQL 為 FOR UPDATE 提供了兩種非阻塞修飾詞，徹底改變了高併發系統保護連線池與排程任務的寫法：

  • 預設（不加尾綴）：進入鎖等待佇列阻塞，直到前手放鎖或觸發 innodb_lock_wait_timeout（預設 50 秒）／PostgreSQL lock_timeout。高流量熱點下，數百條執行緒卡死等待同一列，會在幾秒內把資料庫連線池耗盡。
  • FOR UPDATE NOWAIT：一旦目標列已被鎖住，0 毫秒立即拋錯返回，絕不排隊阻塞。適合秒殺搶購、座位鎖定等需要「搶不到就立刻回傳忙碌或已售出」的快速失敗（Fail-fast）API。
  • FOR UPDATE SKIP LOCKED：掃描過程中遇到已被其他活躍交易鎖住的列時，不等待也不報錯，直接跳過它，繼續往後找第一筆目前沒被鎖住的列上鎖返回。

經典架構模式：用資料表實作工作佇列（DB-backed Job Queue）

在中小型系統或需要與業務資料同庫強一致寫入（Transactional Outbox / 本地佇列）的場景，工程團隊常直接拿關聯式資料表當工作佇列。若沒有 SKIP LOCKED，10 台 Worker 同時執行 ORDER BY id LIMIT 1 FOR UPDATE 都會卡在佇列頭同一筆 id = 101 上排隊，並發度退化為 1；加上 SKIP LOCKED 後，多台 Worker 便能無鎖爭用地平行領取不同任務：

SKIP LOCKED 佇列標準時序：注意 t3 先 COMMIT 放鎖才去跑外部 I/O，避免長交易把連線與 Undo History 拖垮。

鐵律絕不可抱著 FOR UPDATE 鎖去打外部 API

SKIP LOCKED 只負責「領取任務的那 1 毫秒」不互卡。如果你把呼叫第三方金流、寄信或推論服務包在同一筆 BEGIN ... COMMIT 內，交易拉長到數秒，不僅佔死資料庫連線，還會阻止 MVCC 清理舊版本（Vacuum / Purge 停滯）；此外 SKIP LOCKED 回傳的是不完整視圖，只適合「隨便領一筆待辦任務即可」的佇列，不可用於報表加總或餘額核對。

一句話答法SELECT FOR UPDATE 把讀改寫收進排他鎖保護，搭配 NOWAIT 可保護連線池快速失敗，搭配 SKIP LOCKED 則能讓多個 Worker 無阻塞平行領取不同待辦列，是實作交易型工作佇列與 Outbox 輪詢的標準原語。
05

悲觀鎖與樂觀鎖的工程取捨

原地原子更新、FOR UPDATE 預先佔鎖、Version CAS 提交檢驗——三種防寫入衝突手段的邊界。

在系統設計面試被問到「扣庫存或搶票該用悲觀鎖還是樂觀鎖」時，千萬別急著二選一——實務上防範寫入衝突共有三層武器，工程選型的關鍵在於「鎖被握住多久」以及「同一列同時有多少人在搶」。

第一優先：單句原子條件更新（Atomic Conditional UPDATE）

只要不變量（Invariant）能寫進單條 SQL 的 SET 與 WHERE，就不需要把值讀回應用程式再寫回：

UPDATE inventory
SET stock = stock - :qty
WHERE sku_id = 42 AND stock >= :qty;
-- 檢查 affected_rows：1 代表扣減成功；0 代表庫存不足，直接回傳售罄

這條語句在資料庫內部依然會對 sku_id = 42 掛上 X Record Lock（本質仍是資料庫層的排他鎖），但若在單語句自動提交或交易最後一步執行，鎖持有時間 Thold 只包含引擎內部毫秒甚至百微秒級的記憶體改寫與 WAL 落盤，完全省去了應用程式與資料庫之間的網路往返（RTT）。單一熱點列的理論吞吐上限直接受限於鎖持有時間的倒數：

TPSmax (single hot row) = 1 / Thold

把 Thold 從跨兩次網路 RTT 的 5 ms 壓縮到單句執行的 0.25 ms，單列串行吞吐上限立刻從 200 TPS 跳升至 4,000 TPS。

當單條 SQL 寫不完：悲觀鎖 vs 樂觀鎖（Version CAS）

當業務必須跨多張表讀取、套用複雜計價規則後才能決定新值，就必須在「先鎖再算（悲觀鎖）」與「先算最後驗版本（樂觀鎖）」之間抉擇：

  • 悲觀鎖（Pessimistic Locking）：假設衝突大概率會發生，交易一開始就以 SELECT ... FOR UPDATE 取得排他鎖，算完再 UPDATE 提交。優點是搶到鎖就保證能一次成功提交，沒有白做工的重試風暴；缺點是持鎖時間橫跨應用層運算與多次網路 RTT，高併發下排隊嚴重且容易因多列加鎖順序不一致而死鎖。
  • 樂觀鎖（Optimistic Concurrency Control，OCC）：假設衝突罕見，讀取時走普通無鎖快照讀，一併讀出單調遞增的 version 欄位；提交時才以 Compare-And-Swap（CAS）語意驗證版本未被他人改動：
-- 1. 無鎖讀取（甚至可跨前端頁面停留數分鐘）
SELECT price, content, version FROM articles WHERE id = 9;   -- 讀到 version = 7

-- 2. 提交時檢驗版本號並原子 +1
UPDATE articles
SET price = :new_price, content = :new_content, version = version + 1
WHERE id = 9 AND version = 7;
-- affected_rows = 1 → 成功；affected_rows = 0 → 版本已變，重讀重算或提示使用者合併
關鍵為什麼樂觀鎖一定要用單調遞增 version，不能直接比對舊欄位值？

若條件寫成 WHERE id = 9 AND balance = 100，當餘額在期間經歷 100 → 20 → 100（且同時變更了信用額度或凍結狀態），比對舊值會誤判「沒人動過」而放行，這就是經典的 ABA 問題。只增不減的整數 version（或高精確度狀態序號）才能嚴格捕捉任何中間改動。

評估維度 單句原子條件 UPDATE 悲觀鎖 SELECT FOR UPDATE 樂觀鎖 version CAS
鎖持有時間 Thold 極短（單次引擎內執行 ＋ COMMIT） 長（涵蓋多次 App ↔ DB RTT 與運算） 極短（僅最後 UPDATE 瞬間掛鎖）

寫入並行控制選型表：讀多寫少或跨請求選樂觀鎖；高爭用單列計數優先壓成單句原子 UPDATE；複雜多表強一致且重試昂貴才開悲觀鎖。

一句話答法能壓進單條條件 UPDATE 就別分兩步讀寫；讀多寫少或需跨人類操作時間用 version 樂觀鎖省下持鎖開銷，高衝突且重試代價昂貴的多步交易則用悲觀鎖排隊保吞吐。
06

死鎖成因、Wait-for Graph 偵測與犧牲者選擇

循環等待如何成形、資料庫如何在毫秒內抓環，以及為什麼回滾的總是「改最少」的那筆交易。

單純的「鎖等待（Lock Wait）」只要前手提交就會自然解開；死鎖（Deadlock）則是兩筆以上的交易彼此握著對方下一步需要的鎖，形成有向循環等待（Circular Wait）——如果沒有外力介入，環上的每一筆交易都會永遠等下去。

線上最高頻的三種死鎖原型

  1. 多資源逆序加鎖（AB-BA 交錯）：T1 先鎖帳戶 A 再鎖帳戶 B，同一毫秒 T2 先鎖帳戶 B 再鎖帳戶 A。這不只發生在兩條獨立 UPDATE，連單條批次 UPDATE items SET ... WHERE id IN (9, 2) 與 WHERE id IN (2, 9) 若執行計畫依輸入順序逐筆加鎖，也會直接互卡。
  2. 同列鎖升級與 Gap 相容陷阱（最反直覺！）：兩筆交易先在同一列取得相容的 S 鎖，隨後雙雙執行 UPDATE 請求升級為 X 鎖——T1 等 T2 放掉 S 鎖，T2 也等 T1 放掉 S 鎖，單一列上直接死鎖！同理，第 3 節提過兩把 Gap Lock 彼此相容，因此兩筆交易同時執行「先 SELECT ... FOR UPDATE 查某唯一鍵不存在（雙雙拿到同一段 Gap Lock），接著各自 INSERT（雙雙請求 Insert Intention Lock）」時，也會在同一段縫隙上瞬間死鎖：
sequenceDiagram
    participant T1 as 交易 T1
    participant DB as InnoDB 鎖管理器
    participant T2 as 交易 T2
    T1->>DB: SELECT id=25 FOR UPDATE
    DB-->>T1: 核發 Gap Lock (20,30)
    T2->>DB: SELECT id=25 FOR UPDATE

    Note over DB,T2: 成環！回滾代價較小者
    DB-->>T2: Error 1213 Deadlock
    DB-->>T1: 喚醒並完成 INSERT

經典「查無此列再插入」死鎖：前兩步 Gap Lock 彼此相容不會排隊，導致雙方同時踏入陷阱，直到雙雙 INSERT 才互等成環。

  1. 多索引路徑交錯：T1 走二級索引 idx_email 更新（加鎖順序：idx_email → PRIMARY），而 T2 走主鍵更新同一列並修改了 email 欄位（加鎖順序：PRIMARY → idx_email），在微秒級時間差內迎頭相撞。

Wait-for Graph 主動抓環 vs Timeout 被動逾時

面對死鎖，為什麼資料庫不能只靠 innodb_lock_wait_timeout（預設 50 秒）逾時解開？因為在高併發線上服務裡，讓兩條持鎖連線白白卡死 50 秒，後面排隊依賴它們的數百個請求會像骨牌一樣連鎖逾時。

因此主流引擎都實作了等待圖（Wait-for Graph，WFG）主動偵測：以交易為節點，只要 Ti 請求的鎖與 Tj 已持有的鎖（或排在前面等待中的不透明鎖請求）衝突，就畫一條有向邊 Ti → Tj，並以深度優先搜尋（DFS）檢查是否出現有向環：

  • MySQL InnoDB（立即偵測）：開啟 innodb_deadlock_detect = ON（預設）時，每次鎖請求發生阻塞的當下就立刻遍歷 Wait-for Graph，微秒級抓出死鎖。但在「數百執行緒同時搶同一列」的極端熱點下，每次阻塞都鎖住全域鎖表做 O(V+E) 圖搜尋會燒光 CPU（MySQL 8.0.18 起改由背景專用執行緒非同步掃描大幅緩解此瓶頸）。
  • PostgreSQL（延遲偵測折衷）：阻塞當下不立刻建圖，而是先睡一個 deadlock_timeout（預設 1s）；99.9% 的正常鎖爭用在幾毫秒內就拿鎖離開，完全零圖搜尋成本，只有睡眠滿 1 秒仍未獲鎖的交易才會喚醒死鎖偵測器跑一次 Wait-for Graph。

誰會被選為犧牲者（Victim Selection）？

一旦偵測到環（例如 T1 → T2 → T1），資料庫只需強制 ROLLBACK 環上其中一筆交易即可破環。InnoDB 的 lock_deadlock_select_victim 遵循最小回滾代價原則：比較環上各交易目前已產生的 Undo Log 紀錄筆數（鎖權重與已修改列數 trx->undo_no），挑修改量最少、回滾最便宜的那筆交易作為犧牲者回滾並回傳 SQLSTATE 40001（MySQL Error 1213），保留已經做完大量寫入的重型交易繼續前進。

應用端防禦清單、重試協定與面試 FAQ

把鎖競爭擋在架構層的四條鐵律、正確的交易重試寫法，以及高頻考題拆解。

在分散式與高併發後端中，死鎖不可能也不需要被徹底消滅到零——就像網路封包重傳一樣，工程目標是「架構上把發生率壓低兩個數量級，程式碼裡讓偶發死鎖對使用者無感」。

把鎖競爭與死鎖壓到最低的四條架構鐵律

  1. 全域固定加鎖順序（Canonical Resource Ordering）：只要一筆交易會鎖定多筆同類資源（例如 A 轉帳給 B、一次結算多筆購物車商品），在進入交易或發送批次 SQL 前，一律先在應用程式記憶體按主鍵升冪排序（sort((a, b) => a.id - b.id)）。第 6 節的模擬器已驗證：當所有交易都先鎖小號再鎖大號，Wait-for Graph 在拓樸上只會形成有向無環圖（DAG），絕不可能成環。
  2. 把最熱點的那條 SQL 移到交易最後一步：交易內所有的鎖都是在 COMMIT 瞬間才一次釋放（Strict 2PL，嚴格兩階段鎖定），但加鎖時刻卻是執行到該條 SQL 才發生！如果一筆訂單交易包含「① 插入訂單主檔 → ② 插入明細 → ③ 扣減熱門商品總庫存 → ④ 寫入稽核紀錄」，把第 ③ 步調到 COMMIT 前最後一行執行，就能讓熱點庫存鎖的持有時間從整筆交易耗時縮短到最後幾百微秒。
  3. 收斂鎖定半徑，消除無謂的 Gap Lock：
    • 用唯一約束搭配原子 Upsert（MySQL INSERT ... ON DUPLICATE KEY UPDATE／PostgreSQL INSERT ... ON CONFLICT DO UPDATE）取代「先 SELECT FOR UPDATE 查不存在再 INSERT」。
    • 若業務不依賴當前讀的區間防幻讀且使用 Row-based Binlog，將隔離級別設為 READ COMMITTED 可直接卸除搜尋掃描的 Gap Lock 與大半部分死鎖來源。
  4. 為寫入連線設定合理的防守逾時：將會話級 lock_timeout（PostgreSQL）或 innodb_lock_wait_timeout 從預設的 50 秒調降至符合 SLA 的 2s ~ 5s（或針對搶購路徑直接使用 NOWAIT），防止慢查詢持鎖時引發全站執行緒雪崩。

應用端標準死鎖重試協定（Transaction-level Retry）

當資料庫回傳序列化或死鎖錯誤（SQL 標準 SQLSTATE 40001、MySQL Error 1213、PostgreSQL 40P01）時，整筆交易其實已經被資料庫引擎自動回滾完畢。應用端重試必須遵守三個關鍵細節：

誤區 1
只重送報錯的那一條 SQL——死鎖發生後舊交易已回滾、先前讀取的值與鎖全部失效；重試單位必須是整個交易閉包（重新 BEGIN、重讀最新資料、重算業務邏輯再寫入）。
誤區 2
0 延遲緊密迴圈立刻重試——剛對撞的兩台應用伺服器若在 0 毫秒後同時重跑相同順序，極高機率再次在同一個時間點迎頭互鎖；重試之間應加入 5ms ~ 40ms 的指數退避與隨機抖動（Exponential Backoff + Jitter）錯開相位。
誤區 3
交易閉包內夾帶不可重入的外部副作用——若閉包裡發送了沒有冪等鍵（Idempotency Key）的扣款 RPC 或推播訊息，重跑交易就會重複觸發外部動作。外部通知應改寫進同庫 Outbox 表，提交後非同步投遞。
// 標準交易重試包裝器（虛擬碼）
async function runTxWithDeadlockRetry(db, maxAttempts, workFn) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await db.transaction(async (tx) => workFn(tx)); // 每次皆全新 BEGIN + 重讀重算
    } catch (err) {
      const retryable = err.sqlState === '40001' || err.errno === 1213 || err.code === '40P01';
      if (!retryable || attempt === maxAttempts) throw err;
      const baseMs = 8 * Math.pow(2, attempt - 1);
      const jitterMs = Math.floor(Math.random() * baseMs);
      await sleep(baseMs + jitterMs); // 隨機抖動錯開並發重試相位
    }
  }
}

面試高頻追問 FAQ

Q1單條 UPDATE 語句、沒有顯式寫 BEGIN...COMMIT，也有可能發生死鎖嗎？▸

完全有可能！在自動提交（Autocommit）模式下，單條 UPDATE 本身就是一筆獨立交易，但它在底層並不是一瞬間把所有鎖一次拿齊，而是隨著索引掃描逐筆加鎖。

例如兩條自動提交的 UPDATE 分別走了不同的二級索引卻命中同一批資料列（加鎖順序一正一反），或是單條範圍 UPDATE 掃描途中與另一條反向掃描／回表更新交錯，一樣會在單句執行期間形成循環等待並拋出 Error 1213。

Q2既然已經有 MVCC 了，為什麼高併發系統還是常常被鎖卡住？▸

MVCC 只解放了「純讀取（快照讀）不阻塞寫入、寫入也不阻塞純讀取」這兩個方向；但「寫入對寫入（Write-Write Conflict）」依然必須靠排他鎖串行化。

只要多筆交易集中修改同一個熱點列（如商戶總餘額、熱門活動剩餘名額），或是查詢沒走索引、在 Repeatable Read 下觸發大範圍 Next-Key Lock，寫入執行緒之間依然會大排長龍。

Q3MySQL 遇到死鎖時如何排查第一現場？▸

實務排查三板斧：① 執行 SHOW ENGINE INNODB STATUS 查看 LATEST DETECTED DEADLOCK 區塊，裡面會完整印出參與死鎖的兩筆交易當時正在執行的 SQL、各自持有的鎖（HOLDS THE LOCK(S)，標明是 rec but not gap、gap before rec 還是普通 Next-Key Lock）與正在等待的鎖（WAITING FOR THIS LOCK TO BE GRANTED），以及最後誰被 WE ROLL BACK TRANSACTION；② 開啟 innodb_print_all_deadlocks = ON，將每一次死鎖完整記錄到錯誤日誌以免被下一次覆蓋；③ 即時阻塞現場則查 performance_schema.data_locks 與 data_lock_waits。

Q4秒殺扣減單一商品庫存 10,000 件，單列鎖上限撐不住怎麼辦？▸

當單列原子 UPDATE 也撞上物理鎖持有時間天花板時，資料庫層有兩種經典擴展思路：① 庫存分桶（Inventory Bucketing / Slotted Counter）——把 1 列 stock = 10000 拆成 16 或 64 列子桶（每桶 625 件），請求按雜湊隨機挑一桶扣減，直接把鎖競爭攤薄 16～64 倍（桶空時再降級掃其他非空桶）；② 請求合併（Group / Batch Update）或前置快取預扣（詳見「Redis 架構」與「快取模式」相關篇章），把高頻小扣減聚合成低頻批次落庫。

一句話答法工程防死鎖靠「固定資源加鎖序、熱點 SQL 後置、精準索引縮減 Gap 範圍、整筆交易帶隨機抖動重試」四招並進，讓資料庫鎖保護一致性而不拖垮吞吐。
