01

總覽：切塊是 RAG 品質的隱形殺手

Embedding 模型再強，也救不回「切錯位置」的知識庫——本篇只深入 Chunking 與檢索調校，不重複 RAG pipeline 全貌。

在 RAG 架構綜合手冊 裡，我們把線上路徑畫成「Embed → Retrieve → Prompt → Generate」。實務上，召回品質往往在離線 ingest 的切塊階段就定生死：塊切得太粗，向量被多主題平均掉；切得太細，答案被拆散到不同 chunk；切在句子中間，關鍵條件與例外條款分離——之後再怎麼調 Top-k 也只是在噪音裡打轉。

邊界切斷
「退貨 14 日」與「須原包裝」被切成兩塊；查詢只命中半句，模型補腦幻覺。
語義稀釋
一大段混合退貨、運費、促銷；embedding 變成「什麼都有一點」的模糊向量。
上下文不足
小塊命中分數高，但沒有標題／章節父文，生成時缺前提與適用範圍。
定位本篇 vs 綜合手冊

綜合篇交代 pipeline 與痛點；本篇假設你已懂「為何需要 RAG」，專心回答：固定長度怎麼選、要不要 overlap、metadata 寫什麼、以及 parent-child / small-to-big 如何同時兼顧召回與上下文。

一句話答法RAG 品質常死在切塊：錯邊界、語義稀釋、上下文不足——調檢索參數救不了離線切錯的索引。
02

固定長度 vs 語意切塊

兩條主幹路線：可預期、便宜、好批次；或對齊段落／標題，讓一塊幾乎對應一個語義單元。

固定長度（Fixed-size）
TOKEN / CHAR WINDOW
  • 依 token 或字元數切（常見 256–512 tokens）。
  • 實作簡單、吞吐高、成本可預期。
  • 易在句中切斷；多主題同塊會稀釋向量。
  • 適合結構亂、HTML 雜訊多、或先求「有索引」的冷啟動。
語意切塊（Semantic）
HEADING / PARAGRAPH / BOUNDARY
  • 依標題、段落、列表、或 embedding 相似度斷點切。
  • 一塊較像「一個可回答單元」，召回更乾淨。
  • 實作與調參成本高；長度不均影響 batch。
  • 適合手冊、政策、RFC 等有清楚結構的文件。
固定窗 → 快、齊長、易切壞 ｜ 語意邊界 → 對齊主題、長短不一
維度固定長度語意切塊
實作成本 低（計數器即可） 中高（解析器／相似度斷點）
塊內純度 不可控，常混主題 較高，一塊一意
長度分布 齊整，利於 batch 長尾，需設 max／merge 規則
面試答法 冷啟動、雜訊語料首選 結構化知識庫品質首選

實務常採「語意優先 + 固定上限兜底」：先依標題／段落切，超過 max tokens 再二次固定切。

陷阱別把「塊越大越好」當召回解法

加大 chunk 看似「比較完整」，卻讓向量平均掉細節；Top-k 命中一塊卻塞滿無關段落，反而擠掉真正相關的其他塊。大小要對齊「一個問題通常需要多少上下文」，不是對齊模型最大窗口。

一句話答法固定長度換便宜與可預期；語意切塊換純度與召回品質——結構化文件優先語意，再以 max size 兜底。
03

Overlap 與 Metadata 標註

Overlap 修補邊界切斷；Metadata 讓檢索可過濾、生成可引用——兩者常比換 embedding 模型更划算。

Overlap（重疊窗）

相鄰 chunk 保留一段重疊（常見為窗長的 10%–20%）。當答案橫跨切點時，至少有一塊仍同時含「條件 + 結論」。代價是索引膨脹與近似重複；overlap 過大等於變相加大塊並製造近重複命中。

overlap ≈ 0.1 × chunk_size　～　0.2 × chunk_size

Metadata（檢索與引用的把手）

每塊至少應帶：doc_id、title／路徑、section、page 或偏移、updated_at、以及權限標籤。線上路徑用 metadata 先過濾再 ANN（或 post-filter），避免把過期政策、無 ACL 權限的片段送進 prompt。

欄位用途不做會怎樣
section / heading 組 prompt 時還原章節語境 模型不知道「這段適用哪個產品線」
updated_at 新鮮度過濾、衝突時取新 舊政策與新政策同時進 Context
acl / tenant 檢索側權限隔離 敏感 chunk 泄漏進 prompt
source_url 強制引用與人工稽核 答案無法回溯，無法除錯召回
關鍵Overlap 是止血，不是架構

Overlap 修的是「切點剛好落在答案中間」；它治不好多主題同塊的語義稀釋。結構清楚時，寧可語意切塊 + 小 overlap，也不要超大固定窗假裝「一定覆蓋」。

一句話答法Overlap 用 10%–20% 救邊界；Metadata 負責過濾、引用與除錯——兩者比盲目換模型更有效。
04

Parent-Child 與 Small-to-Big 檢索

小塊負責「好命中」，大塊（父段）負責「好生成」——把召回粒度與生成上下文拆開。

Parent-Child（父子索引）：把文件切成較大的 parent（例如一整節），再切成較小的 child（句子／短段）。索引與 ANN 只打在 child；命中後用 child 的指標回填對應 parent，把 parent 全文（或標題 + parent）塞進 prompt。

Child（小）
嵌入＋ANN
高純度召回
→
Parent（大）
回填章節全文
補足前提與例外
→
Prompt Context
小塊定位
大塊說清楚

Small-to-Big 是同一思路的檢索說法：先用小單位找準位置，再「放大」到足夠回答的上下文。變形包括：命中句 → 取前後 N 句；命中段落 → 取整節；多個 child 同 parent 時去重，只送一次 parent。

做法優點代價／留意
只索引大塊 實作簡單 向量稀釋，細問題召回差
只索引小塊 召回準 Context 缺前提，易斷章取義
Parent-Child 召回準＋生成完整 雙層索引／映射表；要去重 parent
膨脹 Top-k 不用改切塊 噪音與 token 成本上升，治標
陷阱命中三個 child、塞三份幾乎一樣的 parent

同一 parent 被多個 child 打中時，務必依 parent_id 去重，否則 prompt 被重複段落洗版，既浪費窗口又讓模型過度關注同一節。評測時應同時看「召回是否對」與「送進 Context 的唯一 parent 數」。

一句話答法Parent-Child＝小塊檢索、大塊生成；small-to-big 把定位與上下文解耦，比單純加大 chunk 更乾淨。

06

檢索調校清單（不動模型先調這些）

換 embedding 很貴；先把切塊、過濾、Top-k 與去重調穩，通常就能拉開一截品質。

旋鈕常見起點觀察訊號
chunk_size 256–512 tokens（手冊可更短） 塊太大→分數平；太小→答案碎片
overlap 10%–20% 窗長 跨句問題漏召回時先加；過大則近重複
Top-k 先 3–8，有 rerank 可取更大候選池 無 rerank 時盲目加大常變差
metadata filter 產品線／版本／ACL／時效 答到錯產品或過期條款
parent 去重 依 parent_id 唯一化再組 Context Context 重複、窗口被洗版
銜接下一步不在本篇

純向量仍可能漏「精確型號／錯誤碼」——那是 Hybrid Search + Reranking 的戰場。本篇把「塊切對、上下文夠」做完，再往混合檢索與評估篇走，才不會把問題全怪到模型頭上。

一句話答法先調 size／overlap／metadata／Top-k／parent 去重；這些旋鈕穩了，再考慮換模型或上 hybrid。
07

面試折衷與實務清單

能講清「為何切錯會害死召回」、並畫出 parent-child，就比只背「用 LangChain 切一下」有說服力。

決策點一端做法另一端做法留意
切塊策略 固定窗：快、齊 語意切：純、準 結構化文件別死守固定窗
上下文策略 加大單一 chunk Parent-Child / small-to-big 加大塊會稀釋；父子要去重
邊界保護 無 overlap 10%–20% overlap overlap 是止血，不是萬靈丹
除錯單位 只看最終答案 看命中 chunk + metadata 沒引用就無法判「切錯還是生成錯」
實務上線前至少準備的三件事

（1）一組「答案橫跨段落邊界」的回歸問句；（2）每塊必有 section／版本／來源 URL；（3）若用父子索引，量測「唯一 parent 進 Context」而非只看 child 分數。這三樣能快速分辨是切塊問題還是生成問題。

一句話答法面試答 Chunking：固定 vs 語意、overlap 止血、parent-child 解耦召回與上下文，並用邊界回歸題驗收。
