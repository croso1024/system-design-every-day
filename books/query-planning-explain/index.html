查詢計畫與 EXPLAIN (Query Planner & Join Algorithms)

SQL 是宣告式語言：你只描述「要什麼結果」，不指定「先讀哪張表、走不走索引、用哪種演算法把兩張表接起來」。把語意翻譯成執行路徑的，是資料庫裡的基於成本優化器（Cost-Based Optimizer, CBO）。線上慢查詢有八成不是資料庫壞了，而是優化器拿著過期或失真的統計資訊，算出一份「帳面最便宜、實跑卻災難」的執行計畫。本篇拆解四種掃描算子、三種 Join 演算法、統計直方圖與基數估計，並帶你從 EXPLAIN ANALYZE 一眼抓出估計列數與實際列數的致命落差。

01

總覽：一條 SQL 如何變成執行樹

你寫的是關聯代數的目標，資料庫跑的是一棵由算子組成的實體執行樹。

當應用程式送出一條 SQL，資料庫並不會直接打開磁碟找資料，而是依序走過四個階段。理解這個管線，才能區分「語法改寫能救的事」與「必須修統計資訊或索引才能救的事」：

Parser & Rewriter
語法樹、語意分析、展開 View 與規則
▸
Catalog 統計資訊
總頁數、NDV、MCV 與等頻直方圖
▸
Planner / CBO
常數折疊、謂詞下推，枚舉掃描路徑與 Join 順序，挑最低成本樹
▸
Executor
火山模型拉取 tuple，管理記憶體與溢寫

慢查詢診斷的核心切口在中間兩格：Catalog 給錯統計數字，CBO 就會用正確的算術選出錯誤的執行樹。

優化器比較的不是毫秒，而是抽象的成本單位（cost units）。以 PostgreSQL 為例，預設以「循序讀一個 8 KiB 磁碟頁」為基準 seq_page_cost = 1.0，隨機讀一頁為 random_page_cost = 4.0（SSD 環境常調降為 1.1），每處理一筆 tuple 的 CPU 成本為 cpu_tuple_cost = 0.01。每個節點都會報出兩個數字：

  • Startup cost（啟動成本）：吐出第一筆結果前必須先付的代價。例如 Seq Scan 讀到第一頁就能吐資料，啟動成本為 0.00；Sort 或 Hash Join 必須先把子節點整批讀完才能吐第一筆，啟動成本很高。
  • Total cost（總成本）：假設把這個節點的所有結果全部讀完的累積代價。一般查詢看總成本；但如果查詢帶有 LIMIT 10，優化器會按比例折算，這時低啟動成本的算子（如走索引免排序的 Nested Loop）就會反超總成本較低的 Hash Join。
邊界本篇與前後主題的分工

B+Tree 的頁結構、複合索引最左前綴、聚簇索引回表與索引失效條件，已在資料庫索引原理篇完整展開；跨網路節點的分散式執行計畫（DistSQL、Shuffle、1PC/2PC 與租約讀取）則見分散式 SQL 資料庫篇。本篇聚焦於單機資料庫內部的優化器決策、單表掃描算子、多表 Join 演算法與 EXPLAIN 診斷，範例以成本模型最透明的 PostgreSQL 為主，關鍵處對照 MySQL（InnoDB）。

一句話答法Query Planner 是基於成本的搜尋器：它根據統計資訊估計每個條件會留下幾列（基數），再把掃描與 Join 算子的 I/O 與 CPU 單位成本加總，挑出預期總成本（或 LIMIT 下的部分成本）最低的執行樹。
02

單表掃描四種路徑：Seq、Index、Index Only 與 Bitmap Scan

「有索引卻不走」不見得是失效，往往是因為隨機回表的頁數算起來比循序掃全表還貴。

給定一張單表與 WHERE 條件，優化器手上有四種主要的取數算子。它們的取捨完全圍繞兩件事：要讀多少頁，以及這些頁在磁碟上是循序還是隨機。

掃描算子 讀取路徑 I/O 型態 輸出是否有序 典型勝出區間（經驗量級）
Seq Scan
（全表掃描）		 從頭到尾直讀整張表的所有資料頁，逐列過濾 WHERE 純循序 I/O，OS 預讀友善，一頁讀進來全頁列都檢查 無序（依實體頁順序） 高命中率（通常 > 15%–25%）、小表（僅數十頁），或無可用索引
Index Scan 沿 B+Tree 葉鏈找符合條目，每命中一筆立刻去資料表抓整列（回表） 索引葉鏈循序，但回表若實體位置分散則為隨機 I/O，同一頁可能被反覆觸碰 依索引鍵有序（可省下 ORDER BY，搭配 LIMIT 極快） 高選擇性（命中 < 1%–5%）、欄位高度聚簇（correlation ≈ 1），或有 ORDER BY ... LIMIT
Index Only Scan 查詢所需欄位全在索引條目裡，不回資料表（PostgreSQL 需先查 Visibility Map） 只讀索引頁，體積遠小於主表 依索引鍵有序 Covering Index 成立且主表頁近期已 VACUUM（Heap Fetches 低）
Bitmap Index + Bitmap Heap Scan 先掃索引把命中的 TID 在記憶體建成頁級與列級點陣圖，依實體頁號排序去重後再批次讀表 把散落的隨機回表轉成跳躍式循序 I/O，且每個資料頁保證只讀一次；可合併多個索引 無序（已改依實體頁號排序，不再保索引序） 中度選擇性（約 2%–20%，單走 Index Scan 太隨機、走 Seq Scan 又讀太多廢頁），或跨索引 AND / OR

Bitmap Scan 是連結 Index Scan 與 Seq Scan 的橋樑：它放棄了索引原本的排序，換取「每一頁最多讀一次、依頁號順序讀」的 I/O 效率；MySQL 對應的機制是 MRR（Multi-Range Read）與 Index Merge。

為什麼 Bitmap Scan 能組合兩個獨立的單欄索引？

假設查詢寫了 WHERE region = 'APAC' AND tier = 'PRO'，表上只有 idx_region 與 idx_tier 兩個獨立索引，沒有複合索引。一般 Index Scan 一次只能沿一棵樹走；Bitmap Scan 則可以各自掃出兩份 TID 點陣圖，在記憶體裡做位元級的 BitmapAnd（若是 OR 條件就是 BitmapOr），只對交集留下的頁號去讀主表。

但點陣圖有記憶體上限：它受限於 work_mem（每個 Sort／Hash／Bitmap 算子各自一份上限，PostgreSQL 預設僅 4MB）。當命中筆數太多、精確記錄每一列位址的點陣圖塞不進 work_mem 時，它會自動退化成Lossy（失真）模式——只記「哪一個 8 KiB 資料頁有命中」，不記頁內第幾列。進到 Bitmap Heap Scan 時就必須把整個標記頁的每一列都撈出來重跑一次 Recheck Cond。如果你在 EXPLAIN ANALYZE 看到 Heap Blocks: exact=120 lossy=48000，代表 work_mem 不夠裝點陣圖，大量無關列被拖進來重驗。

陷阱實體聚簇相關係數（Correlation）會讓同一條查詢成本差上百倍

同樣命中 10,000 列，若條件是自增時間欄 created_at，這 10,000 列緊密擠在相鄰的 150 個資料頁裡（pg_stats.correlation ≈ 0.99），Index Scan 回表幾乎等同循序讀；若條件是隨機的 user_id（correlation ≈ 0.02），這 10,000 列散在 9,500 個不同頁，隨機讀成本暴增兩百多倍。優化器在計算 Index Scan 成本時，會依 correlation 在 seq_page_cost 與 random_page_cost 之間插值——這就是為什麼欄位命中率一樣，一個走 Index Scan、另一個卻切去 Bitmap Heap Scan 或 Seq Scan。

一句話答法命中極少或需保序配 LIMIT 用 Index Scan；欄位全覆蓋且可見性乾淨用 Index Only Scan；命中率落在中間尷尬帶、或需跨多個索引做 AND/OR 交聯集時用 Bitmap Scan 把隨機回表排成頁序；命中過高就直接 Seq Scan 循序掃全表。
03

三種 Join 演算法：Nested Loop、Hash Join 與 Merge Join

所有多表查詢都會被拆成兩兩相接的二元節點；選哪一種接法，看外層列數、內層有無索引與記憶體夠不夠。

資料庫執行 A JOIN B JOIN C 時，並不是三張表同時混在一起算，而是先挑兩張表（例如 A ⋈ B）透過某種物理算子接成中間結果流，再把這個結果流當成外層（Outer），與 C 做第二次二元 Join。優化器在每一個接合點上，都從以下三種物理演算法擇一：

三種演算法的本質取捨：Nested Loop 賭「外層極少＋內層有索引」、Hash Join 賭「等值連接＋小表塞得進記憶體」、Merge Join 賭「輸入本來就有序，或大到 Hash Table 裝不下」。

MySQL 直到 8.0.18 才正式引入 Hash Join 取代無索引時的 Block Nested-Loop（BNL），且 MySQL 至今沒有獨立的 Merge Join 算子；PostgreSQL、Oracle、SQL Server 則三者俱全。

關鍵Hash Join 記憶體不夠時怎麼辦？Grace Hash Join 的 Batches

當優化器或執行器發現內層表建出的 Hash Table 超過 work_mem，並不會直接 OOM，而是把雜湊值切分成 B 個分區（例如 Batches: 8，必為 2 的次方）：第 1 批留在記憶體當場配對，第 2 到第 8 批的內層與外層 tuple 各自按雜湊分區寫進磁碟暫存檔，第一輪跑完再一桶一桶讀回來建表配對。代價是原本只讀一次的資料變成多一輪磁碟寫入＋讀取。在 EXPLAIN ANALYZE 裡看到 Batches: 1 代表全程在記憶體完成；看到 Batches > 1 且伴隨 temp read/written，調高該查詢 session 的 work_mem 往往能立竿見影。

一句話答法外層列數少且內層有索引時選 Indexed Nested Loop（啟動最快）；兩表都大且為等值條件時選 Hash Join（用小表建記憶體雜湊表、O(M+N) 掃過）；若兩側已具備索引順序、或大到 Hash Table 會嚴重溢寫磁碟時，選 Merge Join。
04

統計資訊與基數估計：Planner 的眼睛

優化器不會為了算成本先把表讀一遍；它所有的判斷都建立在抽樣統計的「猜測列數」上。

前面兩節反覆出現同一個關鍵詞：命中幾列。在優化器術語裡，一個節點預計輸出的列數稱為基數（Cardinality），而條件留下的比例稱為選擇性（Selectivity）：

估計列數 (Estimated Rows) = 表總列數 (reltuples) × 選擇性 (Selectivity)

資料庫背景的 ANALYZE（或 autovacuum）會隨機抽樣固定數量的資料頁（PostgreSQL 在 default_statistics_target = 100 時抽樣 30,000 列），將以下四項摘要存進系統目錄（如 pg_statistic，可由檢視表 pg_stats 查詢）：

  • Null 比例（null_frac）：該欄為 NULL 的列佔比，算等值或範圍前先扣除。
  • 相異值數量（n_distinct / NDV）：正數代表估計有幾個不同值，負數（如 -1）代表相異值隨表長等比例成長（例如唯一主鍵）。
  • 高頻值清單（Most Common Values, MCV）與對應頻率（MCF）：專門抓傾斜分布（Skew）。例如 status = 'PAID' 佔 78%、'CANCELLED' 佔 19%、'DISPUTED' 佔 0.05%，查詢常數只要落在 MCV 名單內，優化器直接查表拿精確比例；不在名單內才用剩餘機率除以剩餘相異值數。
  • 等高直方圖（Equi-depth Histogram）：把排除 MCV 後的值排序切成 100 個桶，每桶裝幾乎一樣多的列。遇到 amount BETWEEN 500 AND 2000 這類範圍條件，數一數跨了幾個桶就能估出比例。
為什麼多欄位條件最容易估錯？
獨立性假設 (Independence Assumption)

預設統計都是逐欄獨立收集的。當查詢寫 WHERE country = 'TW' AND currency = 'TWD'，假設全表 TW 佔 1/20、TWD 也佔 1/20，優化器預設兩者獨立，直接相乘得出 1/400。

但現實中台灣訂單幾乎全用台幣，真實比例接近 1/20——基數當場被低估 20 倍。三個高度相關欄位連乘，低估幾百倍是家常便飯。

怎麼修多欄位與表達式失真？
Extended Statistics & Expression Index

PostgreSQL 提供 CREATE STATISTICS s1 (dependencies, ndistinct, mcv) ON country, currency FROM orders;（ndistinct、dependencies 自 PG 10 起，mcv 自 PG 12 起），讓優化器知道欄位間的函數依賴與聯合分布；MySQL 8.0 則只有單欄直方圖，複合索引只提供各前綴組合的相異值數（NDV），無法描述跨欄位的聯合分布。

若是 WHERE lower(email) = ?，一般欄位統計完全不認得函式結果，優化器只能盲猜固定常數（如 0.5%）；建立表達式索引後再跑 ANALYZE，資料庫就會替該表達式單獨收集 MCV 與直方圖。

基數低估是慢查詢的頭號元兇：低估 100 倍會誘導優化器選出 Nested Loop，讓原本該一次掃完的 Hash Join 退化成十萬次隨機索引查找。

陷阱綁定參數（Prepared Statement）看不到常數值時怎麼辦？

當 ORM 使用 WHERE merchant_id = $1 預編譯語句時，通用計畫（Generic Plan）在規劃當下不知道 $1 是佔全表 40% 的超大商戶，還是只有 3 筆訂單的小商戶，只能拿平均頻率去估——結果大商戶被塞進 Index Scan 跑死，或小商戶被迫跑全表掃描。PostgreSQL（自 9.2 起）採混合策略：前 5 次執行根據實際傳入參數量身打造 Custom Plan，第 6 次起比較通用計畫成本是否明顯較差，只有不吃虧時才切去快取的 Generic Plan（PG 12 起另可用 plan_cache_mode 強制指定）。

一句話答法優化器靠 MCV 清單抓傾斜熱點、靠等高直方圖算範圍比例；它最脆弱的地方是「跨欄位預設獨立相乘」與「剛大批量寫入尚未 ANALYZE」，一旦基數被嚴重低估，後面上層的所有 Join 演算法都會跟著選錯。
05

讀懂 EXPLAIN ANALYZE：拆解成本、列數與迴圈倍數

看執行計畫不是從第一行往下唸，而是由內而外找「估計與實際差幾個數量級」以及「loops 乘了幾次」。

單純的 EXPLAIN 只問優化器「你打算怎麼跑」，不真正碰資料，耗時幾毫秒；加上 ANALYZE（MySQL 8.0.18+ 同為 EXPLAIN ANALYZE）則會真的把 SQL 跑完一遍，在每個算子旁邊同時印出「規劃時的預測」與「執行器的真實碼錶紀錄」。建議實務上一律加開緩衝區統計：EXPLAIN (ANALYZE, BUFFERS)。

陷阱對 UPDATE / DELETE / INSERT 跑 EXPLAIN ANALYZE 會真的改資料！

因為 ANALYZE 會完整執行語句，測試寫入類慢查詢時務必包在交易裡：BEGIN; EXPLAIN (ANALYZE, BUFFERS) DELETE FROM ...; ROLLBACK;，否則診斷完資料也刪光了。

來看一段典型的線上慢查詢輸出，我們把文字樹逐層拆開對照：

Nested Loop (cost=0.85..48.20 rows=6 width=128) (actual time=0.09..1842.60 ms rows=94500 loops=1)估 6 列 vs 實 94,500 列
Buffers: shared hit=291400 read=62180
頂層節點的 actual time 右側數字（1842.60 ms）包含所有子節點時間。問題不在這層本身，在下面兩個子節點的乘積。
-> Index Scan using idx_orders_region_tier on orders (cost=0.42..16.50 rows=3 width=72) (actual time=0.05..28.40 ms rows=31500 loops=1)禍首：低估 10,500 倍
Index Cond: ((region = 'APAC') AND (tier = 'PRO'))
跨欄位相關性導致 Planner 以為外層只吐 3 列，信心滿滿選了 Nested Loop；實際吐出 31,500 列，雖然這步本身只花 28 ms，卻把災難傳給了內層。
-> Index Scan using idx_items_order_id on order_items (cost=0.43..10.54 rows=2 width=56) (actual time=0.01..0.055 ms rows=3 loops=31500)0.055 ms × 31,500 圈 = 1,732 ms

關鍵讀法：actual time 與 rows 都是「單圈平均值」！單圈 0.055 ms 看似神速，乘上 loops=31500 就吃掉 1.73 秒與 35 萬次頁讀取。

讀樹四口訣：① 先看最內層葉節點誰先啟動；② 對比預計 rows= 與實際 rows= 是否差超過 10 倍；③ 任何內層節點的真實總耗時與總列數都要乘上 loops；④ 看 Buffers: shared hit / read 與 Rows Removed by Filter 抓白工。

sequenceDiagram

    participant O as Outer: Scan orders

    O-->>P: order_id = 1042

    O-->>P: EOF 結束

火山模型（Volcano / Iterator Model）中上層算子呼叫子節點的 Next() 拉取資料；Nested Loop 內層每換一筆外層列就觸發一次 ReScan，這就是 loops 的物理意義。

BUFFERS 與 Filter 欄位透露的硬體真相
  • shared hit vs shared read：hit 代表頁已在資料庫共享記憶體（Shared Buffers）中命中，只需幾百奈秒；read 代表向作業系統發起讀取（可能命中 OS Page Cache，也可能真的打到 SSD/磁碟）。第一次跑慢、第二次跑飛快，看這兩個數字一秒就能證實是冷快取效應而非計畫變了。
  • Index Cond vs Filter：Index Cond 是在 B+Tree 導航與葉頁上直接界定範圍；Filter 則是已經把整列抓回來（含回表）之後才丟掉。若 Rows Removed by Filter: 980000 而最終只留 rows=20，代表索引缺了關鍵過濾欄，九成九的回表都是白工。
  • MySQL EXPLAIN 對照速查：MySQL 傳統表格格式的 type 欄由好到壞依序是 system/const（主鍵唯一命中 1 列）▸ eq_ref（Join 時內層走主鍵/唯一索引每圈必只中 1 列）▸ ref（非唯一索引等值查找）▸ range（索引範圍）▸ index（掃整棵索引樹葉鏈）▸ ALL（全表掃描）；Extra 出現 Using filesort 代表無法借索引序被迫額外排序，Using temporary 代表建了記憶體或磁碟暫存表。
一句話答法讀 EXPLAIN ANALYZE 先抓「估計列數 vs 實際列數」差一個數量級以上的節點，再把子節點的單圈時間與列數乘上 loops 算真實總開銷，最後看 Rows Removed by Filter 與 Buffers: read / temp written 定位 I/O 浪費在哪裡。

    2. 
    
  2. 聚簇係數救回 Index Scan：在選擇性 5% 時原本走 Bitmap Scan；把「實體聚簇 correlation」拉到 1.00（代表資料完全照索引順序存放），Index Scan 回表變成近似循序讀，成本從 24,641 降到 343，立刻奪回冠軍。
    3. 
    
  3. work_mem 不足引發 Hash Spill：從預設把選擇性拉到 12%（外層 24,000 列）、work_mem 壓低到 4 MB；Hash 表建在過濾後較小的 orders 一側，24,000 列已塞不進 4 MB，勝出的 Join 變成 Hash Join (Batches=2)、Join 指標框轉為橘色。此時切到「雙邊已排序索引」，Hash Join 橫條轉橘落選，免排序的 Merge Join 完全不吃 Hash 記憶體，以 34,810 對 39,606 反超勝出。
    4. 
    
  4. 統計過期低估災難：把選擇性設在 12%（實際 24,000 列），正常該跑 Hash Join；接著把「統計估計偏差」往左拉到 0.02x（低估 50 倍），Planner 以為外層只有幾百列而誤選 Nested Loop，右上角會直接算出真實執行成本比最佳計畫暴增數倍。

    一句話答法沒有哪種掃描或 Join 永遠最快：低選擇性＋內層索引屬於 Index Scan 與 Nested Loop，中高選擇性屬於 Bitmap/Seq Scan 與 Hash Join，預先排好序或記憶體受限時則是 Merge Join 的主場。
  





  

    07
    
三大實務慢查詢模式：N+1、OFFSET 深分頁與統計過期

  

  
很多拖垮資料庫的慢查詢，單看每一條 EXPLAIN 都走了索引，甚至毫秒級返回。


  
1. N+1 查詢：把資料庫內的批次 Hash/Index Join 拆成網路上的迴圈

  
ORM 預設的 Lazy Loading（延遲載入）最容易製造這種隱形殺手：先跑 1 條 SELECT * FROM orders LIMIT 50，接著在應用程式的 for 迴圈裡，每次讀 order.items 就觸發 1 條 SELECT * FROM order_items WHERE order_id = ?，總共打出 1 + 50 = 51 次獨立 SQL。

  
為什麼危險？因為單條子查詢走主鍵或外鍵索引只要 0.3 ms，根本不會進資料庫的 Slow Query Log（門檻常設 200 ms 或 1 s）！但應用程式到資料庫每次跨網路往返（RTT）加協定解析就要 0.8–1.5 ms，50 圈串行累加就是 60–90 ms；列表頁若是 200 筆再套兩層關聯，一個 API 請求就會打出 400 條 SQL、連線池瞬間被佔滿。

  
    
    
  • 修法 A（預先批次載入 `WHERE id IN (...)` / DataLoader）：外層撈出 50 個 order_id 後，合併成單條 WHERE order_id = ANY($1)。資料庫只付 2 次網路 RTT，且內部能用 Bitmap/Index Scan 一次排好抓回。
    • 
    
  • 修法 B（單條 `JOIN` 查詢）：當需要依子表欄位過濾或排序時直接寫 SQL JOIN，交給優化器在同一個記憶體空間跑 Nested Loop 或 Hash Join；但若一對多比例極懸殊，要注意父表欄位重複傳輸造成的網路封包膨脹。
    • 
  


  
2. OFFSET 深分頁：越往後翻越慢的「讀完再丟」陷阱

  
傳統分頁寫 SELECT id, title FROM posts ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 100000。即使 (created_at, id) 上有完美的複合索引，B+Tree 節點預設並不會記載「子樹底下有幾筆對當前 MVCC 快照可見的列」（因為不同並行交易看到的可見列數都不同）。

  
結果執行器別無選擇：它必須老老實實從第 1 筆定位，沿著索引與資料頁取出前 100,020 列、逐筆檢查可見性、把前 100,000 列直接丟進垃圾桶，只留下最後 20 列回傳。翻到第 5,000 頁的成本是第 1 頁的五千倍，爬蟲或匯出排程往後翻頁時直接把資料庫 I/O 打爆。


  

    

      
延遲關聯（Deferred Join）：只能治標一半

      
子查詢先走 Covering Index 再回表 20 次

      
改寫為 SELECT p.* FROM posts p JOIN (SELECT id FROM posts ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 100000) t USING (id)。

      
這省下了前 100,000 筆的隨機回表，讓子查詢只掃輕量的覆蓋索引葉鏈，通常能快 5–10 倍；但索引葉鏈掃描本身仍是 O(OFFSET)，百萬級深分頁依然會慢。

    

    

      
Keyset / Cursor 分頁（Seek Method）：真正的 O(log N)

      
記住上一頁最後一筆的座標當起點

      
前端帶回上一頁最末筆的 (last_ts, last_id)，改查 WHERE (created_at, id) < ($last_ts, $last_id) ORDER BY created_at DESC, id DESC LIMIT 20。

      
B+Tree 直接下探定位到游標旁，往後連讀 20 筆即停，丟棄列數永遠是 0，第 1 頁與第 50,000 頁一樣只要 1–2 毫秒。唯一必須遵守的鐵律是排序鍵必須唯一（時間欄一定要補上唯一 id 當平手決勝欄 tie-breaker），否則同秒鐘的多筆紀錄會在翻頁邊界漏掉或重複。代價是無法隨機跳去「第 372 頁」，適合無限滾動、歷史時間軸與批次匯出。

    

  

  
OFFSET 是「數人頭跳過」，成本隨頁碼線性惡化；Keyset 是「拿書籤直接翻開」，成本與頁碼完全脫鉤。


  
3. 統計過期造成計畫突變（Plan Flip / Plan Regression）

  
為什麼同一條 SQL 昨天跑 5 ms，今天凌晨突然飆到 40 秒，而且沒人改程式碼？常見劇本有三種：

  
    
    
  1. 冷熱水位劇變（佇列表／狀態表反模式）：一張 job_queue 表平時 status = 'PENDING' 只有幾十筆，autovacuum / ANALYZE 剛好在低水位時跑過，Catalog 記下「PENDING 佔 0.01%」。促銷整點瞬間湧入 30 萬筆 PENDING，autovacuum_analyze_scale_factor（預設變動滿 10% 才觸發背景重算，大表上可能要等很久）還沒來得及更新，優化器仍拿舊統計選 Nested Loop。
    2. 
    
  2. 自增時間欄超出直方圖右邊界（Out-of-Range Predicate）：直方圖紀錄的最大 created_at 是昨天半夜 23:50。今天早上查詢 WHERE created_at >= '今天 09:00'，落在直方圖已知上限之外！優化器會以為幾乎沒資料（估成 rows=1），一旦這條結果被拿去當 Nested Loop 的外層驅動表，後面串接的所有大表就會被循環狂掃數萬次。
    3. 
    
  3. 大批量匯入後立刻跑報表：ETL 剛灌進 500 萬列，在同一條腳本下一行馬上跑複雜聚合 JOIN，此時背景統計執行緒根本還沒排程進場。工程鐵律：任何大批次 COPY / INSERT / DELETE 結束後，在應用程式流程主動執行一次手動 ANALYZE table_name;（它只抽樣讀幾萬列、不鎖讀寫，通常一兩秒就跑完）。
    4. 
  


  

    一句話答法N+1 死在網路往返累加而非單條慢查詢，用 IN 批次或 JOIN 根治；OFFSET 深分頁死在必須讀完並丟棄前 N 列，用帶唯一 tie-breaker 的 Keyset 游標化為常數時間；統計過期常發生在時間超出直方圖上界或批次灌資料後，主動 ANALYZE 與調低單表抽樣觸發門檻是標準防線。

線上慢查詢診斷與安全調校 SOP

  

  
不要看到慢查詢就反射性亂加索引或硬塞 Optimizer Hint；照固定順序排查才能治本且不留技術債。


  
當監控系統（如 PostgreSQL 的 pg_stat_statements 或 MySQL 的 Performance Schema / Slow Query Log）抓出總耗時最高的前五名 SQL 時，建議按這套由淺入深的五步清單執行：


  

    

      
        

          排查步驟
          觀察指標（EXPLAIN ANALYZE）
          根因判讀
          標準工程處置（優先級由高到低）
        

      
      
        

          ① 對帳基數估計
          預計 rows 與實際 actual rows 差距 > 10x
          統計過期、直方圖顆粒度太粗，或多欄位強相關違反獨立假設
          跑 ANALYZE tbl ▸ 調高熱點欄位 ALTER TABLE ... ALTER COLUMN c SET STATISTICS 1000 ▸ 建多欄位 CREATE STATISTICS
        

        

          ② 檢查過濾白工
          Rows Removed by Filter 遠大於最終輸出列數
          索引只涵蓋部分條件，大量無關列回表後才被篩掉；或欄位被函式包住
          補齊複合索引等值欄、把高頻查詢改為 Covering Index（INCLUDE），或改寫 SARGable 條件（見資料庫索引原理篇）
        

        

          ③ 檢查記憶體溢寫
          Hash Join Batches > 1、Sort 出現 external merge Disk、Bitmap 出現 lossy
          單算子可用的 work_mem / sort_buffer_size 小於工作集
          針對該報表連線或交易局部調高 SET LOCAL work_mem = '64MB'（切忌無腦調高全域設定，因每個並行算子都會乘上一份！）
        

        

          ④ 校準硬體成本常數
          統計完全準確，但 SSD 環境仍死守 Seq Scan 拒走好索引
          預設 random_page_cost = 4.0 是機械硬碟時代的比值，高估了隨機讀代價
          在 NVMe / 雲端 SSD 上將 random_page_cost 調至 1.1–1.5，並如實設定 effective_cache_size（約系統記憶體 50%–75%）
        

        

          ⑤ 最後手段：Hint
          跨複雜 CTE / 特殊邊界分布，優化器受限模型結構始終選錯
          CBO 代數模型盲區（如複雜子查詢展開或特定版本限制）
          MySQL 8.0.20+ 以 /*+ BNL(t1, t2) */／NO_BNL 開關 Hash Join（HASH_JOIN 提示僅 8.0.18 有效），或 PG 擴充套件 pg_hint_plan；必須寫註解壓單號並排程追蹤，避免日後資料長大反而鎖死爛計畫
        

      
    

  

  
調校鐵律：先餵給優化器正確的事實（統計資訊與硬體成本比），讓它自己算出好計畫；只有當它看對事實仍算錯決策時，才人工介入綁死執行路徑。


  

    
陷阱千萬別在測試機 500 筆假資料上驗收 EXPLAIN！

    
這是後端團隊最常踩的部署事故：工程師在本地開發庫（只有 500 列）跑 EXPLAIN，看到 Seq Scan 以為索引壞了，硬改語法或硬塞 Hint；殊不知一張只佔 4 個磁碟頁的小表，走 Seq Scan 讀 4 頁本來就比「先讀索引 2 頁再回表讀 3 頁」更快！執行計畫隨資料規模與值分布動態變化，驗收查詢計畫必須在等比例資料量與真實分布的 Staging 環境（或生產唯讀副本）上進行。

  


  

    一句話答法線上慢查詢排查依序看：① 估計與實際列數落差（修統計）▸ ② Filter 丟棄列數（修索引與語法）▸ ③ Disk Spill 與 Lossy 區塊（局部調 work_mem）▸ ④ SSD 隨機讀成本參數；Optimizer Hint 永遠放最後一招。

面試答題框架

  

  
遇到「線上某支 API 突然變慢，怎麼查 SQL？」或「三種 Join 怎麼選？」，用結構化因果鏈拿滿分。


  

    

      
        
高頻面試追問高分答題骨架

      
      
        

          Nested Loop、Hash Join、Merge Join 各在什麼時候勝出？
          先看等值限制，再看資料量與排序：① 外層過濾後列數少＋內層 Join 鍵有索引 → Indexed Nested Loop（啟動成本最低、配 LIMIT 最強）；② 兩表都大＋等值條件＋無現成排序 → Hash Join（小表建記憶體雜湊表、O(M+N) 掃過，留意 work_mem 溢寫分批）；③ 兩側已有 B+Tree 排序或結果需要該順序、或表大到 Hash 嚴重爆記憶體，以及部分範圍配對 → Merge Join。
        

        

          有建索引、語法也沒失效，為什麼資料庫還是走全表掃描？
          因為優化器算的是總頁數與隨機 I/O 成本：當條件選擇性不夠高（例如命中 20%）、且實體存放散亂（低 correlation）時，走索引再隨機回表數萬次的成本遠高於循序預讀掃過全表；或是表本身極小只佔幾頁。中間地帶資料庫常改選 Bitmap Heap Scan 先把 TID 按頁號排好再讀。
        

        

          給你一份 EXPLAIN ANALYZE，你第一眼看哪裡？
          四步：① 由最內層節點往外看誰耗時佔比最高（記得扣掉子節點時間）；② 比對每個節點的預計 rows 與 actual rows 是否差一個數量級以上（抓基數估錯引發的錯誤 Nested Loop）；③ 將內層單圈 actual time 與 rows 乘上 loops 還原真實總量；④ 看 Rows Removed by Filter、Heap Fetches 與 Buffers: read / temp written。
        

        

          昨天很快的 SQL 今天沒改版卻突然超時，可能原因？
          典型「計畫突變（Plan Flip）」：① 大批寫入/刪除後尚未 ANALYZE，統計過期；② 查詢時間窗跨出直方圖右邊界被估成 1 列，觸發災難性 Nested Loop；③ 預編譯語句前 5 次都是小客戶，其 Custom Plan 成本讓 PG 判定 Generic Plan 不吃虧而改用快取的通用計畫，之後原封不動套在大租戶（Data Skew）上；④ 資料量跨過 work_mem 臨界點開始磁碟 Spill。
        

        

          百萬筆列表翻到第 5,000 頁很慢，怎麼設計？
          指出 OFFSET 100000 必須實際掃過並做 MVCC 可見性檢查再丟棄前十萬列，複雜度 O(OFFSET)。產品允許上下頁或無限滾動時，改用 Keyset / Cursor 分頁 WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20（強調唯一平手欄位 id 防漏列），壓回 O(log N)；若產品硬性要求跳頁碼，則限制最大可翻頁深（如前 100 頁）搭配覆蓋索引 Deferred Join 或搜尋引擎。
        

      
    

  

  
面試談資料庫效能，能講出「統計直方圖 ▸ 基數估計誤差 ▸ Join 演算法翻轉 ▸ loops 乘法放大」這條完整因果鏈，就能立刻與只會背「加索引、不要 SELECT *」的候選人拉開差距。


  

    
延伸下一步往哪裡走？

    
讀懂單機執行計畫之後，若系統面臨高並發寫入競爭，下一步要搞懂執行器在掃描這些索引紀錄與間隙時到底鎖住了什麼（Row Lock / Gap Lock 與死鎖偵測）；若單機容量見頂需要水平拆表，跨分片的查詢計畫如何做 Predicate Pushdown 與 Shuffle Merge，則可銜接分散式 SQL 資料庫篇與資料分片實戰篇。
