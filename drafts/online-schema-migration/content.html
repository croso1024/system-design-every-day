線上 Schema 變更與零停機 Migration

在每秒承受數千筆讀寫的線上資料表上改結構，真正的殺手往往不是 ALTER TABLE 本身跑得慢，而是一把等不到前序交易釋放的排他元資料鎖，加上滾動部署期間新舊版程式對同一張表的契約撕裂。

01

為什麼一句 10ms 的 ALTER 會癱瘓整座資料庫？

從 Metadata Lock 佇列護航效應與實體重寫代價出發，拆解 PostgreSQL 與 MySQL InnoDB 的 DDL 鎖行為。

在單機開發環境對幾千列的資料表下 ALTER TABLE users ADD COLUMN ...，毫秒間就能收工；但把同一句 SQL 放到每秒數千筆查詢的生產主庫，卻經常在三十秒內把應用端連線池全部卡死、觸發全站雪崩。許多工程師的第一反應是「因為大表搬移資料很慢」，但真實事故現場裡，就算是一句只需要 5 毫秒改完資料字典（Catalog）的輕量 DDL，照樣能癱瘓整座叢集。

在進入細節前先劃清知識邊界：資料列鎖、區間鎖（Gap / Next-Key Lock）與死鎖偵測機制由資料庫鎖與死鎖篇負責；服務實例的滾動更新與金絲雀流量調度由部署與發佈策略篇負責；跨實體節點的資料分片搬遷則由分片實戰與線上擴容篇負責。本篇專注於單一邏輯資料庫內，如何在讀寫不中斷的前提下安全演進表結構與資料內容。

頭號殺手：元資料鎖佇列護航效應（Lock Queue Convoy）

無論是 PostgreSQL 的表級鎖（Table-level Lock）還是 MySQL Server 層的 Metadata Lock（MDL），都必須保護「查詢執行期間表結構不會半路變形」這條不變量。因此，哪怕是最普通的快照讀 SELECT（不加任何列鎖），在執行期間都會持有一把最輕量的共享結構鎖——PostgreSQL 稱為 ACCESS SHARE，MySQL 稱為 MDL_SHARED_READ。

這把共享鎖平時與所有的 SELECT、INSERT、UPDATE 完全相容，唯獨與修改表定義所需的最高級排他鎖——PostgreSQL 的 ACCESS EXCLUSIVE 與 MySQL 的 MDL_EXCLUSIVE——正面互斥。更致命的是，鎖管理器的等待佇列為了防止排他鎖「餓死（Starvation）」，一旦有 ALTER TABLE 在佇列中排隊等鎖，後續新抵達的所有普通 SELECT 與 INSERT 都不能插隊，必須排在這句 ALTER 後面：

第二重代價：全表實體重寫（Table Rewrite）vs 原地與瞬間演算法

躲過鎖排隊只是第一關；第二關是這句 DDL 在拿到鎖之後到底要做多少實體 I/O。現代引擎把 DDL 分為三個量級：

  • 瞬間元資料變更（Metadata-only / INSTANT）：只修改系統目錄或資料列版本表，不掃描也不改寫既有資料頁。PostgreSQL 11 起，ADD COLUMN ... DEFAULT <非揮發常數> 會將預設值存在 pg_attribute.attmissingval，讀取舊 Tuple 時由引擎動態補上，億級大表也能在數毫秒內收工（注意：若預設值是 random() 或 gen_random_uuid() 這類每次求值不同的揮發函式，仍會強制重寫全表）。MySQL 8.0.12 引入尾端加欄的 ALGORITHM=INSTANT，8.0.29 起更透過列版本號（最多累積 64 個版本）支援任意位置加減欄位。
  • 原地線上變更（INPLACE + Online DML Log）：需要在背景掃描資料頁（例如建立次級索引），但不建立整張新表；引擎在掃描期間將併發的業務 INSERT/UPDATE/DELETE 暫存在記憶體變更日誌（MySQL innodb_online_alter_log_max_size），掃描尾聲再追平並短暫升級排他鎖完成切換。
  • 全表實體重寫（Table Rewrite / COPY）：例如將主鍵從 INT 改為 BIGINT，每一列的實體 byte 佈局都改變，資料庫必須配置全新檔案把數億列逐一轉型重寫並重建所有索引——磁碟空間瞬間翻倍，且在原生 ALTER 下會長時間鎖死寫入（PostgreSQL 甚至全程握緊 ACCESS EXCLUSIVE 連讀一起封死）。

陷阱外層交易包裹多句 DDL 會把短鎖拖成長鎖

PostgreSQL 支援交易式 DDL（Transactional DDL）。許多 ORM Migration 框架預設把「瞬間加欄位」與「耗時資料轉換」包進同一個 BEGIN ... COMMIT 區塊——一旦第一句取得 ACCESS EXCLUSIVE，這把最高級排他鎖會一路握到整個交易 COMMIT 才釋放！在生產環境中，需要排他鎖的 Catalog 變更必須拆成獨立的極短交易單獨提交。

一句話答法線上 DDL 有兩道生死線：進場時怕慢查詢卡住排他鎖引發 FIFO 佇列雪崩，進場後怕觸發全表實體重寫；前者靠鎖逾時快速放棄，後者靠瞬間元資料演算法、雙階段驗證或影子表繞開。
02

資料庫原生防護原語：lock_timeout、CONCURRENTLY 與 NOT VALID

在不引入外部工具的前提下，把排他鎖持有時間壓到毫秒級、把全表掃描降級為不擋讀寫的背景驗證。

在搬出沉重的外部遷移框架之前，現代關聯式資料庫其實內建了三把極其實用的安全手術刀。只要掌握它們的運作邊界，八成以上的日常加欄、建索引與補約束都能在毫秒級鎖視窗內安全落地。

第一道防線：lock_timeout 快敗重試迴圈（絕不裸跑 DDL）

既然第 1 節的雪崩源自「ALTER 卡在鎖佇列裡死等慢查詢」，最直接的解法就是嚴禁 DDL 在佇列裡久留。切記區分 statement_timeout（限制整句 SQL 總執行時間）與 lock_timeout（專管等鎖排隊時間）：我們只希望「搶不到鎖時在 1～2 秒內立刻放棄讓路」，若搶到鎖開始安全做事就不該誤殺。

-- PostgreSQL：外層由腳本以指數退避重試 5~10 次，每次只允許排隊 1.5 秒
BEGIN;
  SET LOCAL lock_timeout = '1500ms';
  ALTER TABLE orders ADD COLUMN phone_e164 VARCHAR(32);
COMMIT;

-- MySQL 8.0：鎖等待上限設為 2 秒，並強制斷言必須走 INSTANT 演算法
SET SESSION lock_wait_timeout = 2;
ALTER TABLE orders ADD COLUMN phone_e164 VARCHAR(32), ALGORITHM=INSTANT;

一旦線上恰巧有慢查詢佔著共享鎖，ALTER 會在 1.5 秒後主動拋出鎖逾時錯誤退出佇列，積壓在它後方的業務請求瞬間恢復暢通；部署腳本休息數秒後再次嘗試，直到逮到沒有長查詢的空檔完成毫秒級寫入。寧可讓發佈流水線重試十次，也絕不讓線上請求陪葬排隊三秒。

第二道防線：CREATE INDEX CONCURRENTLY 的兩階段追趕

在億級大表建立索引必然要讀取並排序全表資料。傳統 CREATE INDEX 持有 SHARE 鎖，掃描半小時就封鎖寫入半小時；加上 CONCURRENTLY 後，PostgreSQL 改拿與普通讀寫完全相容的 SHARE UPDATE EXCLUSIVE（僅與其他 DDL 或 VACUUM FULL 互斥），拆成三個內部交易分兩趟掃描完成：

sequenceDiagram
    participant D as DDL 工作階段
    participant C as 系統目錄
    participant W as 線上寫入交易
    participant H as 資料表與索引
    D->>C: 登記 INVALID 索引
    Note over C,W: 等待舊寫入提交
    W->>H: 新寫入同步維護新索引
    D->>H: 第一趟基準快照掃描
    Note over D,W: 等待期間開啟的交易結束
    D->>H: 第二趟掃描補齊遺漏列
    D->>C: 標記索引 VALID 可用

CONCURRENTLY 不必鎖寫入的秘密：先讓新來的寫入主動雙寫新索引（HOT 鏈與狀態位同步），再靠第二趟快照掃描把「第一趟掃描前就已啟動、尚未提交」的那批邊界交易補齊。

陷阱INVALID 幽靈索引殘骸與交易限制

CREATE INDEX CONCURRENTLY 有兩條硬鐵律：第一，因為它內部必須自己分段提交多筆交易以推進快照，絕對不能包在 BEGIN ... COMMIT 區塊內執行（多數 ORM Migration 需顯式宣告關閉外層交易，如 Rails 的 disable_ddl_transaction! 或 Flyway 的 non-transactional 設定）。第二，若建唯一索引時撞上重複資料、或中途遭遇死鎖與斷線，系統目錄會留下一顆標記為 INVALID 的半成品索引——查詢最佳化器完全不會用它加速讀取，但每一筆線上 INSERT / UPDATE 卻仍被迫持續寫入它！上線腳本失敗後務必巡檢 pg_index.indisvalid = false，並以 DROP INDEX CONCURRENTLY 清除（PostgreSQL 12 起亦可用 REINDEX INDEX CONCURRENTLY 原地修復）。

第三道防線：NOT VALID 兩段式約束與免鎖轉正 NOT NULL

替大表補上外鍵（Foreign Key）或非空約束（NOT NULL）是另一個高頻踩雷點：直接執行 ADD CONSTRAINT ... FOREIGN KEY 會在子表與父表同時掛鎖並掃描全表；直接執行 ALTER COLUMN ... SET NOT NULL 則會握著最高級 ACCESS EXCLUSIVE 掃過每一頁確認沒有空值。

正確工程手法是把「攔截未來新髒資料」與「驗證歷史存量資料」徹底拆開：

-- 步驟 1（毫秒級短鎖）：掛上 NOT VALID 檢查約束，新寫入立即受檢，但不掃描歷史舊列
SET lock_timeout = '1500ms';
ALTER TABLE orders
  ADD CONSTRAINT chk_orders_phone_nn CHECK (phone_e164 IS NOT NULL) NOT VALID;

-- 步驟 2（不擋讀寫）：只拿 SHARE UPDATE EXCLUSIVE 慢慢掃完全表，將約束標記為 VALID
ALTER TABLE orders VALIDATE CONSTRAINT chk_orders_phone_nn;

-- 步驟 3（PostgreSQL 12+ 毫秒級免重掃）：引擎見 chk_orders_phone_nn 已驗證通過，
-- 直接證明全表無 NULL，跳過全表掃描瞬間轉正為欄位級 NOT NULL，隨後卸除臨時約束
SET lock_timeout = '1500ms';
ALTER TABLE orders ALTER COLUMN phone_e164 SET NOT NULL;
ALTER TABLE orders DROP CONSTRAINT chk_orders_phone_nn;
一句話答法原生安全 DDL 的三板斧：所有排他鎖操作必掛 lock_timeout 退避重試，建索引用 CONCURRENTLY 並監控 INVALID 殘骸，加外鍵或 NOT NULL 一律先掛 NOT VALID 攔新寫入、再用低階鎖 VALIDATE 驗舊資料。
03

破壞性變更與雙版本並存：Expand / Contract 實戰

引擎層的不鎖表救不了應用層的 SQL 報錯——拆解欄位改名、拆分與非空約束的相容演進順序。

許多團隊學完 ALGORITHM=INSTANT 後，興沖沖地在線上執行 ALTER TABLE users RENAME COLUMN phone TO phone_e164——資料庫確實只花 3 毫秒就改完了，但下一秒監控警報全面炸裂：線上正在運行的數十台舊版應用程式實例（v1）發出的每一條 SELECT phone 與 INSERT INTO users (phone) 全部拋出 Unknown column 'phone'！

部署與發佈策略篇從流量調度視角指出：滾動更新與金絲雀發佈期間，線上必然同時存在 v1 與 v2 兩代程式碼共用同一座資料庫。落實到資料庫 Schema 與 SQL 契約層面，任何「改名、拆分欄位、合併欄位、改變資料語意或收緊約束」的破壞性變更，都必須拆解成向後與向前雙向相容的多階段 Expand / Contract 序列，且藏有三個極易在面試與實戰漏掉的資料庫細節：

  • 新增欄位期（Expand）嚴禁直接掛無預設值的 NOT NULL：新欄位剛加進去時，v1 完全不知道它的存在；若直接標記 NOT NULL 且無 DEFAULT，v1 的每一筆 INSERT 都會因違反非空約束當場失敗。
  • 切讀停寫期（Cutover）的「舊欄 NOT NULL 反咬陷阱」：假設舊欄位 phone 原本就帶有 NOT NULL 約束。當演進走到後期、新版程式 v3 準備「停止雙寫舊欄、只寫新欄 phone_e164」時，如果忘了先解除舊欄 phone 的 NOT NULL 約束，v3 一上線就會因為沒填 phone 而全部寫入失敗！
  • ORM 欄位快取與 SELECT * 防護：部分框架會在進程啟動時讀取系統表快取 Schema，若未宣告忽略即將廢棄的舊欄（如 Rails ignored_columns），直接執行 DROP COLUMN 仍會讓執行中的新版實例崩潰。MySQL 8.0.23 起可先下毫秒級的 ALTER TABLE ... ALTER COLUMN phone SET INVISIBLE 隱藏欄位觀察數日，確認零查詢引用後再真正刪除。

雙寫（Dual-Write）該寫在應用層還是資料庫 Trigger？

在過渡期讓新舊欄位保持同步有兩種經典實作，兩者在「版本退場耦合」與「資料庫負載」上恰成互補：

方案 A · 應用層雙寫（Application Dual-Write）
由新版程式 v2 同時寫入 old_col 與 new_col
  • 優點：轉換邏輯（如電話國碼正規化）可用熟悉的應用語言撰寫並覆蓋完整單元測試；不消耗資料庫 CPU 解析觸發器。
  • 硬約束：只要線上還有任何一台 v1 實例存活（例如 Canary 僅放量 20%），v1 寫入的列其新欄仍是 NULL；因此最終一輪收尾 Backfill 必須在 v1 100% 下線後才能封口。
方案 B · 資料庫觸發器雙向鏡像（DB Trigger Sync）
BEFORE INSERT / UPDATE 自動互補新舊欄位
  • 優點：在單筆交易內由引擎保證原子同步——哪怕 v1 只寫舊欄、或回滾後 v1 接手，Trigger 都會自動補齊另一欄，Backfill 可隨時開始且不會產生新空洞。
  • 代價：每筆寫入額外承受 Trigger 解譯開銷，複雜字串或跨表邏輯難以維護，且容易被開發者遺忘在資料庫內。

選擇準則：欄位轉換邏輯複雜或寫入極高頻時優先走「應用層雙寫＋等 v1 全退場後封口回填」；多服務共用同一張表、難以同步升級所有寫入端時，用輕量 BEFORE Trigger 兜底最穩妥。

04

億級大表 Backfill：主鍵游標分批與動態節流

把單筆毀滅性大交易拆成可觀測、可剎車的短交易微批次，守住 MVCC 垃圾回收與從庫複寫延遲預算。

當新欄位掛好、雙寫程式碼也全量上線後，接下來要把資料表裡既有的數千萬到數億筆歷史舊資料補齊（Backfill）。此時若直接執行一句看似無害的 UPDATE orders SET phone_e164 = ... WHERE phone_e164 IS NULL;，會在四個維度同時引爆生產事故：

  • 列鎖覆蓋面失控：單筆長交易一路累積數千萬把排他列鎖直到提交才釋放，線上正常的訂單更新高機率撞鎖超時或形成環狀死鎖（見資料庫鎖與死鎖篇）。
  • MVCC 版本膨脹與 Undo 塞爆：PostgreSQL 的每次 UPDATE 都會產生新 Tuple 並留下舊 Dead Tuple，長交易不提交會卡住全域最舊快照，令 AUTOVACUUM 無法清理垃圾；InnoDB 則會撐爆 Undo Log 拖垮快照讀性能（見交易隔離級別與 MVCC篇）。
  • 主從複寫延遲（Replication Lag）尖峰：單筆巨型交易在提交瞬間傾倒數十 GB 的 WAL 或 Binlog，從庫回放執行緒被長交易獨佔，讀寫分離從庫瞬間落後數百秒（見資料複製基礎篇）。
  • 崩潰回滾災難：跑到第 99% 因逾時或 OOM 中斷時，資料庫必須逐列做 Undo Rollback，回滾耗費的磁碟 I/O 往往比正向寫入更久。

黃金範式：主鍵區間切批（Keyset Bounding）＋ 閉迴路節流

工程上標準的 Backfill Worker 絕不使用 LIMIT ... OFFSET（深分頁會重掃前面數千萬筆索引，總複雜度退化為 O(N²)），而是沿著叢集主鍵（Clustered Primary Key）每次切一段固定寬度的 ID 區間獨立提交：

-- 每次推進固定主鍵區間 (cursor, cursor + batch_size]，每批獨立交易提交
UPDATE orders
SET    phone_e164 = CONCAT('+886', SUBSTRING(phone, 2))
WHERE  id > :cursor
  AND  id <= :cursor + :batch_size
  AND  phone_e164 IS NULL;
關鍵為什麼用 id <= :cursor + :batch_size 封頂，而不是 WHERE col IS NULL LIMIT 2000？

假設資料表中間有一段連續兩千萬筆資料早已由雙寫填好非空值，而 phone_e164 上又還沒有索引。若寫成 WHERE id > :cursor AND phone_e164 IS NULL ORDER BY id LIMIT 2000，資料庫為了湊滿 2,000 筆空值，會在單一交易內一口氣掃過兩千萬個主鍵頁，瞬間退化成慢查詢！用主鍵上下界把掃描範圍硬鎖在 batch_size 個 ID 內，哪怕這批只有 0 筆需要更新，單批 I/O 上限也永遠可預測。

閉迴路節流管線：Worker 每跑完幾批就讀取從庫複寫延遲與主庫 Threads_running，一旦逼近警戒水位立即拉長休眠或完全暫停，把 I/O 優先權讓給線上業務。

設總列數為 N、單批大小為 B、單批資料庫執行耗時為 t_exec、批次間固定休眠為 t_sleep，且從庫最大回放速率為 C_rep（列／秒）、線上業務自身寫入速率為 W_app，則有效推進吞吐率 R_bf 與總耗時需同時滿足：

R_bf = B / (t_exec + t_sleep)   &   W_app + R_bf < C_rep

只要 W_app + R_bf > C_rep，超出從庫回放能力的差額就會逐秒累積成複寫延遲峰值；此時把 B 調小（壓低單批鎖持有毫秒數）並拉大 t_sleep，就是用「背景總遷移時長（數十分鐘至數小時）」換取「線上 P99 零抖動」。

影子表線上遷移工具：pt-online-schema-change vs gh-ost

當全表重寫無可避免時，如何靠「背景分批拷貝＋增量變更追趕＋原子換表」達成近乎零感知的線上重構。

當遇到「主鍵由 INT 升 BIGINT」、「調整叢集索引順序」、「轉移字元集 utf8mb4」或「回收數百 GB 刪除碎片」這類物理上無可避免必須重寫整張表的手術時，即便 MySQL 提供部分 INPLACE 支援，它也存在兩個致命硬傷：第一，引擎全速掃盤無法感知「從庫是不是已經延遲了三十秒」而自動踩剎車；第二，高寫入期間一旦增量緩衝區（innodb_online_alter_log_max_size）被塞滿，耗時兩小時的 DDL 會在最後一刻直接報錯作廢。

為了解決這道難題，業界發展出成熟的影子表（Shadow / Ghost Table）線上遷移架構：不在原表上動刀，而是先建一張套用好新結構的空表（毫秒級完成），接著在背景同時推進「存量分批拷貝」與「增量異動追趕」，等兩張表完全同步後，再用毫秒級的原子 RENAME TABLE 瞬間偷天換日。

兩大流派對決：Trigger 同步觸發（pt-osc）vs Binlog 非同步串流（gh-ost）

Percona 的 pt-online-schema-change 與 GitHub 開源的 gh-ost 走了截然不同的增量擷取路線，這決定了它們在高併發熱表上的生死表現：

核心架構分水嶺：pt-osc 把影子表寫入塞進業務交易本身，尖峰時無法卸載 Trigger 成本；gh-ost 透過 ROW 格式 Binlog 把增量同步徹底移出業務熱路徑，緊急時能做到 100% 靜默暫停。

為什麼 gh-ost 在高併發場景勝出？拆解三個工程細節

  • 真正意義上的「隨時緊急煞車（True Throttling）」：在 pt-osc 下，當主庫 CPU 飆到 95% 時按暫停，只能停下背景拷貝執行緒，原表上的三支 Trigger 依然在每一筆用戶下單時同步執行——想拔掉 Trigger 又得再拿一次排他 MDL_EXCLUSIVE 鎖並宣告遷移作廢。gh-ost 原表完全乾淨，只要停止消費 Binlog 與分批查詢，主庫負荷瞬間歸零，等流量洪峰過去再從斷點 Binlog 位點無縫續傳。
  • 可動態線上調參與預演驗證：gh-ost 內建 Unix Socket 控制介面，執行途中可隨時動態調整 chunk-size 與 max-lag-millis；甚至支援 --test-on-replica，直接在生產從庫完整跑完一次遷移與切換測試再停機校驗資料一致性。
  • 雙連線無縫原子 Cut-over：最後換表那一刻，如何確保「不會在鎖定原表與重命名之間漏掉最後幾筆 Binlog」？gh-ost 利用 MySQL 中 RENAME TABLE 優先權高於一般 DML 的特性：先由連線 A 執行 LOCK TABLES orders WRITE 擋住新寫入，再由連線 B 送出 RENAME TABLE orders TO _orders_del, _orders_gho TO orders（此時連線 B 排在連線 A 之後、但排在所有被擋的業務 DML 之前）；gh-ost 從 Binlog 讀到自己寫入的心跳標記，確認封鎖前最後一筆變更已套進 _orders_gho 後，連線 A 釋放鎖——連線 B 瞬間完成原子換表，業務端只感受到數十毫秒的微小停頓，零資料遺失。

工具沒有絕對通吃：大型網路公司普遍移除實體外鍵約束，因此以 gh-ost 為首選；若遺留系統高度依賴跨表外鍵，則需評估 pt-osc 的 rebuild_constraints 模式或改走應用層分階段遷移。

延伸PostgreSQL 生態系的對應工具：pg_repack 與 pgroll

PostgreSQL 因為具備第 2 節介紹的 CONCURRENTLY、attmissingval 與兩段式約束，日常 DDL 對外部工具的依賴遠低於 MySQL。遇到真正需要重整膨脹表或改實體型別時，社群常用 pg_repack（透過輕量 Trigger 記錄增量至日誌表、背景建新 Heap 後短暫排他鎖交換檔案指標）；而新一代工具如 pgroll 則自動化管理多版本 Schema Views，讓新舊版應用程式連上不同 search_path 視圖各自讀寫，省去手工維護雙寫程式碼的負擔。

一句話答法影子表工具把「鎖表重寫」轉化為「空表改結構＋背景拷貝＋增量追趕＋毫秒級原子 RENAME」；gh-ost 改讀 Binlog 拔除原表 Trigger，徹底解決了高併發下觸發器拖垮業務交易與無法真暫停的痛點。

    生產環境變更前後標準防禦清單（Pre-flight & Post-flight Checklist）

    上線前
    清查長交易與孤兒連線：執行前先查 pg_stat_activity（找出 idle in transaction 與長報表）或 MySQL information_schema.innodb_trx，並確認磁碟剩餘空間大於目標表總容量的 1.5～2.2 倍（含索引與暫存排序檔）。
    上線中
    強制雙重保險絲：每一條需要排他鎖的 DDL 都必須搭配 lock_timeout（1～3 秒）與顯式演算法斷言（如 ALGORITHM=INSTANT）；所有背景 Backfill 與影子表工具都必須綁定從庫複寫延遲上限（如 Lag > 2 秒自動暫停）。
    上線後
    巡檢半成品殘骸與統計資訊：確認沒有遺留 INVALID 索引、未卸除的過渡期 Trigger 或未刪除的影子舊表（如 _orders_old 佔滿磁碟）；大面積資料回填後主動執行 ANALYZE 更新查詢最佳化器統計資訊（避免查詢計畫走歪，見查詢計畫與 EXPLAIN篇）。

    面試高頻追問 FAQ

    Q1 · PostgreSQL 核心訂單表的 INT 主鍵即將突破 21 億上限，如何在不停機前提下升級為 BIGINT？ ▸

    絕對不能直接下 ALTER TABLE orders ALTER COLUMN id TYPE BIGINT，這會握著 ACCESS EXCLUSIVE 重寫數百 GB 的 Heap 與所有索引。標準零停機解法分五步：(1) Expand：毫秒級新增可空欄位 id_big BIGINT，並掛一支輕量 BEFORE INSERT Trigger 讓新寫入自動執行 NEW.id_big := NEW.id；(2) Backfill：用主鍵游標分批將歷史列的 id 填進 id_big；(3) 平行建唯一索引與驗證非空：執行 CREATE UNIQUE INDEX CONCURRENTLY idx_orders_id_big ON orders(id_big)，並以 CHECK (id_big IS NOT NULL) NOT VALID + VALIDATE CONSTRAINT 完成非空證明；(4) 毫秒級換主鍵：在 SET LOCAL lock_timeout = '1500ms' 保護的單一短交易內，將欄位改名對調並使用 ALTER TABLE orders DROP CONSTRAINT orders_pkey, ADD CONSTRAINT orders_pkey PRIMARY KEY USING INDEX idx_orders_id_big——直接把剛建好的唯一索引升級為主鍵，完全跳過全表重掃；(5) 將 Sequence 升為 BIGINT，待舊版程式退場後清理舊 INT 欄位。

    Q2 · gh-ost 最後一步做 RENAME TABLE 切換時，若剛好有一條慢查詢在讀原表，會不會一樣引發鎖佇列雪崩？ ▸

    如果無防護地死等，確實會！因為 RENAME TABLE 依然需要取得 MDL_EXCLUSIVE。gh-ost 之所以安全，是因為它內建了嚴格的 --cut-over-lock-timeout-seconds（預設僅 3 秒）與最大重試上限：一旦在切換瞬間被長查詢擋住超過 3 秒，gh-ost 會主動放棄該次 Cut-over 連線並釋放鎖請求，讓後方業務查詢立刻通行，自己則退回背景繼續追趕這幾秒產生的幾十筆 Binlog，等幾秒後再次嘗試切換，直到順利逮到無長查詢的毫秒空檔。

    Q3 · 既然我們有主從架構，直接「先在從庫跑完 DDL、再做主從切換（Rolling Replica Upgrade）」不就不用影子表了嗎？ ▸

    從庫輪流變更確實能把重寫 I/O 隔離在離線從庫上，在超大規模叢集中常與影子表搭配使用，但它有三個嚴格限制：(1) 主從複寫格式相容性：在 ROW 格式 Binlog 下，主庫（舊結構）與從庫（新結構）只有在尾端加減欄等少數情況下能跨結構回放，若在中間插欄或修改不二進位相容的型別，複寫執行緒會直接斷裂；(2) 主從切換本身是一次基礎設施級有感事件，切換瞬間連線重連、Buffer Pool 冷快取預熱都會造成延遲抖動；(3) 應用層契約問題仍在：切換那一秒線上仍有新舊程式並存，破壞性改名或刪欄一樣必須遵循 Expand / Contract。

    Q4 · MySQL 8.0 的 ALGORITHM=INSTANT 可以無限次對同一張表加減欄位嗎？ ▸

    不行！MySQL 8.0.29+ 的任意位置加減欄位靠的是在系統表維護 TOTAL_ROW_VERSIONS 版本號（上限為 64 個版本）。每執行一次 INSTANT 加欄或刪欄就會消耗一個版本號；一旦累積滿 64 次，第 65 次 DDL 就會被迫退回重建整張表（可查 information_schema.innodb_tables 監控剩餘額度）。此外，含有 FULLTEXT 全文索引或使用 ROW_FORMAT=COMPRESSED 的資料表亦不支援 INSTANT。

    一句話答法零停機 Schema 變更的本質是把「一次性的鎖表＋契約突變」拆解為「受 lock_timeout 保護的毫秒級元資料變更 ＋ 節流分批的背景資料追趕 ＋ 雙向相容的多階段應用發佈」。
