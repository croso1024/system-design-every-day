01

總覽與定位：為何時序資料值得專屬儲存

從只增不改、依時間查詢、整塊淘汰三個負載特徵，看透時序資料庫與通用關聯式資料庫的結構分歧。

幾乎所有系統裡都有一類資料跟訂單或會員資料長得完全不同：伺服器每秒吐出的 CPU 使用率、十萬台 IoT 感測器每 10 秒上報的溫度與電流、交易所每毫秒成交的逐筆行情、或是 API 閘道記錄的延遲指標。把它們直接塞進傳統關聯式資料庫（RDBMS）的單張 B-Tree 資料表，初期看來一切正常，直到寫入量衝上每秒十萬點、保留期拉長到三個月，磁碟 I/O、索引體積與清理任務就會同時崩潰。

時序資料庫（Time-series Database, TSDB）之所以獨立成為一種儲存類別，並不是因為它發明了全新的數學，而是因為它把三個在一般 OLTP 場景不敢做的假設寫進了底層儲存結構裡：

  • 99% 以上是只增不改（Append-Only）：新資料點幾乎總是附帶當前時間戳一路往後追加，極少隨機回頭 UPDATE 單一歷史紀錄。
  • 讀取強依賴時間區間（Time-Range Locality）：查詢幾乎永遠帶上 WHERE ts BETWEEN t1 AND t2，而且絕大多數請求集中在「最近幾小時到幾天」的熱區，並伴隨時間窗口聚合（例如每 5 分鐘取平均或 P99）。
  • 淘汰是整批按時間過期（Bulk Expiry）：資料通常依合規或成本策略整段保留（如 30 天原始精度、1 年彙總），不會隨機刪除某幾天零散的列。

通用 B-Tree RDBMS（未針對時序特化）

  • 寫入放大：複合索引（如 (device_id, ts)）讓每筆寫入隨機散落到不同葉節點，頻繁觸發 Page Split 與髒頁回寫。
  • 儲存膨脹：以列（Row）為單位存 64-bit 時間戳與浮點數，每列外加 Tuple Header 與 MVCC 版本欄位，一筆點常吃掉 40–80 bytes。
  • 刪除風暴：用 DELETE WHERE ts < ... 清理過期資料會寫爆 WAL、產生大量死元組（Dead Tuples）並引發漫長 VACUUM。

專屬 TSDB 儲存引擎

  • 循序寫入：先寫 WAL 與記憶體 Head Block，滿窗後依時間序列排好序一次 Flush 成不可變的欄式檔案（Chunk / TSM）。
  • 極致壓縮：同條序列相鄰點的時間間隔幾乎固定、數值緩慢變化，套用 Delta-of-Delta 與 XOR 可壓到約 1.37–2 bytes / 點。
  • O(1) 淘汰：資料物理上按時間切塊，過期直接 DROP 整個分區檔案，幾乎零寫入放大、無碎片。

核心差異不在查詢語法，而在物理佈局：RDBMS 為「隨機單筆 CRUD」優化，TSDB 把「時間順序 + 不可變分塊」換成十倍以上的寫入吞吐與壓縮率。

關鍵不要為了「有 timestamp 欄位」就引入 TSDB

訂單表、審計日誌也有 created_at，但它們往往需要與商品、使用者表做 ACID 交易與複雜 JOIN，且寫入量遠低於感測器與監控指標。唯有當「高頻追加、時間窗聚合、定期批次淘汰、極致壓縮成本」成為瓶頸時，專屬 TSDB 才展現價值；具體的選型分界會在第 7 節拆解。

一句話答法TSDB 用「只增不改、按時間分塊、同序列欄式壓縮」三個特化假設，消除了傳統 B-Tree 在高頻時序寫入下的隨機 I/O、空間膨脹與刪除碎片問題。
02

時序資料模型：Measurement、Tag、Field 與 Series

拆解一筆時序資料點的四個核心欄位，以及為什麼「放進 Tag 還是 Field」會直接決定系統會不會 OOM。

無論底層實作是 InfluxDB、Prometheus、TimescaleDB 還是 Amazon Timestream，時序資料在邏輯上都圍繞同一個四元結構展開。以下是一筆常見的 Influx Line Protocol 寫入範例：

factory_sensor,region=tw-north,device_id=dev-042,line=A temp=23.5,humidity=61.2,voltage=3.31 1700000060000000000
1. Measurement（量測指標 / 資料表）例：factory_sensor
描述「量測的是哪一類現象」（如 cpu_usage、factory_sensor），概念上最接近關聯式資料庫的資料表名或寬欄儲存的 Table。
2. Tag Set（標籤鍵值對 — 建立倒排索引）例：region=tw-north, device_id=dev-042, line=A
描述資料點「從哪裡來」的維度中繼資料（字串型別）。會被放進倒排索引（Inverted Index），用來做 WHERE 過濾與 GROUP BY 分群。
3. Series Key（序列鍵 = Measurement + 排序後的 Tag Set）唯一決定一條時間序列
同一組 Measurement + Tag Set 定義出一條獨立的時間線（Series）。儲存引擎會把同一個 Series 的資料點排在一起壓縮，因此 Series 總數直接決定索引與記憶體開銷。
4. Timestamp + Field Set（時間戳 ＋ 觀測數值 — 不建索引）例：ts=1700000060, temp=23.5, humidity=61.2
Field 是真正隨時間變化的量測值（浮點、整數、布林），不建立倒排索引，因此不會增加 Series 數量，但也不適合拿來做高速等值過濾（WHERE temp = 23.5 需要掃描區間）。

時序模型的關鍵分水嶺在「Tag vs Field」：Measurement 加上整組 Tag 的笛卡兒積決定 Series 總數，而每條 Series 內部只剩純粹按時間遞增的 (Timestamp, Field) 陣列。

這個分層其實和「寬欄儲存（Wide-Column Store）篇」裡談的 Partition Key 與 Clustering Key 模型高度呼應：在寬欄語境下，(Series Key, Time Bucket) 扮演定位磁碟分區的 Partition Key，而 Timestamp 則是分區內嚴格排序的 Clustering Key，確保讀取同一台裝置一段時間的紀錄時只需要一次循序磁碟掃描。至於監控領域中 Counter、Gauge、Histogram 等指標型別與觀測面語意，則由「可觀測性基礎（Observability Fundamentals）篇」展開，本篇專注於底層儲存與索引如何承載這些序列。

比較面向 Tag（維度標籤） Field（量測數值）
資料型別 字串（String） Float64 / Int64 / Boolean / String
是否建立索引 是（倒排索引，常駐記憶體或快取） 否（僅按 Series 與時間循序掃描）
對 Series 基數的影響 每個新值組合都會誕生一條新 Series 零影響（只增加既有 Series 內的點數）
常見範例 region、env、host、sensor_type cpu_pct、temp_c、latency_ms、err_msg

設計 Schema 時的黃金檢核：會拿來 GROUP BY 且可能取值有限的維度放 Tag；連續數值、高變動 ID 或非結構化字串一律放 Field。

陷阱把 request_id、user_id 或 trace_id 塞進 Tag

只要將任何無上限增長的識別碼放進 Tag，每筆請求就會在資料庫裡永久（至少在該時間分區過期前）創造一條只有 1 個資料點的孤兒 Series。這不只讓倒排索引在幾小時內吃光記憶體引發 OOM，還會讓壓縮演算法完全失效——一條只有 1 個點的序列無從計算相鄰時間差與 XOR，空間瞬間暴增 10 倍以上。

一句話答法Measurement + Tag Set 唯一確定一條 Series 並進入倒排索引，Field 承載不建索引的數值；把高基數欄位誤放 Tag 會同時摧毀索引記憶體與序列壓縮率。
03

儲存引擎與時間分區：Chunk、LSM 與整塊淘汰

寫入路徑如何從 WAL 與記憶體區塊封裝成不可變的時間分區 Chunk，讓資料過期從掃表刪除變成 O(1) 卸載。

為了扛住每秒數十萬到數百萬筆點的寫入，主流時序資料庫幾乎都採用 LSM-Tree（Log-Structured Merge-Tree）的時序特化變體，例如 InfluxDB 的 TSM（Time-Structured Merge Tree）、Prometheus 的 TSDB Block，或是 TimescaleDB 的 Hypertable Chunk。它們的核心理念一致：把隨機寫入轉化為循序追加，並且在物理磁碟上以固定時間窗口（例如每 2 小時、1 天或 7 天）切成各自獨立的 Chunk。

flowchart LR
    W[寫入請求] --> WAL[WAL 追加日誌]
    WAL --> HEAD[記憶體 Head Block]
    HEAD -->|滿窗 / 達容量| CHUNK[不可變 Time Chunk]
    CHUNK -->|背景合併| COMP[壓實 TSM / Parquet]
    COMP -->|超過保留期| DROP[O(1) 卸載檔案]

寫入先落 WAL 保久再進記憶體 Head Block 緩衝；一旦超過時間窗口就整塊凍結為不可變檔案，過期時直接移除整份檔案而非逐列 DELETE。

為什麼時間分區 Chunk 是壓縮與淘汰的雙重前提

在單一記憶體 Head Block 裡，資料點會先依 Series ID 分組暫存；當這個時間窗（例如 2 小時）結束，儲存引擎把每條 Series 過去 2 小時的點各自連續排放，分欄存成「Timestamp 陣列」與「Field 陣列」，再分別做時間戳與數值壓縮，最後連同該區塊的索引一併寫成唯讀不可變檔案（Immutable Block / Chunk）。

按時間切塊讓查詢引擎可用 Chunk 的 [min_ts, max_ts] 做 Partition Pruning（直接跳過不重疊的區塊），同時讓過期清理退化為移除目錄與檔案。

Chunk 時間寬度該切多寬？這是實務調校的第一道折衷（例如 TimescaleDB 的 chunk_time_interval 或 InfluxDB 的 Shard Group Duration）：

  • 切太寬（如一個 Chunk 存 30 天）：活躍索引膨脹超過 RAM，寫入時 B-Tree 或倒排索引發生大量 Page Fault；而且過期淘汰時必須等整整 30 天後才能一起釋放空間。
  • 切太窄（如每 10 分鐘切一塊）：掃描一週資料要開啟上千個檔案與索引，Query Planner 與檔案描述符開銷暴增，且每塊太短導致同序列點數不足、壓縮率下滑。
  • 經驗法則：讓最近 1 個活躍 Chunk（含索引）的體積維持在可用記憶體的 15%–25% 以內；高吞吐場景常切 2 小時到 1 天，中低吞吐切 1 天到 7 天。
關鍵亂序與遲到寫入（Out-of-Order Writes）會打破不可變假設

如果一台離線三天的邊緣裝置突然重連，把三天前的歷史數據一口氣灌進來，這些點的時間戳會落在早已封存壓縮的歷史 Chunk 裡。引擎必須先把它們收進專門的 Out-of-Order 緩衝區，事後再觸發昂貴的 Re-compaction 解壓、重排、重新壓縮整塊檔案。因此像 Prometheus 預設會設定 out_of_order_time_window 上限，超出就直接拒絕或分流；上游裝置端如何做 Store-and-forward 與限速補傳，請見「IoT Telemetry 寫入管線與離線補傳篇」。

一句話答法TSDB 以 WAL ＋ 記憶體 Head Block 吸收高併發寫入，按固定時間窗封存成不可變 Chunk，把查詢裁剪與資料過期都壓成區塊層級的操作。
04

壓縮演算法：Delta-of-Delta 與浮點數 XOR

深入 Gorilla 論文的位元級壓縮規則，動手拆解時間戳與浮點數如何從 128 bits 壓縮到十幾個 bit。

未經壓縮的一筆時序資料點由一個 64-bit 時間戳與一個 64-bit IEEE 754 浮點數組成，共佔 128 bits（16 bytes）。Meta（Facebook）在 2015 年發表的 Gorilla 論文證明：只要把同一條 Series 的點連續排在一起，針對時間戳與數值各自利用相鄰相關性，就能把實際儲存成本壓低到平均約 1.37 bytes / 點——這套位元編碼後來成為 Prometheus、InfluxDB、TimescaleDB 等幾乎所有現代 TSDB 的壓縮基石。

1. 時間戳壓縮：Delta-of-Delta（二階差分）

感測器與監控採集器多半按固定週期上報（例如每 60 秒一次），即使有微小的網路或排程抖動，相鄰兩筆時間差 Δt 也幾乎相等。因此一階差分還留著常數 60，但再取一次二階差分 D 就會趨近於 0：

D = (t[n] - t[n-1]) - (t[n-1] - t[n-2])

Gorilla 依據 D 的大小選擇不同長度的變長位元前綴（類似霍夫曼編碼的固定前綴碼）：

二階差分 D 的範圍 控制前綴 酬載位元數 總共佔用 典型觸發場景
D = 0 0 0 bits 1 bit 完全準時的週期採集（佔真實流量 90% 以上）
-63 ≤ D ≤ 64 10 7 bits 9 bits 輕微 GC 停頓或幾秒內的網路抖動
-255 ≤ D ≤ 256 110 9 bits 12 bits 數分鐘等級的短暫延遲
-2047 ≤ D ≤ 2048 1110 12 bits 16 bits 較大幅度的採樣間隔變動
其餘範圍 1111 32 bits 36 bits 斷線重連或跨度極大的異常跳躍

當採樣節奏穩定時，原本 64 bits 的時間戳被壓縮到只剩 1 bit；但只要時間戳帶入無意義的毫秒隨機雜訊，D 就會掉出 0 而多花 8–15 bits。

2. 數值壓縮：IEEE 754 Float64 XOR

相鄰兩筆量測值（例如溫度 23.5 與 23.6）轉成 64-bit IEEE 754 二進位後，符號位、11-bit 指數位與高段尾數位往往完全相同。把它們做按位元互斥或（XOR）後，頭尾會出現大量連續的 0，中間只剩一小段真正改變的有意義位元（Meaningful Bits）：

XOR[n] = bits64(v[n]) ^ bits64(v[n-1])
  • XOR = 0（數值沒變）：只寫 1 個控制位元 0（總計 1 bit）。
  • XOR ≠ 0 且前導零與尾隨零都落進前一次的視窗內：寫 2 個控制位元 10，接著只輸出前一個視窗寬度的有意義位元，省去重寫視窗頭尾資訊。
  • XOR ≠ 0 且超出既有視窗：寫 11 ＋ 5 bits（前導零數，上限 31）＋ 6 bits（有意義位元長度減 1）＋ 實際有意義位元。

即使肉眼看起來只差 0.00001，二進位 IEEE 754 的低位尾數卻可能全面翻轉，導致 XOR 的尾隨零瞬間歸零、每筆數值退化成 50–64 bits。實務上在感測器端或寫入管線中，依物理儀器真實精度做四捨五入（或把時間戳對齊到合理粒度），常常就能在不損失業務精度的前提下讓硬碟成本直接腰斬。

一句話答法Gorilla 靠「時間戳二階差分」把規律採樣壓成 1 bit，再靠「浮點數 XOR 前導/尾隨零視窗」消去緩變數值的重複位元；前提是同序列連續存放且避免無意義的時間抖動與尾數噪音。
05

查詢模式、降採樣與保留策略

時間窗口聚合、Continuous Aggregates 與熱溫冷分層如何同時滿足「秒級近況」與「年度趨勢」查詢。

把資料高效寫進去只是上半場，下半場的挑戰在於「查詢跨越的時間尺度差異極大」。儀表板首頁要看「過去 15 分鐘每秒 CPU」，而容量規劃報表要畫「過去一年每天的溫度趨勢」——兩者差了 35,000 倍 的資料點數。如果拿一年份的秒級原始點現場掃描聚合，單一查詢就能拖垮整座叢集。

1. 降採樣（Downsampling）與預先聚合（Continuous Aggregates）

解法是把「時間精度」和「保留天數」解耦：原始高頻資料只留短期，背景排程（或串流計算）持續將原始資料滾動聚合為較粗粒度的 Rollup Table（例如 1 分鐘、5 分鐘、1 小時桶），並長期保存：

  • 熱層（Hot，例 7–14 天）：保留完整原始精度（如 10 秒級）於本機 NVMe SSD，支撐告警與根因細查。
  • 溫層（Warm，例 30–90 天）：以 5 分鐘為時間桶降採樣，每桶存 min、max、sum、count（外加必要時的直方圖或 P99 Sketch）。
  • 冷層（Cold，例 1–5 年）：以 1 小時或 1 天降採樣後轉存至低成本物件儲存（S3 / GCS 上的 Parquet 檔），供長期趨勢與稽核查詢。

Query Router 依時間跨度自動分流（例如 TimescaleDB 的 Real-Time Continuous Aggregates 或 M3DB / VictoriaMetrics 的 Downsampling Rule），避免長區間報表把熱層 SSD 掃爆。

2. 保留策略（Retention Policy）的執行成本

因為底層已經依時間切成獨立的 Chunk（見第 3 節），保留策略的實作極度單純：背景任務定期檢查哪些 Chunk 的 max_ts 已早於 now - retention_window，直接將整塊檔案從中繼資料摘除並交由作業系統 unlink。相比傳統資料庫逐列刪除所引發的鎖競爭與 I/O 尖峰，時間分區淘汰幾乎不影響線上寫入延遲。

陷阱千萬別對「平均值的平均值」做二次聚合

把每 5 分鐘的 avg 存進 Rollup 表後，若事後想算「1 小時平均」而直接對 12 個 5 分鐘 avg 再取一次 AVG()，只要各桶內的樣本數不均（例如某幾分鐘斷線掉點），結果就會出現數學偏差。正確作法是在 Rollup 表中儲存可加性統計量 sum 與 count，跨桶彙總時一律用 SUM(sum) / SUM(count)；同理，若需要觀測尖峰不能只留平均，必須同時記錄 max 或可合併的 Percentile Sketch（如 t-digest / DDSketch）。

一句話答法用「熱層原始點 ＋ 背景預聚合 Rollup ＋ 整塊 Drop 保留策略」換取近即時細查與跨年趨勢並存，且 Rollup 務必存 sum 與 count 而非裸 avg。
06

高基數陷阱與儲存容量規劃

倒排索引如何隨 Series 數量膨脹，以及在設計初期如何量化索引記憶體、寫入吞吐與分層儲存成本。

在時序資料庫的運維事故裡，第一大殺手不是寫入吞吐量，而是高基數（High Cardinality）。同樣是每秒寫入 10 萬個資料點：「1,000 台裝置每台每秒寫 100 點」與「1,000 萬條短命 Series 每條每 100 秒寫 1 點」對磁碟頻寬需求差不多，但後者往往會直接把資料庫打到 OOM 崩潰。

1. 倒排索引如何隨基數膨脹

為了讓 WHERE region = 'tw-north' AND env = 'prod' 在毫秒內找到所有符合條件的時間線，傳統 TSDB（如 InfluxDB TSM、Prometheus TSDB）在記憶體裡維護一張倒排索引（Inverted Index）：把每個 tag_key=tag_value 映射到一組排序後的 Series ID 集合（常以 Roaring Bitmap 壓縮），同時還有一張 Series Metadata 表維護每條活躍序列的 Head Chunk 緩衝區。

Series 總數 = ∏ (各個 Tag 實際出現的不重複取值組合數)

一旦某個 Tag 帶有高變動性（例如 Kubernetes 頻繁重建的 pod_uid、每次連線不同的 session_id），不只 Series 總數呈乘法放大，還會引發 Series Churn（序列流失）：舊序列不再寫入卻仍佔據該時間分區內的索引條目直到 Chunk 過期，同時新序列源源不絕地強制配置新的記憶體緩衝、增加倒排表交集計算成本與 Compaction 寫入放大。關於監控系統端如何治理指標標籤與排查高基數爆炸，請見「可觀測性基礎（Observability Fundamentals）篇」。

2. 現代欄式架構如何緩解基數上限

新一代架構（如 InfluxDB 3.0 基於 Apache Arrow / DataFusion / Parquet，或 TimescaleDB 的 Columnar Compression）試圖打破傳統記憶體倒排索引的天花板：不再把所有 Tag 組合硬塞進常駐 RAM 的全域 Series Index，而是將資料按時間與少量分區鍵寫成物件儲存上的 Parquet 欄式檔案，靠欄位統計值（Min/Max Zone Map）、Bloom Filter 與向量化掃描在查詢時裁剪資料塊。它的取捨是：高基數上限大幅放寬、冷儲存成本大降，但高併發超低延遲（< 5ms）的即時點查往往不如全記憶體倒排索引。

07

技術選型對照：TimescaleDB、InfluxDB、Timestream 與原生存儲

橫向比較主流時序資料庫的架構取捨，並界定何時只用一般關聯式資料庫加時間分區就已足夠。

市面上的時序儲存方案走出了三條截然不同的架構路線：在成熟關聯式資料庫上加掛時序擴充、從零打造的專屬時序引擎、以及全託管 Serverless 服務。選型的核心不是誰的基準測試跑分最高，而是你需不需要和業務表 JOIN、寫入基數有多高、以及團隊能承受多少維運複雜度。

方案 底層儲存架構 查詢語言與 JOIN 能力 高基數與壓縮特性 最適合的場景
PostgreSQL ＋ 原生時間分區 Declarative Range Partitioning + B-Tree / BRIN 完整 SQL 與 ACID 交易、任意 JOIN 無原生 Gorilla 壓縮；依賴 TOAST / 分區 Drop 中小寫入量（< 5K–10K pts/s）、強關聯業務資料
TimescaleDB PostgreSQL 擴充：Hypertable Chunk + 欄式壓縮（DoD / Gorilla） 完整 PostgreSQL 生態 + Continuous Aggregates 冷 Chunk 轉欄式壓縮可達 90%+；索引受限於 PG B-Tree 需要標準 SQL、與業務表 JOIN、保留 PG 維運工具鏈
InfluxDB（v2 TSM / v3 Parquet） v2：TSM + 倒排索引；v3：Apache Arrow + DataFusion + Parquet InfluxQL / Flux（v2）或 SQL + InfluxQL（v3）；弱跨表 JOIN v2 受限於記憶體基數上限；v3 改用 Parquet 大幅放寬基數 超高吞吐監控與 IoT 指標、純時序分析與低成本物件儲存
Amazon Timestream 全託管 Serverless：Memory Store（熱）自動移轉 Magnetic Store（冷） SQL 子集（專注時間窗與插值函數）；不適合複雜業務 JOIN 免容量規劃、按寫入與掃描量計費；高頻小查詢成本需留意 AWS 生態、不想自管叢集與分層壓實的 IoT／遙測管線

實務選型對照：TimescaleDB 勝在「不離開 PostgreSQL 生態」，InfluxDB 3.0 勝在「物件儲存＋高基數吞吐」，Amazon Timestream 勝在「零維運自動熱冷分層」。

什麼時候「一般關聯式資料庫 ＋ 時間分區」就夠用？

系統設計裡最常見的過度設計之一，就是在只有幾百台裝置、每秒不到一千筆寫入的專案裡多養一座獨立 TSDB 叢集。只要同時滿足下列四個條件，直接用 PostgreSQL 宣告式時間分區（PARTITION BY RANGE (ts)）搭配 BRIN 索引（Block Range Index，體積只有 B-Tree 的不到 1%）與排程 DROP TABLE 分區，往往是最穩、最省成本的解法：

  1. 寫入量在單機可輕鬆吸收的區間：持續寫入低於約 5,000–10,000 rows/s（批次 COPY 或 multi-row INSERT 下甚至更高），尚未觸及磁碟 IOPS 天花板。
  2. 必須與既有業務表做即時 JOIN 或跨表 ACID 交易：例如計費系統要把用量事件直接對齊客戶方案表，跨庫同步反而徒增資料一致性難題。
  3. 查詢與保留規模溫和：原始資料總量在數百 GB 以內，沒有數億條高基數 Series 或極端壓縮（> 90%）的硬性成本壓力。
  4. 團隊精簡：現有備份、監控、權限與災難復原流程全都建在既有關聯式資料庫上，不值得為單一功能承擔第二套資料庫的維運與故障排查風險。
關鍵演進路徑：別一上來就推翻整個資料庫棧

若專案目前已在用 PostgreSQL，最平滑的演進階梯是：單表 ＋ 複合索引 → 原生按天時間分區 ＋ BRIN 索引 → 啟用 TimescaleDB 欄式壓縮與 Continuous Aggregates → 當吞吐或基數跨越單機 / SQL 邊界時，再將純遙測資料拆出至 InfluxDB 3.0、VictoriaMetrics 或 Amazon Timestream。

一句話答法強關聯與中低吞吐先用 PG 時間分區或 TimescaleDB；超高寫入、極致壓縮與高基數分析選 InfluxDB 3.0；追求零維運且深耕 AWS 則選 Amazon Timestream。
08

面試實戰：高頻考題與架構答法

面對「十億筆監控／IoT 資料怎麼存」的追問時，直接切中寫入放大、壓縮、基數與補傳痛點的回答框架。

在 System Design 面試裡，無論題目是「設計百萬台 IoT 裝置監控平台」、「設計分散式指標告警系統」還是「設計高頻行情儲存」，考官幾乎都會沿著下面四個追問驗證你是否真的懂 TSDB 的底層機制：

高頻面試問題 考官真正想聽的關鍵答點
1. 為什麼不直接用 MySQL / PostgreSQL 存十億筆感測器資料？ 點出三個物理瓶頸：(a) 複合 B-Tree 索引在高併發隨機插入時會引發嚴重 Page Split 與寫入放大；(b) 列式儲存缺乏同序列 Delta-of-Delta ＋ XOR 壓縮，空間膨脹 8–10 倍；(c) DELETE WHERE ts < ... 會觸發 WAL 爆量與 VACUUM 碎片。同時補一句「若寫入量低於數千 pts/s 且要 JOIN 業務表，PG 時間分區 ＋ BRIN 就夠用」，展現不盲目炫技的工程判斷。
2. 裝置數十萬台，Schema 設計怎麼避免系統 OOM？ 明確切分 Tag（低基數維度，進倒排索引） 與 Field（高變動數值／高基數 ID，不建索引）。提醒面試官估算 Series 總數 = 各 Tag 組合乘積，禁止把 request_id、session_id 或無限成長的錯誤訊息放進 Tag；若業務確需高基數維度查詢，改採 Parquet 欄式架構（如 InfluxDB 3.0）或把追蹤事件分流至 Log / Trace 系統。
3. 產品要同時看「過去 1 小時秒級」與「過去 1 年趨勢」，怎麼兼顧延遲與成本？ 提出分層保留 ＋ Continuous Aggregates：熱層 NVMe 留 7–14 天原始點供秒級細查；背景排程滾動產生 5 分鐘與 1 小時 Rollup 存進溫冷層（物件儲存 Parquet）；關鍵細節是 Rollup 必須存 sum、count、min、max（需要百分位數就存 Sketch），絕不對 avg 做二次平均。
4. 離線裝置三天後同時重連補傳歷史數據，儲存層會發生什麼事？ 指出亂序寫入（Out-of-Order Writes）會撞進已封存的歷史不可變 Chunk，引發昂貴的 Re-compaction 與壓縮率下降，同時造成瞬時寫入尖峰。儲存層應設定 out_of_order_time_window 邊界並把超窗資料導入獨立補錄路徑（Backfill Pipeline），上游則靠限速與抖動平滑流量（詳見「IoT Telemetry 寫入管線與離線補傳篇」）。

面試回答 TSDB 題目時，把「寫入路徑 → 壓縮模型 → 基數上限 → 分層淘汰」四條主軸串起來，並主動給出回退到關聯式資料庫的邊界，就能拉開與背誦產品清單的差距。

一句話答法面對時序儲存設計題，先量化「每秒點數 × 活躍 Series 基數 × 保留跨度」，再用時間分區 Chunk、Gorilla 壓縮、預聚合 Rollup 與基數治理四根柱子收斂架構。
