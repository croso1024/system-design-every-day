01

先決定放不放，再讓上游開工

限流器賣的是「在昂貴工作發生之前說不」。演算法選擇決定你允許什麼樣的突發，以及多節點時這句話還算不算數。

面試題 Design a Rate Limiter 容易被答成「用 Redis INCR」。那只是儲存。題目真正要的是四件事：限流器坐在哪、鍵是誰、一段時間內允許什麼形狀的流量、很多台機器時這個計數怎麼保持一個意思。演算法決定形狀；原子操作決定這個意思在多節點下還在不在。

限流器要在上游開工之前做完決定。決定本身必須比被保護的工作便宜，否則它就是另一個需要被保護的熱點。

身份通常是使用者、API key 或來源 IP，有時再乘上路由。驗證要做到「認得出這個鍵」就夠，不要等整個業務邏輯跑完才計數——否則超限的請求已經把資料庫打過一輪。不同端點的成本可以不同：上傳可以扣 5，讀取扣 1。Token Bucket 用扣減量表達這件事最自然；對齊視窗的計數器通常還是一筆算 1。

邊界三道門不要答成同一道

限流是工作開始前，依「這個鍵最近打了多少」拒絕。熔斷、艙壁隔離與降級是依賴已經失敗或自己已經忙不過來之後的自保。逾時、重試與退避是客戶端在失敗之後怎麼再試——限流器要假設拒絕不是終點，被拒絕的客戶端常常馬上回來。429、Retry-After 與額度標頭的契約在 API 設計風格與演進；Redis 的資料結構在 Redis 架構與運維；以模型 token 計價的預算在 LLM Gateway。這篇只處理「怎麼數、數出來的形狀、多節點如何共用這一個數」。

一句話答法限流器在上游之前、用便宜的原子計數拒絕超額。演算法決定允許的突發形狀；多節點若各數各的，等於把上限乘上台數。
02

對齊視窗：好寫，邊界會放兩倍

Fixed Window 把時間切成等寬的格子，每格一個計數。格子對齊絕對時間時，所有身份在同一條邊界上一起歸零。

規則很短：請求時刻 t、窗寬 W、上限 L，視窗編號是 floor(t / W)。該編號的計數未滿 L 就放行並加一，否則拒絕。熱路徑只留兩個數字：現在的編號、這個編號已經放了幾筆。實作用帶視窗編號的 key，到期時間設成一個窗寬，下一格自然換一把新 key。

代價出現在邊界。設 L = 2、W = 1000 ms。800 ms 與 900 ms 落在視窗 0，兩筆都放。1000 ms 起算視窗 1，計數從 0 再開，1100 ms 再放一筆。演算法覺得自己守住了「每窗 2 筆」。把尺改成「任意連續 1000 ms」，800 到 1100 這四筆全部還在同一段裡，實際是 2 × L。

邊界兩側合起來，最短約一個窗寬內可放進 2 × limit

還有一種常見寫法不把視窗編號放進 key：第一次 INCR 時把 TTL 設成 W，key 過期就等於重新開窗。邊界從「大家共用的整點」變成「這個鍵自己的第一筆」。單鍵仍然可以在過期前後各吃滿一次 L，所以 2 倍還在，只是每個身份的尖峰不對齊。時鐘若只靠各台應用自己算 floor(t / W)，歪 200 ms 在 60 秒窗裡無所謂，在 1 秒窗裡會讓相鄰兩台把同一筆請求算進不同格。要對齊就用計數器那台機器的時間來算編號。

陷阱「固定視窗很簡單」不算答完

面試官下一句通常是：限制每秒 5 次，攻擊者能不能在某個瞬間打進 10 次？能。就在邊界兩側。你若接受這個突刺，要說得出來；你若不接受，就不要停在 Fixed Window。

一句話答法Fixed Window 每格一個計數，好寫也好原子化。相鄰兩格各吃滿上限時，任意一個窗寬裡最多約兩倍。
03

滑動視窗：精確的日誌，或兩個整數的近似

Sliding Window 要守的是「任意一段 W 內不超過 L」，不是「每個對齊格子不超過 L」。精確與省記憶體在這裡分家。

Sliding Log 留下這個鍵在窗內每一次放行的時間戳。新請求進來，先丟掉年齡已經達到 W 的舊戳（年齡剛好等於 W 算窗外），剩下的筆數小於 L 才放行，並把自己的時間戳推進去。任意一段長度為 W 的區間都不會超過 L，邊界突刺消失。熱路徑的記憶體等於窗內放行筆數：上限 1 萬就是 1 萬個時間戳，每次還得在原子腳本裡刪舊的、數剩下的。低頻或上限很小的時候這很舒服；每秒幾萬筆的熱鍵會把腳本與記憶體一起撐大。

Sliding Counter 用兩個整數換這份精確。只留上一格的放行數 prev 與這一格已經放行的 curr。請求落在格子內的偏移是 elapsed，用上一格還「掛在」滑動窗裡的比例來估計：

estimate = prev × (W − elapsed) / W + curr

estimate 小於 L 才放行，然後 curr 加一。它假設上一格的請求沿時間均勻鋪開——這通常不是真的。

上一格 5 筆若都擠在格子一開頭，新格子剛開始時它們的年齡已經到達 W，日誌會把它們全部丟掉、估計應為 0。加權仍然把 prev 整段算進去，estimate = 5，上限若也是 5 就會拒絕。這是偏嚴。反過來，5 筆若都擠在上一格的末端，過了半窗它們其實還全部活著；加權只算一半，estimate 偏低，可能在日誌已經超限時仍然放行。這是偏鬆。兩個整數買到的是「大多時候接近滑動窗」，不是證明。

陷阱加權不是保守的下界

它會雙向偏。流量在格子裡越不均勻，偏得越多。需要「任意窗絕對不超過」當契約時，不要用它交差；需要「比 Fixed Window 少很多突刺、又不能存時間戳」時，它是實務上的妥協。

一句話答法Sliding Log 用時間戳守住任意窗寬；Sliding Counter 用上一格加權，只留兩個整數，均勻假設不成立時會偏嚴或偏鬆。
04

兩種桶：立刻送出，或排開再送

Token Bucket 允許閒置後一次倒出容量。Leaky Bucket 把已接受的工作排成固定間隔。放行筆數可以一樣，上游看到的形狀不一樣。

Token Bucket 記兩個數：現在還有幾個 token、上次補充的時刻。閒置時以固定速率把 token 加到不超過容量。來一筆成本為 1 的請求，餘額至少是 1 就扣掉並立刻轉發，否則拒絕。容量是突發的寬度，每秒補充量是穩態速率。閒置夠久之後，下游會在很短的時間裡收到整整一桶——因為放行的當下請求就進了上游，桶並不幫你排隊。

tokens = min(capacity, tokens + 經過秒數 × 每秒補充)

Leaky Bucket 把同一組數字用來排隊。出發間隔是 1 / 每秒補充。桶深 capacity 表示最多有這麼多筆可以在途，最晚那筆要比到達時間晚 (capacity − 1) 個間隔。排不進去就拒絕，而不是先放行再祈禱上游撐住。已經排進去的請求，出發時刻彼此相隔一個間隔；上游看到的是平滑的流水，不是一桶倒下來。

同一組數字可以讓兩種桶放行同樣的筆數。容量 3、每秒補充 2，請求在 0、10、20、30 ms 到達：Token 立刻放行前三筆、拒絕第四筆，三筆在 30 ms 內都已進上游。Leaky 的間隔是 500 ms，前三筆的出發時刻是 0、500、1000 ms，第四筆要排到 1500 ms、超過桶深，拒絕。放行數都是 3。

所以選擇不在「哪個比較先進」，而在你有沒有地方讓請求等。同步的 HTTP 中介層通常只能現在放或現在拒絕，Token Bucket 跟這個模型一致，突發會真實打進上游——上游要另有容量或別的保護才接得住。前面若有佇列，Leaky Bucket 用延遲換輸出間隔。nginx 的 limit_req 就是漏桶：超出速率的請求預設被延後；burst 加上 nodelay 則把突發立刻轉發，再超出才拒絕。那是「有沒有排隊」的開關。Envoy 的本地限流配置用的是 token bucket，放行即走。

補充速率拉到 0 時兩種桶也不再是對偶：Token 仍能把初始那一桶倒完，Leaky 沒有出發間隔，一筆都排不出去。這是模型的邊界，不是生產參數。

關鍵GCRA 不是第三種桶

GCRA（Generic Cell Rate Algorithm）記的是「下一筆理論上最早可以到的時刻」，而不是水位。和漏桶同一件事，只是記帳方向相反。面試聽到這個名字，把它歸到 Leaky Bucket，然後問對方：放行之後請求是立刻進上游，還是在佇列裡等到那個時刻。

一句話答法Token Bucket 用閒置累積的容量換一次突發，放行就立刻打進上游。Leaky Bucket 把出發時間排開；沒有佇列時，它只能拒絕，不能延後。
05

同一條到達序列，兩種演算法並排

把窗寬、上限、容量、補充速率定成同一份預算，差異就只來自演算法，不來自你偷偷換了一組數字。

下面這把尺是：「任意一段窗寬裡最多放行 limit 筆」。它就是 Sliding Log 的契約。Fixed Window 會在邊界上超過它；Token 與 Leaky 根本不沿格子歸零，它們的穩態由每秒補充決定，突發由容量決定。要讓桶的穩態和這把尺對齊，把每秒補充設成 limit / (窗寬秒數)。預設是 1000 ms、3 筆、每秒補充 3、容量 4——比視窗上限多 1，用來看見多出來的那一點突發。表的每一列是你填的順序，不是時間順序；圖的橫軸才是時間。

暖色表示這一筆被拒絕，那是限流器在履行職務，不是故障。變紅的「任意視窗超出」才是相對精確契約多放的筆數。底線上的圓點是左欄、頂端的方點是右欄，實線與虛線是兩邊的累計放行。淡的直虛線是對齊視窗的邊界，只作對照：Token 與 Leaky 不會在那條線上歸零。

06

多節點：原子扣額度，或先預取再承擔不公平

每一台都在本地數，上限就被乘上台數。共用一個計數器之後，下一題才是：每筆請求都去問，還是一次借一批。

三個行程可以各留一份本地餘額，但扣減要打到同一個計數器。各數各的，等於每個節點都擁有完整上限。

集中式的固定視窗是一次原子加一。key 帶規則、身份與視窗編號，值是這個格子已經放行的筆數。兩條命令拆開寫會留下一個經典洞：INCR 成功、行程在 PEXPIRE 之前死掉，key 沒有到期時間，這個身份之後每一筆都算在同一個永不歸零的計數上，等於被永久限流。修法是一支腳本：加一之後若發現沒有 TTL（PTTL 小於 0），就補上。視窗編號用計數器自己的時間來算，應用機器的時鐘歪了也不會把同一筆算進不同格。

local t = redis.call('TIME')
local ms = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
local wid = math.floor(ms / tonumber(ARGV[1]))
local key = KEYS[1] .. ':' .. wid
local c = redis.call('INCR', key)
if redis.call('PTTL', key) < 0 then
  redis.call('PEXPIRE', key, ARGV[1])
end
return c

腳本整段是一次往返。PTTL 小於 0 才補到期時間，避免「第一次設定 TTL 失敗後，這個 key 永遠不再被補上」。

Token Bucket 的競態更明顯：先讀餘額、本地扣、再寫回，兩個請求會讀到同一個餘額、各扣一次，最後一個 token 被花兩次。讀、算、寫必須在同一支腳本裡。Sliding Log 則是同一支腳本裡做刪除窗外時間戳、計數、條件寫入。這些都還是「儲存提供原子讀改寫」，不是 Redis 內部怎麼持久化。

每筆請求都在關鍵路徑上等這一趟往返。計數器慢，限流器就比上游還慢。

本地預取是用公平性換往返。節點手上沒有餘額時，向中央一次原子借走 min(批次, 剩餘)，然後在本地花。借到 0 就記住這一窗已經空了，不要每筆都再打一次。全域計數不會超過上限，因為借走的當下已經從中央扣掉。吃虧的是額度會卡在借走它的那台機器上。

兩個節點、各兩筆請求、全域上限 6、一次借 4：節點 A 借走 4、用掉 2、手上還留 2；節點 B 只能再借到剩下的 2，兩筆都用掉。這一批四筆全部放行，但有 2 個額度鎖在 A 上直到視窗結束。此時若第 5 筆打到 B，中央已經是 0、B 手上也是 0，請求被拒絕——額度還在 A 手上，搬不過去。

陷阱預取不是超發

上面這種原子預取，全域放行數不會超過上限。會超發的是另一種設計：每台用自己的本地計數放行，過一秒才回寫。4 台各允許每秒 10 筆、全域目標若是每秒 10，這一秒最多進去 40。預取解決的是往返與「額度卡在別台」；過期本地計數解決不了超發，它就是超發的來源。

熱鍵也不要幻想成「把同一個使用者的 key 拆成好幾片再加總」。不同身份本來就會落到不同 key，這已經把負載分開。單一熱身份若再拆片，每片各有一份上限，總和會超；若把每片上限調低，流量不均時又會提早拒絕。熱身份能做的是少打中央：批次借、接受卡額。計數器掛了要事先選邊。登入、驗證碼這類安全上限應失敗即拒絕，否則攻擊者只要打掛計數器就沒有門。讀取類的禮貌上限可以失敗即放行，但每台仍要一個很小的本地天花板，避免「中央失聯」變成無限放行。

下面把同一批請求同時送給兩種共用方式。請求以輪替順序到達各節點。集中式每筆都打一次中央；預取只在本地沒餘額時借一批。紅字是卡在節點上的餘額、最終少放行的筆數，以及拒絕發生時別的節點仍握有餘額的次數。後兩個不必相等：最終總量仍可能補滿，只是拿到額度的不是先被拒絕的那台。

預設 4 個節點、各 2 筆、上限 20、一次預取 8。把批次收到 1，卡額會消失，往返會靠近集中式。節點數拉高時，同一份上限被更多人同時預借。

一句話答法多節點必須共用一個原子計數，否則上限乘上台數。每筆都問中央最準也最慢；一次預取省往返，但額度會卡在借走它的那台機器上，全域計數仍不超發。
07

面試時按這個順序講完

十五分鐘夠用的骨架：先鎖契約，再選演算法，再講多節點與計數器掛掉。不要從 Redis 命令開始。

先問清楚鍵是使用者、IP 還是 API key，上限是每秒幾筆還是任意窗，允不允許突發，有沒有多台應用。接著選演算法，用第 5 節那把精確契約說明你放棄了什麼。儲存只需要「單一 key 上的原子讀改寫與 TTL」。熱身份不拆 key，改預取。最後講計數器失聯時安全上限失敗即拒絕、禮貌上限失敗即放行並加上本地天花板。429 的本體與標頭不要在這裡發明，指到 API 設計風格與演進裡已經定的那一套。

08

Usage Plan 與 WAF 各管一種粒度

AWS 已經有兩套現成限流。它們不是同一種演算法，也不能互相替代你服務內部的使用者級預算。

API Gateway 的 usage plan 把 throttle 與 quota 拆開。throttle 的 rate 是穩態每秒請求數，burst 是桶容量，也就是 token bucket：閒置時可以一次打進 burst 筆，然後回到 rate。quota 是另一個計數，按日、週或月歸零，不負責抹平秒級突發。計劃綁在 API key 與 stage 上。就算計劃寫得很寬，stage 與帳號層還有自己的 throttle，請求可能先死在那兩層。超限時請求已經到達閘道，回應是 429；標頭怎麼寫不在這篇。

WAF 的 rate-based rule 粗得多。評估視窗可以是 1、2、5 或 10 分鐘，預設 5 分鐘，依來源 IP、轉送過來的 IP，或你指定的自訂鍵計數。超過門檻就對該鍵執行動作，直到速率掉回門檻以下。門檻下限以帳號當下的限制為準：文件上的下限曾是每視窗 100，後來改成 10。它適合擋邊緣上的大量濫用，不適合「每個使用者每秒 5 次」這種契約——視窗最短 1 分鐘，而且被擋下的請求常常到不了你的應用，你的 429 本體不會出現。

兩套都叫限流。一個是合作夥伴的秒級 token bucket，一個是邊緣上以分鐘計的視窗。內部使用者的毫秒級預算仍然要自己數。

陷阱閘道有了，服務裡那一層還在

Usage plan 看的是 API key，不是你資料庫裡的使用者。金鑰被共享、或流量從內部服務直接打進來時，閘道的桶根本看不到。WAF 擋住的是粗暴流量，擋不住已經通過認證、慢慢磨配額的客戶。自己的限流器仍要放在認得出身份的那一層前面。

一句話答法API Gateway usage plan 用 token bucket 管 API key 的每秒速率與突發，quota 另算。WAF rate-based rule 用分鐘級視窗擋邊緣濫用。使用者級、加權、亞秒級的契約要自己做。
