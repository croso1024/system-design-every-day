交易隔離級別與 MVCC (Isolation Levels & MVCC)

當兩筆交易同時讀寫同一批資料列，「各自究竟看得到什麼」決定了系統會不會算錯帳、超賣名額或讀到幽靈紀錄。資料庫並非只有「全部排隊串行」與「完全裸奔」兩個極端：MVCC 用版本鏈與快照讓讀寫互不阻塞，而四個隔離級別則是一張明確的防護邊界表。本篇以兩筆交易的交錯執行為主軸，拆解五種經典並發異常、PostgreSQL 與 InnoDB 截然不同的版本鏈與 Repeatable Read 行為，以及無鎖達成可串行化的 SSI。

01

總覽：當兩筆交易交錯執行時各自看到什麼

ACID 裡的 Isolation 解決什麼問題、為什麼不能全靠大鎖，以及本篇在單機與分散式版圖中的邊界。

在單執行緒的世界裡，每筆交易（Transaction）從頭跑到尾才換下一筆，系統永遠維持乾淨的不變量（Invariant）。但真實的線上資料庫必須同時服務數百條連線：只要兩筆交易的讀寫語句在時間軸上交錯（Interleave），一筆交易就可能讀到另一筆尚未提交的半成品、兩次讀取拿到不同數字，甚至兩筆各自合法的交易合起來把業務規則撞破。

ACID 當中的 Isolation（隔離性），字面承諾是「讓並發執行的多筆交易，看起來就像一筆接一筆串行執行一樣」。問題在於代價：如果真的用讀寫大鎖把所有交易排成單行道，吞吐量會在高並發讀取下瞬間崩盤。因此現代關聯式資料庫幾乎一致走向兩層分工——底層用 MVCC（Multi-Version Concurrency Control，多版本並發控制）保留資料列的歷史版本，達成讀不擋寫、寫不擋讀；上層則提供四個隔離級別（Isolation Levels），讓工程師在「擋掉多少種並發異常」與「付出多少延遲或重試成本」之間精準取捨。

隔離強度光譜：由左至右能擋下的並發異常越來越多，但鎖競爭（2PL）或衝突中止重試（SSI）的代價也隨之上升；PostgreSQL 預設落在 Read Committed，MySQL InnoDB 預設落在 Repeatable Read。

邊界單機隔離 vs 鎖機制 vs 分散式交易 vs 複寫一致性

面試談到一致性與隔離時，四個概念極易混為一談，本篇聚焦在單機儲存引擎內部的隔離級別與 MVCC 可見性：
• 鎖的粒度與死鎖偵測（Row Lock、意向鎖、Gap Lock 細節與 Wait-for Graph）由「資料庫鎖與死鎖（Database Locking & Deadlock）」專門拆解。
• 跨節點／跨微服務的原子提交（2PC、TCC、Saga 與 Outbox）見「分散式交易手冊」。
• 多副本複寫延遲下的一致性模型（Linearizability、Read-your-writes、Monotonic Reads）則屬於「進階複寫與一致性模型手冊」的範疇——別把單機 ACID 的 Serializable 跟分散式 CAP 的 Linearizability 畫上等號。

一句話答法Isolation 定義「並發交錯時一筆交易能看見別人多少中間結果」，MVCC 則以多版本快照取代讀取鎖，讓絕大多數唯讀查詢不必等寫入放鎖就能拿到一致視圖。
02

五種並發異常：從髒讀到寫偏斜

Dirty Read、Non-repeatable Read、Phantom、Lost Update 與 Write Skew 的精確交錯條件與帳務災難。

要選對隔離級別，不能死背名詞，必須先看清「如果不攔截，兩筆交易交錯會出什麼具體事故」。SQL-92 標準最初只定義了前三種讀取異常，但實務上真正造成扣款歸零、超賣與排班開天窗的，往往是標準漏寫的後兩種寫入異常——Lost Update 與 Write Skew。

1. Dirty Read（髒讀）：讀到別人尚未提交、甚至隨後回滾的修改

交易 T1 把帳戶餘額從 100 改成 200（尚未 COMMIT），交易 T2 此刻進來讀到 200 並據此發貨，結果下一秒 T1 因檢查失敗執行 ROLLBACK，餘額退回 100——T2 依據一筆「從未正式存在過」的幽靈金額做出了不可逆的外部動作。除此之外，就算 T1 最終會提交，若它在轉帳途中先扣 A 帳戶還沒加 B 帳戶，T2 在中間讀總帳也會看到憑空蒸發的金額（即窺見交易內部的半成品狀態）。

2. Non-repeatable Read（不可重複讀 / Fuzzy Read）：同一筆交易讀同一列兩次，值變了

交易 T1 先讀帳戶 x 拿到 100；此時 T2 把 x 改成 200 並正式提交；T1 稍後再讀一次 x 卻拿到 200。T2 已經提交，所以這不是髒讀；但如果 T1 是一支「先算明細、再算總和對帳」的財務報表查詢，前後兩條 SELECT 看到不同時間點的帳面，報表在單一交易內就自相矛盾。

3. Phantom Read（幻讀）：同一條件範圍查詢兩次，符合條件的「列集合」變了

不可重複讀針對的是既有單一列被修改，幻讀針對的則是範圍謂詞（Predicate）下冒出新插入或消失的列。例如 T1 執行 SELECT COUNT(*) FROM shifts WHERE on_call = true 得到 1，接著 T2 INSERT 一筆新的值班紀錄並提交，T1 在同一筆交易裡再次掃描同一條件時發現變成 2 列。傳統行級鎖鎖得住「已經存在的列」，卻鎖不住「還沒被寫進索引縫隙裡的新列」，這正是幻讀在實作上比不可重複讀更難纏的原因。

4. Lost Update（遺失更新）：兩筆 Read-Modify-Write 互相覆蓋

當應用程式寫出「先 SELECT 讀出舊值、在記憶體算新值、再 UPDATE SET val = 新值」的三步模式時，兩筆交易同時讀到 balance = 100，各自加 50 寫回 150，先提交那筆的 +50 就被後提交那筆無聲無息地蓋掉了。

5. Write Skew（寫偏斜）：讀重疊集合、寫不相交的列，合起來打破跨列不變量

這是資深面試最愛考的陷阱，因為它連 Snapshot Isolation 都擋不住。經典案例是醫院急診室規定「至少要有 1 位醫師保持值班（on_call = true）」：目前 Alice 與 Bob 兩位醫師都在值班，兩人恰巧在同一毫秒點下「請假下班」。兩筆交易各自先檢查目前有幾人值班、看到 2 人（大於 1，合法），接著各自更新自己的那一列為 false 並雙雙提交——沒有任何一列被兩個人同時改到，因此不會觸發列級寫寫衝突，但提交後值班人數變成 0，業務不變量徹底破裂。

陷阱Lost Update 與 Write Skew 差在哪裡？

兩者都是「先讀後寫」引發的異常，區別在於寫入目標是否重疊：Lost Update 是兩筆交易讀同一列、最後也覆寫同一列（可視為 Write Skew 在單一列上的退化特例）；Write Skew 則是兩筆交易讀取同一批列做決策，最後卻各自修改不同的列（甚至各自 INSERT 一筆新列，稱為 Phantom Write Skew，例如同一會議室同一時段被兩組人同時預約成功）。

一句話答法前三種異常（Dirty、Non-repeatable、Phantom）談的是「讀取視圖被別人干擾」，後兩種（Lost Update、Write Skew）談的是「基於快照讀取做決策後寫回，把單列更新蓋掉或把跨列不變量撞破」。
03

四個隔離級別與 Snapshot Isolation 的真實面貌

SQL-92 標準的歷史包袱、五大異常防護矩陣，以及為什麼主流引擎的 Repeatable Read 其實是 Snapshot Isolation。

1992 年制定的 ANSI SQL-92 標準做了一個影響深遠、卻也留下無數混淆的設計：它用「不允許出現哪幾種異常（Dirty Read、Non-repeatable Read、Phantom）」來反推四個隔離級別。當時主流商業資料庫多數基於兩階段鎖（2PL，讀鎖加寫鎖）實作，壓根沒有預料到後來 Berenson 等人在 1995 年論文《A Critique of ANSI SQL Isolation Levels》點出的 Snapshot Isolation（SI，快照隔離）會接管世界。

今天你在工程現場打開 PostgreSQL 或 MySQL InnoDB，嘴上喊的雖然同樣是 SQL 標準那四個名字，骨子裡的防護邊界卻已經因為 MVCC 的設計抉擇而分道揚鑣：

  • Read Uncommitted（RU）：標準允許髒讀。MySQL InnoDB 真實支援此級別（掃描時直接讀最新列版本，不建 Read View）；而 PostgreSQL 直接把 Read Uncommitted 映射為 Read Committed，在 PG 中永遠不可能發生髒讀。
  • Read Committed（RC）：保證只讀已提交資料，消除髒讀（與髒寫）。在 MVCC 下，每一條 SQL 語句開始執行時都會重新拍一張最新快照，因此同一筆交易前後兩條 SELECT 會看見中間別人剛提交的修改（允許 Non-repeatable Read 與 Phantom）。這是 PostgreSQL、Oracle 與 SQL Server 的預設級別。
  • Repeatable Read（RR）與 Snapshot Isolation（SI）：在交易第一次讀取時拍下一張固定快照並沿用到交易結束。但這裡藏著最大的引擎分歧——PostgreSQL 的 REPEATABLE READ 實質上就是完整的 Snapshot Isolation：不僅單純快照讀連 Phantom 都看不到，寫入同一列時更內建 First-Committer-Wins 自動中止後寫者，直接擋掉單列 Lost Update；反觀 MySQL InnoDB 的 REPEATABLE READ 則是「快照讀（MVCC）＋當前讀（Current Read + Next-Key Lock）」的雙軌混合體，若開發者只做普通 SELECT 再 UPDATE，InnoDB 不會自動報錯中止，Lost Update 照樣發生！
  • Serializable：最強保證，要求並發結果等價於某種真實串行順序，連 Write Skew 也必須攔下。傳統引擎（如 MySQL InnoDB）靠自動把普通讀取升級為共享 Next-Key Lock（退回嚴格 2PL，讀寫互擋）；PostgreSQL（9.1+）則用無鎖的 SSI（Serializable Snapshot Isolation）達成。

關鍵在 RC 底下怎麼安全防範 Lost Update？

既然多數團隊在線上使用預設的 Read Committed，遇到扣庫存、加點數怎麼辦？有三條正途：(1) 改寫成原子單語句 UPDATE accounts SET balance = balance - 50 WHERE id = 1 AND balance >= 50，讓引擎在當前最新已提交列上原子取值並上行鎖；(2) 顯式悲觀鎖 SELECT ... FOR UPDATE 先鎖住目標列再算；(3) 應用層樂觀鎖（CAS） UPDATE ... SET val = ?, version = version + 1 WHERE id = 1 AND version = 舊版本，檢查受影響列數為 0 就重試。

一句話答法SQL-92 的四級分類漏掉了 Snapshot Isolation：PostgreSQL 的 RR 實作的是帶 First-Committer-Wins 的純 SI（擋掉 Phantom 與 Lost Update，只剩 Write Skew），而 InnoDB 的 RR 對普通讀不驗寫衝突，仍可能發生 Lost Update。
04

MVCC 核心機制：版本鏈與快照可見性

「讀不擋寫、寫不擋讀」怎麼靠一套四元組快照與一條可見性公式算出來。

在沒有 MVCC 的年代，如果交易 T1 正在修改某一列，尚未提交前該列掛著排他鎖（X Lock），任何想讀這一列的交易 T2 都只能排隊乾等；反過來，長報表查詢掛著共享鎖（S Lock）不放，線上寫入就全面卡死。MVCC（多版本並發控制）的核心洞察極其優雅：每次寫入不要直接毀掉舊資料，而是產生一個帶交易編號（Transaction ID）的新版本，串成一條版本鏈（Version Chain）。寫入者照樣寫它的新版本，讀取者則拿著手上的「快照（Snapshot / Read View）」沿著版本鏈挑選對自己可見的那一版。

快照（Snapshot / Read View）裡到底裝了什麼？

無論是 PostgreSQL 的 SnapshotData 還是 InnoDB 的 ReadView，一張快照本質上都由拍照當下活躍交易集合的四個邊界值組成（兩者欄位命名略有方向顛倒，這裡以通用語意搭配雙引擎術語說明，對照見第 5 節）：

  • creator_trx_id：拍下這張快照的交易自己的 ID（自己寫的未提交變更，自己當然要看得到，保證交易內的 Read-your-own-writes）。
  • m_ids（PG 稱 xip[]）：拍照那一瞬間仍在執行中、尚未提交的所有活躍讀寫交易 ID 清單。
  • low_limit_id（InnoDB 的 m_up_limit_id / PG 的 xmin）：m_ids 裡的最小值——凡是交易 ID 嚴格小於這個下界的版本，在拍照前肯定早已結束，只要是已提交就一律可見（PG 中比 xmin 小的交易也可能已回滾，仍得查 pg_xact；InnoDB 回滾時會用 Undo 把列實際還原，版本鏈上不會留下已回滾的版本）。
  • high_limit_id（InnoDB 的 m_low_limit_id / PG 的 xmax）：系統即將發出的下一個交易 ID——凡是交易 ID 大於等於這個上界的版本，都是拍照之後才剛啟動的新交易（就算它手腳很快在下一毫秒已經提交），對這張歷史快照而言也一律不可見。
visible(trx) ⇔ trx = creator ∨ ( trx < low_limit ∧ committed(trx) ) ∨ ( low_limit ≤ trx < high_limit ∧ trx ∉ m_ids ∧ committed(trx) )

當查詢掃到某一列，發現表頭最新版本是由交易 trx 寫入但通不過上述公式時，引擎不會阻塞等鎖，而是順著版本指標往舊版本走一步，重新套用同一條公式，直到找到第一個可見版本（若走到鏈尾仍無可見版本，代表該列在快照當下尚未誕生，直接略過）。

Read Committed 與 Repeatable Read 在 MVCC 下只差「何時按快門」

理解了這套公式，RC 與 RR（純快照讀）的實作差異其實只是一行呼叫時機的差別：

  • Read Committed：每次執行單條 SELECT 語句前重新建立一張新的 ReadView。中間別人只要 COMMIT，移出了活躍清單 m_ids，下一條 SELECT 的新快照就會立刻看見它。
  • Repeatable Read：只在交易內第一條讀取語句執行時建立唯一一張 ReadView（PG 若下 BEGIN ISOLATION LEVEL REPEATABLE READ，同樣在交易第一條一般查詢語句時凍結快照），之後整筆交易不管再讀幾百次都重用同一張 m_ids。
陷阱BEGIN 按下去的那一刻，快照還沒拍！

很多工程師以為只要執行了 BEGIN;，Repeatable Read 的時間點就凍結了。事實上在 PostgreSQL 與 MySQL InnoDB 中，單純的 BEGIN 為了節省開銷都是延遲啟動：直到你發出交易內的第一條查詢語句（SELECT 等）那一刻，快照才真正拍下！在 MySQL 若想在交易起點立刻鎖定快照，必須顯式寫 START TRANSACTION WITH CONSISTENT SNAPSHOT;。

一句話答法MVCC 的核心是「多版本鏈 ＋ 活躍交易快照（Read View）」：寫入只追加版本，讀取靠比對版本 trx_id 與快照上下界及活躍清單決定可見性，而 RC 與 RR 的本質差別只在「每條語句重拍快照」還是「整筆交易共用首張快照」。

引擎實作對決：PostgreSQL vs MySQL InnoDB

Append-only Heap Tuple 對決就地更新加 Undo Log，以及同叫 Repeatable Read 為何行為大不相同。

同樣都叫 MVCC，PostgreSQL 與 MySQL InnoDB 在底層儲存佈局上卻做出了截然相反的架構折衷——正如「資料庫索引原理」篇比較過的 Heap Table 與 Clustered Index 差異，這個物理結構的分歧一路延伸到歷史版本存在哪裡、ROLLBACK 要花多久，以及同名的 REPEATABLE READ 在面對並發寫入時會不會出現驚悚的行為差異。

PostgreSQL 與 InnoDB 的版本鏈方向相反：PG 在 Heap 追加新 Tuple 並由舊指新（HOT 優化可省下同頁索引更新）；InnoDB 在原地改寫最新列並用 DB_ROLL_PTR 指往 Undo Log 裡的舊紀錄。

靈魂拷問：兩家的 Repeatable Read 到底差在哪裡？

如果面試官問「同樣設成 REPEATABLE READ，PostgreSQL 與 MySQL InnoDB 的行為一樣嗎？」，回答「一樣，都防不可重複讀」只拿到及格邊緣；真正拉開差距的是寫入觸發點上的兩大差異：

  1. PostgreSQL RR 是嚴格的單一快照 + First-Committer-Wins：在 PG 的 RR 下，當交易 T1 執行 UPDATE 或 SELECT FOR UPDATE 撞上一列在 T1 快照拍下之後已經被 T2 修改並提交的列時，PG 絕不允許 T1 靜默覆蓋它，而是等 T2 提交後立刻對 T1 拋出 ERROR: could not serialize access due to concurrent update (SQLSTATE 40001)。因此 PG 的 RR 天生免疫單列 Lost Update。
  2. InnoDB RR 區分「快照讀（Snapshot Read）」與「當前讀（Current Read）」：普通 SELECT 走 MVCC Read View（快照讀）；但只要你發出 UPDATE、DELETE、SELECT ... FOR UPDATE 或 LOCK IN SHARE MODE，InnoDB 一律切換成當前讀——無視你手上的舊快照，直接去讀 B+Tree 上最新已提交的那一版並加鎖（Record Lock + Gap Lock = Next-Key Lock）！這會導致兩個震撼現象：
    • 無聲覆寫（Lost Update）：T1 先快照讀拿到舊值 100，中間 T2 改成 200 並提交，T1 接著 UPDATE SET val = 150——InnoDB 會在當前讀拿到 200 的那列上直接改寫成 150 並成功提交，完全不報錯。
    • 半途冒出的幻影列（Read-Write Phantom）：T1 先 SELECT 查範圍沒看到 id=5；T2 插入 id=5 並提交；若 T1 此時冒失地下了一句範圍 UPDATE tbl SET tag='x' WHERE id BETWEEN 1 AND 10，這條當前讀會把 T2 剛插進來的 id=5 一起改掉，並把它的 DB_TRX_ID 換成 T1 自己！下一秒 T1 再跑一次普通 SELECT，因為 trx = creator_trx_id，原本看不見的 id=5 突然大搖大擺出現在結果集裡！

07

版本清理與長交易代價：VACUUM、Purge 與膨脹

為什麼一筆忘記提交的閒置交易會拖垮整座資料庫？長交易凍結水位的定量模擬。

MVCC「保留舊版本、讀寫不互擋」並不是免費午餐。每當一列被 UPDATE 或 DELETE，舊版本不能馬上從磁碟抹除——因為系統裡可能還有一筆 30 秒前啟動的舊快照正準備去讀它。只有當某個舊版本的銷毀交易 ID（如 PG 的 xmax）嚴格小於目前全庫所有活躍快照當中最老的那個下界（OldestXmin / InnoDB 最老 ReadView）時，背景清理執行緒（PostgreSQL 的 VACUUM / Autovacuum，以及 InnoDB 的 Purge Thread）才有資格把它回收。

這直接導出線上資料庫最常見的雪崩根因之一：長交易（Long-running Transaction）或 idle in transaction。只要某個微服務開了 BEGIN 後，在 PostgreSQL 寫過一筆資料（已分配交易 ID，即使在預設 RC 下也算），或在 Repeatable Read / Serializable 下讀過一筆資料（交易快照已拍下並一路沿用；InnoDB 預設 RR 的普通 SELECT 就會建立 Read View），接著去呼叫一個卡住的外部 HTTP API 甚至忘記 COMMIT，OldestXmin 就會像釘子一樣死死釘在原地：

  • 在 PostgreSQL：該時間點之後全表（甚至全庫）產生的所有 Dead Tuple 都無法被 VACUUM 回收，資料頁與索引頁迅速發生表膨脹（Table & Index Bloat），原本存在記憶體 Buffer Pool 裡的熱表被稀疏的死屍撐大數倍，Sequential Scan 與 Index Scan 的 I/O 全面劣化；若放任不管超過約 20 億筆交易，還會撞上致命的 Transaction ID Wraparound（XID 回繞停機保護）。
  • 在 MySQL InnoDB：主表雖然就地更新，但 Purge Thread 無法清理 Undo Log，導致 History List Length（HLL）飆升至數百萬甚至數千萬；任何掃過熱點列的舊快照查詢都必須順著長達數千跳的 DB_ROLL_PTR 鏈逐層回推舊版，CPU 與隨機讀延遲瞬間炸裂。

08

邁向真正的可串行化：2PL 與 SSI，以及面試選型實戰

不靠悲觀鎖怎麼抓出 Write Skew？rw-antidependency 危險結構、隔離級別選型表與高頻面試追問。

既然 Snapshot Isolation 連 Phantom 都壓住了卻唯獨漏掉 Write Skew，當系統遇到金融帳務對沖、庫存配額上限、值班排班或會議室時段預約這類「不允許任何跨列不變量破口」的核心場景時，我們怎麼補上最後一塊拼圖，拿到真正的 Serializable（可串行化）？歷史上演化出兩條截然不同的技術路線：

  1. 悲觀路線——嚴格兩階段鎖（Strict 2PL，如 MySQL InnoDB Serializable）：只要切到 SERIALIZABLE，InnoDB 會把交易內所有不帶鎖的普通 SELECT 自動暗中改寫成 SELECT ... LOCK IN SHARE MODE（加共享 Next-Key Lock）。當 Alice 與 Bob 同時讀值班表時，兩人都掛上共享鎖；接著 Alice 想 UPDATE 自己的列升級為排他鎖時，必須等 Bob 放鎖，Bob 也想升級時直接撞出死鎖（Deadlock），由死鎖偵測器挑一方回滾。缺點很痛：唯讀查詢又重新開始阻塞寫入，MVCC 最引以為傲的「讀不擋寫」優勢當場報銷。
  2. 樂觀路線——可串行化快照隔離（SSI, Serializable Snapshot Isolation，如 PostgreSQL 9.1+ 與 CockroachDB 靈感來源）：由 Cahill 等人在 2008 年提出並獲 SIGMOD 最佳論文。SSI 完整保留了 MVCC 讀不擋寫、寫不擋讀的非阻塞特性！它不在讀取時卡住別人，而是在記憶體裡掛上完全不阻塞的輕量級記號 SIREAD Lock（謂詞鎖記號），專門追蹤交易之間的 rw-antidependency（讀寫反依賴：交易 A 讀到了舊版，而交易 B 隨後改寫了該範圍的新版，記作 A —rw→ B）。

SSI 的理論基石指出：在 Snapshot Isolation 底下，任何會打破可串行化的異常（包含所有變形的 Write Skew），在依賴圖上都必然會形成「連續兩條相鄰的 rw-antidependency 邊」（即危險結構 T1 —rw→ T2 —rw→ T3，在雙交易 Write Skew 中則是 T1 與 T2 互指成環 T1 ↔rw↔ T2）。只要在讀寫或提交時偵測到這個危險結構，引擎就主動讓後提交者以 SQLSTATE 40001 中止重試——沒有衝突時全程零鎖等待，有潛在危險時寧可偶爾誤殺（False Positive，例如粗粒度頁級 SIREAD 鎖合併時）也絕不漏放任何一筆髒帳。

面試高頻追問 FAQ
Q1 MVCC 既然號稱「無鎖讀取」，那是不是代表資料庫再也不需要鎖了？▸

完全不是，MVCC 只免除了「純快照讀與寫入之間」的鎖衝突，寫入與寫入（Write-Write）之間依然百分之百依賴排他行鎖！當兩筆交易同時 UPDATE 同一列時，第二筆交易一樣會被行鎖卡住等待第一筆提交或回滾（RC 下等鎖釋放後重讀最新版再評估條件；PG RR/SSI 下若發現第一筆已提交則直接拋 40001 放棄）。此外，DDL 變更表結構時的 Metadata Lock / AccessExclusiveLock 也與 MVCC 並存。

Q2 為什麼很多網路大廠會把 MySQL InnoDB 的預設級別從 Repeatable Read 調降成 Read Committed？▸

主因是 Gap Lock 與 Next-Key Lock 在高並發下太容易引發死鎖與鎖範圍擴大。在 InnoDB 的 RR 下，為了防範當前讀的幻讀，凡是沒命中唯一索引等值條件的 UPDATE / DELETE / FOR UPDATE 都會鎖住索引間隙（甚至鎖到 supremum 無窮大間隙），導致兩個插入不同 ID 的交易互相卡死。降為 READ COMMITTED（搭配 binlog_format = ROW）後，InnoDB 幾乎不再對一般掃描加 Gap Lock，而且不符合 WHERE 條件的列在評估後會立即釋放行鎖；遇到已被別人鎖住的列時，還會先讀它的最新已提交版本判斷是否符合 WHERE（Semi-consistent Read），不符合就直接跳過、不必等鎖，並發寫入吞吐與死鎖率都會大幅改善。

Q3 開啟 PostgreSQL 的 REPEATABLE READ 或 SERIALIZABLE 後，應用程式碼最常漏寫哪一件事？▸

漏寫「交易級別的重試迴圈（Retry Loop on SQLSTATE 40001）」！在 Read Committed 下，兩筆交易撞同一列時引擎會幫你乖乖排隊等鎖，醒來繼續跑完；但在 PG 的 RR（First-Committer-Wins）與 Serializable（SSI）下，引擎偵測到衝突的唯一手段就是直接讓後提交的交易報錯回滾。如果後端框架只針對單條 SQL 重試（此時舊交易早已處於 aborted 狀態），或直接把 500 錯誤丟給使用者，線上只要一有微幅競爭就會出現大量失敗請求。正確做法是在最外層包一層帶指數退避與微幅抖動（見「逾時、重試與退避」篇）的整筆交易重跑機制。

一句話答法要補齊 Snapshot Isolation 擋不住的 Write Skew，2PL 選擇把讀取退回共享鎖排隊，而 SSI 選擇用非阻塞的 SIREAD 記號攔截雙向 rw-antidependency 並交由應用端重試 40001——在讀多寫少的現代 OLTP 中，預設 RC 搭配單列原子寫、跨列關鍵路徑上 SSI 或父列顯式鎖，是最務實的黃金組合。
