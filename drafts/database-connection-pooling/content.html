資料庫連線池：為什麼連線昂貴，以及 Pool 開多大才對

把連線池從 20 調大到 200，為什麼反而讓資料庫 CPU 衝上 100%、吞吐量腰斬？這份手冊從一條連線背後的網路交握與作業系統行程成本出發，推導連線池大小的倒 U 型轉折點、應用端連線池與 PgBouncer 的雙層分工，以及 Transaction Pooling 在協定層埋下的狀態相容性陷阱。

01

連線為什麼昂貴：從網路交握到後端行程模型

拆解每次新建連線背後的四層固定稅金，以及 PostgreSQL 一條連線一個行程的記憶體與快照代價。

在開發環境跑腳本時，「收到請求 → 連上資料庫 → 跑一條主鍵查詢 → 關掉連線」看起來再自然不過。但只要放到每秒上千次請求的線上服務，一條原本在 B+Tree 上只需 0.8 ms 就能命中的查詢，若每次都重新建連，端到端延遲往往直接暴漲 15 到 40 倍，同時把資料庫的 CPU 燒在跟 SQL 無關的前置工作上。

新建一條資料庫連線，到底付了哪四筆稅？

從應用程式呼叫 connect() 到真正能送出第一條 SELECT，中間必須依序跨過網路層、加密層、認證層與資料庫核心初始化四道關卡：

  1. 1. TCP 三向交握（1 RTT + 核心 Socket 配置）：同可用區（Same-AZ）約 0.3–0.8 ms，跨可用區（Cross-AZ）約 1–2 ms；雙方作業系統還得配置 socket buffer 與連線追蹤表項（conntrack）。
  2. 2. TLS 交握（1–2 RTT + 非對稱密碼學運算）：雲端合規環境普遍強制加密連線，TLS 1.3 即使省到 1-RTT，ECDHE 金鑰交換與憑證簽章驗證仍會消耗可觀的雙方 CPU。
  3. 3. 資料庫身分認證與雜湊迭代（1–2 RTT + 刻意增重的 CPU 成本）：PostgreSQL 預設採用的 SCRAM-SHA-256 為了防禦離線暴力破解，預設跑 4,096 次 SHA-256 迭代；MySQL 的 caching_sha2_password 若未命中快取也需走 RSA 公鑰交換。這意味著頻繁新建連線會直接把認證演算法變成資料庫的 CPU 熱點。
  4. 4. 後端執行單元孵化與本地快取冷啟動：認證通過後，資料庫必須為這條連線分配獨立的行程或執行緒，並在第一次查詢時從系統表載入資料表與型別定義（Catalog Cache），還沒算業務查詢就先觸發數十次內部記憶體配置。

無連線池時，0.8 ms 的查詢前面墊了至少 3 次網路 RTT、密碼學雜湊與作業系統 fork()；連線池把上半段一次性攤提掉，熱路徑只剩純 SQL 往返。

為什麼 PostgreSQL 對「連線數過多」比 MySQL 更敏感？

不同關聯式資料庫對「一條連線」的底層執行模型截然不同，這直接決定了它們能承受的閒置與活躍連線上限：

比較維度 PostgreSQL（Process-per-connection） MySQL InnoDB（Thread-per-connection）
執行單元 每條連線由 postmaster fork() 出一個獨立 OS 行程 在單一 mysqld 行程內，每條連線對應一個 OS 執行緒
單條連線常駐記憶體 約 5–15 MB RSS（視觸碰過多少張表使 relcache / catcache 膨脹而定，另加獨立 work_mem） 約 256 KB–2 MB（執行緒堆疊 + 連線緩衝區，Catalog 與 Buffer Pool 全域共用）
閒置連線的隱形成本 極高：每次產生交易快照 GetSnapshotData() 都需掃描全體連線組成的 ProcArray，連線槽位越多快照鎖競爭越重 中低：閒置執行緒主要佔記憶體，但大量轉為活躍時仍會撞上內部 Mutex 與排程切換
故障隔離性 單一後端行程崩潰較易隔離，但若觸發共享記憶體保護仍會重啟實例 單一執行緒若發生記憶體越界，整個 mysqld 行程直接崩潰

PostgreSQL 的一條連線就是一個真實作業系統行程與獨立系統表快取：開 1,000 條連線光空載就可能吃掉近 10 GB 記憶體，並拖慢全庫的 MVCC 快照取得。

關鍵連線池省下的不只是「建連延遲」，更是「後端常駐足跡」

許多團隊以為只要應用端設了長連線（Keep-Alive），不反覆斷開重連就算解決問題。但在微服務架構下，真正壓垮資料庫的往往不是每秒新建幾條連線，而是數百個容器各自抱著幾十條「看似無害的長連線」不放，把資料庫推入記憶體耗盡與快照掃描退化的深淵。

一句話答法新建資料庫連線需付出 TCP、TLS、密碼學認證（如 SCRAM-SHA-256）與後端行程或執行緒初始化四層固定成本；尤其 PostgreSQL 採用一連線一行程模型，連線過多不僅燒掉數 GB 獨立快取記憶體，還會放大 ProcArray 快照掃描與排程切換開銷。
02

Pool 開多大才對：核心競爭、I/O 比值與倒 U 曲線

為什麼連線池不是越大越好？用排隊論與 Context Switch 物理學找出吞吐量的轉折點。

線上發生「等待資料庫連線逾時」告警時，最常見的反射動作就是把設定檔裡的 maximumPoolSize 從 20 改成 200。結果重新部署後，應用程式確實不再卡在本地連線池，但資料庫的 CPU 卻瞬間釘死在 100%，單筆 SQL 耗時從 4 ms 暴漲到 90 ms，整體系統每秒完成的交易數（TPS）反而跌剩不到原本的一半。

為什麼活躍連線超過核心數後，吞吐量會出現「倒 U 型崩跌」？

一顆 CPU 核心在同一奈秒只能執行一條指令流。當資料庫有 C_cpu 顆可用核心，卻同時湧入遠超核心數的活躍查詢行程時，系統不會變快，而是把算力浪費在三種內部摩擦（Retrograde Contention）上：

  • 作業系統排程切換與 CPU 快取失溫：Linux 排程器被迫每幾毫秒就在上百個 postgres 行程間做 Context Switch。每次切換不僅耗費數微秒保存暫存器，更致命的是把前一個查詢剛預熱好的 L1/L2 指令與資料快取、TLB 頁表快取全部沖掉。
  • 資料庫內部輕量鎖（Spinlock / LWLock）自旋風暴：所有連線共享同一塊 Buffer Pool、WAL 寫入緩衝區與 Lock Manager 雜湊表。當 200 個行程同時爭搶同一個 Buffer Mapping 分區鎖或 WAL Insert Lock，沒搶到的行程會在 CPU 上空轉自旋（Spinning）或頻繁休眠喚醒，產生「越忙越做不了正事」的協調稅。
  • 磁碟佇列深度過載：即使底層是 NVMe SSD，超出控制器最佳並列度後的隨機讀取也只會拉長每次 Page Read 的尾端延遲（P99 Latency）。

怎麼估算最佳連線池大小？兩條經典公式與適用邊界

從純計算與 I/O 等待的時間拆解出發，若單筆查詢在資料庫伺服器上平均花費純 CPU 時間 T_cpu，以及等待磁碟或同步複寫的阻塞時間 T_io，理論上能把 CPU 餵飽又不造成無謂排程競爭的同時活躍連線數 N_opt 為：

N_opt = core_count * (1 + T_io / T_cpu)

這也是為什麼 PostgreSQL 社群與 HikariCP 官方壓測最終收斂出那條著名的經驗公式：

connections = (core_count * 2) + effective_spindle_count

許多工程師第一次看到這條公式都會難以置信：一台 8 vCPU、掛載高速 SSD 的生產資料庫，最佳同時活躍連線數居然只有 16 到 24 條？關鍵在於現代資料庫有高達 95%–99% 的熱資料都命中記憶體內的 Shared Buffers（此時 T_io 趨近於 0），即使落盤到 NVMe SSD，單次讀取也僅 0.1–0.3 ms。T_io / T_cpu 的比值其實很小，因此略大於核心數 2 倍的連線數就足以在某個行程等待 I/O 的空檔把 CPU 填滿。

排隊不會消失，但「在哪裡排隊」決定生死

有人會問：「可是我的服務高峰期每秒有 3,000 個請求，池子只開 20 條怎麼夠用？」請把「併發請求數」與「連線池大小」脫鉤，用排隊論的 Little 定律算一筆帳：

L = λ * W

若單筆查詢耗時 W 為 4 ms（即 0.004 秒），那麼單條連線每秒就能順序跑完 250 筆查詢；20 條無競爭、火力全開的連線，理論最大吞吐高達 20 * 250 = 5,000 QPS！當瞬間突發流量超過 5,000 QPS 時，多出來的請求確實必須排隊，但你有兩個選擇：

  • 正確做法（小連線池 + 應用端記憶體排隊）：讓那 20 條資料庫連線維持零競爭的極速（4 ms 跑完一筆），第 21 個請求在應用程式記憶體內的 Lock-free 佇列裡安靜等 1–2 ms 就拿到剛釋放的連線。
  • 災難做法（開 300 條連線把排隊塞進資料庫）：所有請求都立刻拿到連線衝進 DB，結果鎖競爭與快取失溫讓每筆查詢從 4 ms 退化到 80 ms，單機最大吞吐崩跌到只剩 1,200 QPS，全站雪崩。
陷阱在交易或持連期間呼叫外部 API，會直接摧毀上述公式

上述「20 條連線撐起數千 QPS」的前提，是借出連線後只做純資料庫操作就立刻歸還。若程式碼在 @Transactional 區塊內夾帶一個耗時 300 ms 的第三方支付 HTTP 呼叫或對象儲存上傳，單次持連時間瞬間從 4 ms 暴增 75 倍到 304 ms——這條連線在其中 300 ms 對資料庫毫無貢獻，卻死死霸佔一個槽位，20 條連線每秒最多只能處理 65 筆請求，連線池會在幾秒內被徹底抽乾。

一句話答法連線池的作用不是「放大併發」，而是把進入資料庫的同時活躍查詢「限流」在 CPU 核心與 I/O 最有效率的甜蜜點（通常約為核心數的 2 到 3 倍），讓超額突發流量留在輕量的記憶體佇列排隊，避免資料庫陷入 Context Switch 與內部鎖自旋的倒 U 型吞吐崩跌。

04

雙層分工：應用端連線池與外部 Pooler（PgBouncer）

當微服務水平擴展把每台很小的本地池乘成上千條連線，外部多工器如何守住資料庫最後防線。

在單體架構時代，兩三台應用程式伺服器各自掛一個 maximumPoolSize = 10 的本地連線池（例如 JVM 的 HikariCP、Go 的 sql.DB、Node.js 的 pg-pool），資料庫總共只看到 20–30 條連線，天下太平。但當系統演進成 Kubernetes 微服務叢集，這套算術就會立刻破產。

微服務乘法陷阱：每個 Pod 都很節制，加總卻把 DB 撐爆

假設核心交易資料庫是 16 vCPU 的 PostgreSQL，依第 2 節公式，最佳同時活躍查詢約為 32–40 條，max_connections 設為 200。現在業務拆成 12 個微服務，大促期間自動擴容到每個服務 25 個 Pod（共 300 個 Pod）：

  • 就算你極度克制，把每個 Pod 的本地池縮到 maxPoolSize = 8，叢集對資料庫發起的常駐連線數仍是 300 * 8 = 2,400 條，直接撞破 max_connections 報出 FATAL: sorry, too many clients already。
  • 反過來，如果你為了不撞上限而把每個 Pod 設成 maxPoolSize = 1，某個流量稍微傾斜的 Pod 只要同時進來 2 個請求就得排隊，而其他 299 個閒置 Pod 卻白白佔著連線不幹活——本地連線池無法跨行程共享閒置配額。

（若是無狀態函式隨流量瞬間拉起上千個執行環境的極端連線風暴，以及託管式 RDS Proxy 的認證與權杖整合，詳見 Serverless / FaaS 篇。）

外部 Pooler 扮演「連線漏斗」：對上承接數千條輕量前端連線，對下只維持數十條真正貼合資料庫 CPU 核心數的後端行程。

既然有了 PgBouncer，應用程式還需要本地連線池嗎？

答案是兩層都要留，因為它們解決的是完全不同層次的問題。若拔掉應用端本地池，改成每次查詢都對 PgBouncer 短連線新建與斷開，應用程式與 PgBouncer 之間依然要每筆查詢重跑一次 TCP 與 TLS 交握；留著本地池維持對 PgBouncer 的熱長連線，再由 PgBouncer 對後端資料庫做跨 Pod 多工，才是生產環境的標準雙層配置：

職責維度 應用端連線池（HikariCP / pg-pool / sql.DB） 外部 Pooler（PgBouncer / Odyssey / ProxySQL）
所在位置與視野 嵌在單一應用程式行程內，只看得到該 Pod 自己的執行緒需求 獨立代理層，擁有全叢集所有服務與 Pod 的全域連線視野
核心解決痛點 省去 App 到代理層的建連 RTT、提供執行緒安全的阻塞借用佇列、追蹤未歸還連線的程式碼呼叫堆疊 把數千條大多數時間閒置的前端連線，多工壓縮成數十條後端 DB 實體連線，硬性保護 DB 記憶體與核心
運維與容災附加能力 健康探測（SELECT 1 / JDBC isValid）、依 maxLifetime 平滑輪替老舊連線 支援 PAUSE / RESUME 與線上重指派目標主庫，在主從切換或極短暫重啟期間暫存前端請求而不立刻報錯
典型代表工具 Java HikariCP、Go database/sql + pgxpool、Rust bb8 / deadpool PostgreSQL 生態：PgBouncer、Odyssey、PgCat；MySQL 生態：ProxySQL、Vitess VTGate

本地池消滅「新建連線的網路延遲」，外部 Pooler 消滅「微服務實例數乘出來的後端行程膨脹」，兩者互不替代。

外部 Pooler 擺在哪裡？三種部署拓樸的權衡

  • 獨立集中式代理叢集（Centralized Pooler Deployment）：最常見做法。多台無狀態 PgBouncer 掛在內部負載平衡器後，或由客戶端設定多組位址連線。優點是能在全域精確控管總後端連線上限（例如 3 台 PgBouncer 各配 default_pool_size = 12，主庫保證不超過 36 條）；缺點是多一跳網路 RTT（同可用區約 0.2–0.4 ms）。
  • App Pod Sidecar 模式：每個業務 Pod 旁掛一個 PgBouncer 容器走 localhost Unix Domain Socket，零額外網路跳數，特別適合單 Pod 內有多個 worker 行程（如 Python Gunicorn / PHP-FPM）的語言；但因為每個 Pod 各自一顆 Sidecar，若 Pod 數極多仍可能讓各 Sidecar 至少保底 1 條連線而撐大總數。
  • 與資料庫同機部署（Co-located on DB Host）：直接跑在資料庫主機上透過 Unix Socket 連 postgres，全域配額最精準且省去後端網路棧開銷。需注意傳統 PgBouncer 為單執行緒事件迴圈（libevent），高 TLS 卸載或數萬 QPS 時單核會先滿載，實務上常開啟 so_reuseport = 1 啟動多個 PgBouncer 行程分攤單機負載，或採用原生多執行緒的 Odyssey / PgCat。
一句話答法應用端連線池負責省掉「單一容器內的建連開銷與執行緒排隊」，外部 Pooler（如 PgBouncer）則負責把「幾百個微服務容器乘出來的數千條閒置長連線」多工收斂成資料庫 CPU 最舒服的幾十條後端連線，兩者搭配才能同時兼顧微服務彈性擴縮與資料庫穩定性。
05

Session、Transaction 與 Statement 三種 Pooling 模式

外部 Pooler 何時能把後端連線轉借別人？拆解多工壓縮率與 Prepared Statement、Session 變數的破壞邊界。

外部 Pooler 之所以能把 2,000 條前端連線壓縮成 30 條後端連線，秘密只有一個：趁前端不跑 SQL 的空檔，偷偷把後端連線拔下來借給別人用。但問題來了——關聯式資料庫的連線並不是純無狀態的 HTTP 管線，它身上掛著 Session 變數、預編譯語句（Prepared Statements）、暫存表與鎖。Pooler 在哪一個時間邊界切換連線，直接決定了你能拿到幾倍壓縮率，以及會弄壞哪些資料庫功能。

三種 Pooling 模式的借還邊界

  1. Session Pooling（工作階段級）：客戶端建立 TCP 連線時配發一條後端 postgres 連線，直到客戶端主動斷開 TCP 才收回。所有依賴連線狀態的功能 100% 正常運作；但當上游應用程式本身也開著長連線池時，Session 模式等於 1 對 1 死綁，多工壓縮率是 1.0x，只剩下幫忙擋 max_connections 排隊與省去後端建連的功能。
  2. Transaction Pooling（交易級，生產主力）：客戶端送出單條 Autocommit 語句或進入 BEGIN 時才指派後端連線；一旦收到 COMMIT 或 ROLLBACK，後端連線立刻歸還池中給下一個正在等待的 Pod。因為業務伺服器有 80%–95% 的時間花在解析請求、組裝物件與網路傳輸，Transaction 模式通常能輕鬆達成 5x 到 20x 的後端連線壓縮率。
  3. Statement Pooling（語句級）：每執行完單條 SQL 就立刻收回後端連線。只要應用程式送出跨語句的顯式交易（BEGIN; UPDATE ...; COMMIT;），PgBouncer 會直接報錯中止，因為前後兩條語句根本無法保證落在同一個後端行程上，實務上極少用於 OLTP 業務。

06

逾時、閒置回收與連線洩漏的生產診斷

對齊 NAT 靜默斷線與 maxLifetime，並用三層可觀測性指標定位吃光連線池的殭屍交易。

把連線池大小與 Pooling 模式調對只完成了前半場；後半場的高頻生產事故，幾乎都出在逾時邊界沒對齊、雲端網路設備靜默砍斷閒置連線，以及單一慢路徑把整個池子的槽位洩漏光。

四組關鍵生命週期參數與設定鐵律

  • 取連等待逾時（connectionTimeout / PgBouncer query_wait_timeout）：許多連線池預設高達 30 秒，這對線上 API 幾乎等於自殺——當資料庫短暫抖動時，上游 Web 容器的工作執行緒會全部卡死在等連線，拖垮連帶不查 DB 的健康檢查端點。線上微服務應壓低至 250 ms – 2,000 ms 快速失敗（Fail-fast）；至於上游收到逾時後如何避免無腦重試放大災情，請搭配 Timeout / Retry / Backoff 篇 的退避與預算原則。
  • 固定池 vs 動態伸縮池（minimumIdle 與 maximumPoolSize）：直覺上設定 minimumIdle = 2, maxPoolSize = 20 看似省資源，但實際效果是「平時省下區區幾十 MB，流量突刺殺到的那一秒卻被迫同步跑 18 次 TCP + TLS + SCRAM 認證建連」，把尖峰延遲推得更高。除非是極低頻背景服務，核心線上服務建議固定池大小（minimumIdle == maximumPoolSize）。
  • 最大存活時間（maxLifetime）對齊 NAT / 防火牆靜默斷線：AWS NLB（預設 350 秒閒置逾時）、NAT Gateway 或企業防火牆會在連線無封包往返時悄悄清除狀態表，但不發送 TCP RST。若應用程式的 maxLifetime 設為 30 分鐘且沒開 TCP Keepalive，借出這條「半開死連線（Half-open Connection）」送出 SQL 時，作業系統會卡在無回應的封包重傳十幾秒才報錯。鐵律是讓 maxLifetime 比沿途最短網路設備逾時少 30–60 秒，開啟定期探活（keepaliveTime），並加上 5%–10% 隨機抖動（Jitter）避免整池連線在同一秒集體到期重建。
  • 洩漏偵測與資料庫側最後保險絲：應用端開啟 leakDetectionThreshold（例如 5–10 秒未歸還即印出借用處 Stack Trace）；同時資料庫端務必設定 statement_timeout 與 idle_in_transaction_session_timeout（例如 15–30 秒），防止掛掉的容器或忘記 COMMIT 的程式碼永遠霸佔後端連線。

骨牌效應剖析：一條「Idle in Transaction」如何癱瘓全站

連線洩漏最陰險的地方在於：壞掉的往往只是一個冷門匯出功能，陪葬的卻是全站所有核心 API。而且卡在 idle in transaction 的連線不只是佔住一個池槽位——它還會同時釘死舊快照阻止垃圾回收（詳見 交易隔離級別與 MVCC 篇），並持續握住已修改資料列上的排他鎖（詳見 資料庫鎖與死鎖篇）：

三層診斷指標：十秒定位「卡在哪一層」

發生取連延遲告警時，依序對照這三組數字就能立刻鎖定根因：

  1. 應用端指標（如 HikariCP Metrics）：看 connections_active 是否貼齊 max、connections_pending（排隊執行緒數）是否飆升，以及 connections_usage_seconds（持連時間分佈）。若持連時間遠大於實際 SQL 耗時，代表應用程式借了連線卻在做非 DB 運算或忘記歸還。
  2. PgBouncer 管理埠（SHOW POOLS;）：觀察 cl_waiting（等待配發後端連線的客戶端數）、maxwait（最老等待秒數）與 sv_active（活躍後端數）。若 sv_active 已滿且 cl_waiting > 0，問題在後端查詢變慢或後端池開太小。
  3. 資料庫視圖（pg_stat_activity）：按 state 與 wait_event_type 分組。若大量處於 active 且等待 Lock，是鎖競爭；若大量處於 idle in transaction，立刻去抓業務程式碼的交易邊界洩漏。
陷阱把資料庫 CPU 低落誤判為「可以再調大連線池」

當上圖 t3 發生時（10 條連線全都因為等鎖或等外部 HTTP 而躺平，DB CPU 只有 2%），若不查 pg_stat_activity 就盲目把連線池調大 10 倍，只會製造出 100 條同樣卡住的殭屍交易，把連線洩漏升級成記憶體耗盡（OOM）與鎖表災難。

一句話答法生產環境必須設短取連逾時（Fail-fast）、令 maxLifetime 短於網路設備 NAT 閒置回收時間，並在資料庫端強制配置 idle_in_transaction_session_timeout；排查「DB CPU 很低但應用狂報逾時」時，優先檢查持連時間與殭屍交易洩漏。

面試深水區：四題高頻連環追問

Q1 · 大促前把微服務從 20 個 Pod 擴容到 120 個 Pod，結果流量還沒來資料庫就先掛了，發生什麼事？▸

這是典型的「連線乘法風暴」。若每個 Pod 啟動時預熱 minimumIdle = 15 條本地連線，120 個 Pod 同時拉起就會瞬間向資料庫發起 1,800 次 TLS + SCRAM 認證交握，並吃掉 1,800 個 postgres 行程槽位（耗費逾 15 GB RSS 記憶體且直接撞破 max_connections）。

根治方式：在微服務與資料庫之間補上 PgBouncer（Transaction Pooling），讓 1,800 條前端長連停在每條僅佔 2 KB 的事件迴圈層，後端嚴格鎖定在核心數 2–3 倍（如 32–48 條）的真實資料庫連線。

Q2 · 導入 PgBouncer Transaction Mode 後，偶爾出現 prepared statement "S_1" does not exist，甚至發生租戶資料串門子？▸

兩者都是因為連線級狀態跨越了交易邊界。在 Transaction 模式下，客戶端第一筆交易可能在後端連線 #2 執行 PREPARE S_1 或 SET app.current_tenant = '42'，COMMIT 後連線 #2 被轉借給其他客戶端（導致別人繼承了租戶 42 的變數），而原客戶端下一筆交易被派到從未準備過 S_1 的連線 #9 就直接報錯。

標準解法：① 所有會話變數一律改寫為交易結束即自動還原的 SET LOCAL；② 升級至 PgBouncer 1.21+ 並設定 max_prepared_statements = 200 由代理層維護客戶端與後端的語句映射表，或在舊版環境關閉驅動層的具名預編譯（如 JDBC prepareThreshold=0）。

Q3 · 為什麼報表匯出 API 跑 8 秒（QPS 只有 2），就能把耗時 2 ms 的核心下單 API（QPS 1,000）全部拖死？▸

依 Little 定律 L = λ * W：下單 API 雖然每秒 1,000 筆，但因耗時僅 0.002 秒，平均只佔用 1000 * 0.002 = 2 條連線；反觀報表 API 雖然每秒只有 2 筆，但每筆霸佔連線 8 秒，平均同時佔用 2 * 8 = 16 條連線！只要報表稍微併發到 3–4 筆，20 條的共用連線池就會被報表 100% 塞滿，所有 2 ms 就能跑完的下單請求全在門外排隊逾時。

解法：在應用端與 PgBouncer 層建立雙連線池隔離（Bulkhead），慢查詢走專屬小池（最好直接路由到 Read Replica），絕不與核心交易共用同一組連線槽位。

Q4 · 半夜低峰期過後每天早上第一批請求特別容易報 I/O 錯誤或卡住十幾秒，該查哪個參數？▸

查 maxLifetime、keepaliveTime 與中間網路設備（NLB / NAT / 防火牆）閒置逾時的不一致。低峰期連線長時間無流量，中間設備在 350 秒時靜默丟棄了 TCP 狀態表，但應用程式連線池以為連線還活著（maxLifetime 設了 30 分鐘）。早高峰第一個請求借到半開死連線發送封包，直接陷入作業系統 TCP 重傳黑洞。將 maxLifetime 調短至低於網路設備逾時（例如 240–300 秒）並啟用定期探活即可根除。

全篇總結秒答資料庫連線昂貴在建連交握與後端行程記憶體，Pool 開太小會排隊、開太大會因核心排程與鎖自旋陷入倒 U 型崩跌；用「核心數 2–3 倍」定錨後端活躍連線、以「本地池 + PgBouncer Transaction Mode」承接微服務水平擴展，再配齊 SET LOCAL、短取連逾時與殭屍交易自動斬斷，才是完整的生產級連線池架構。
